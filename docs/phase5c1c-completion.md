# Phase 5c-1c — MC の深度を Vulkan に渡して可視化する (深度経路の向き)

**状態**: **完了。** 実機で地形がグレー・空がマゼンタ・緑の四角が左上に出ることを確認
[確認済 — 目視]。地形を透過して mob が見える現象も無し (5c-1b の失敗例 12 の再発なし)。
**自動検査**: `interopCompositeCheck` **28 項目 PASS** (C10〜C13 を追加)、JUnit **180 PASS**
(`VkDepthVisualiseTest` 4 件を新設)。
**§4 の保留事項は実機で決着した** — 空の深度は<b>クリア値のまま</b>だった。

---

## 1. この段で何をしたか

**GL が書いて Vulkan が読む向き**を本番経路に初めて通した。

```
MC の深度 ──(GL 取り込み)──→ IOSurface(R32F) ──(Vulkan 可視化)──→ IOSurface(BGRA) ──(GL 合成)──→ 画面
   D32F        GlDepthImport                      VkDepthVisualise                GlInteropCompositor
```

5b までは<b>Vulkan が書いて GL が読む</b>向きだけだった。
**色 (5c-1b) とは別経路なので、片方の反転が他方を打ち消せない** [docs/phase5c-plan.md §9]。

| 追加したもの | 場所 | 役割 |
|---|---|---|
| `GlDepthImport` | main | MC の深度 (sampler2D) → interop R32F。値は<b>一切変換しない</b> |
| `VkDepthVisualise` | main | interop R32F → 色。グレー + 空を専用色 |
| `depth_visualise.vert/.frag` | resources | 可視化のシェーダ |
| `GlVkSync` | main | GL → Vulkan の同期 (フェンス)。5a の実測に基づく |
| `VkInteropImage.primeLayout()` | main | GL が書く前のレイアウト遷移 (§7.1) |
| `GlScratchFramebuffer` の RECTANGLE 対応 | main | interop を描き先にするため |
| C10〜C13 | `interopCompositeCheck` | 深度経路の自動検査 (§5) |
| `VkDepthVisualiseTest` | JUnit | 規約の結び付きを常時走る網に置く (§5) |

**画面は 5c-1b から変わる**: 赤い帯は落とし、<b>緑の四角だけ</b>残した。
四角は<b>色経路</b>の向きの目印として常設する — 深度側の向きがおかしいときに
「色も一緒に狂ったのか、深度だけか」を一目で切り分けられる。

## 2. 目視の判定基準 — **見る前に書き出す**

MC は OpenGL バックエンドで起動すること (`preferredGraphicsBackend:"default"`)。

```bash
./gradlew runClient
```

### 基準スクリーンショット: **平地に立って水平を見た状態**

この 1 枚に<b>独立した 3 つの事実</b>が収まる。

| # | 見るもの | 意味 |
|---|---|---|
| 1 | **画面の上半分が「遠い」** (マゼンタ<b>または</b>暗いグレー。§4) | 深度経路の Y の向き |
| 2 | **画面の下半分が明るいグレー** (近い地形) | 深度の値域と向き (手前が明るい) |
| 3 | **緑の四角が左上** | <b>色</b>経路の向き (5c-1b から引き継ぎ) |

**1 と 2 は同じ規約に依存しない** — 空が上・地面が下というのは
<b>Voxy の規約に一切関係しない物理的な事実</b>である [規約 4]。

### ⚠ 対照の 2 視点 — **片方だけでは「たまたま」と区別できない**

水平を見た 1 枚だけでは、<b>偶然そう見えた</b>可能性を排除できない。
7 例目と 5c-1e の設計と同じ理由で、<b>視点を振って予測どおりに変わること</b>を見る。

| 視点 | 予測される画面 |
|---|---|
| **真上を見上げる** | <b>全面が「遠い」</b> (一様。マゼンタか暗いグレー) |
| **真下を見下ろす** | <b>全面が明るいグレー</b> (近い地形しかない) |

**2 枚とも撮ること。** 見上げて全面が明るいグレーになったら、深度が反転している。

### 実機での結果 [確認済 — 目視]

| # | 見たもの | 判定 |
|---|---|---|
| 1 | 空が<b>マゼンタ</b>で画面の上 | ✅ 深度経路の Y は正しい |
| 2 | 地形が<b>グレー</b>で下ほど明るい | ✅ 値域・向きとも正しい (手前が明るい) |
| 3 | <b>緑の四角が左上</b> | ✅ 色経路の向きも保たれている |
| 4 | 地形を<b>透過して mob が見えない</b> | ✅ 5c-1b の失敗例 12 (深度バッファの破壊) が再発していない |

### ⚠ 水が青いのは<b>正常</b> — むしろ深度が無事である証拠

実機では<b>水だけが普通の青</b>で見える。可視化はグレーとマゼンタしか出力しないので
一見おかしいが、これは<b>合成の後に MC が描いたもの</b>である。

```
... → 地形 (CUTOUT) ← ★ここで合成 → 半透明 (水) → エンティティ → 雲・パーティクル → UI
```

Voxy が注入するのは Sodium の <b>CUTOUT パス</b>なので、
<b>半透明 (水) と mob はその後に描かれ、合成した絵の上に乗る</b>。

> **これは 2 つのことを同時に示している:**
> 1. <b>MC の深度バッファが壊れていない</b> — 水は地形の深度に対して深度テストされて
>    正しい位置に出た。潰していれば水の前後関係が崩れる
> 2. <b>合成が後続の描画を壊していない</b> — GL 状態の復帰が効いている (5c-1b §9 / §12 の型)

**5c-1d 以降も同じことが起きる。** 合成した Voxy の絵の上に、
MC の半透明とエンティティが乗る。これは<b>意図した順序</b>である
(既存の GL 経路も同じ位置に注入している)。

### 失敗したときの読み方

| 症状 | 意味 |
|---|---|
| 上下が逆 (見上げると明るい) | **深度経路の Y が反転**。`GlDepthImport` か可視化のどちらか |
| 緑の四角が右下 | **色経路**の向きが狂った (深度とは別の原因) |
| 画面が一様 (濃淡が無い) | 深度が届いていない。ログの `depth in interop:` を見る (§3) |
| 全面が真っ黒 | テクスチャの読みが失敗している。`-Pvoxy5c1c=solid` で切り分ける |
| 地形・mob が壊れる | GL 状態の復帰漏れ [5c-1b §9 と同じ型] |

### 切り分けスイッチ (再ビルド不要)

```bash
./gradlew runClient -Pvoxy5c1c=off       # 合成を止める (5c-1a と同じ)
./gradlew runClient -Pvoxy5c1c=state     # FBO/ビューポートの控え・復帰だけ
./gradlew runClient -Pvoxy5c1c=pattern   # 5c-1b の非対称パターン (深度に触らない既知の正解)
./gradlew runClient -Pvoxy5c1c=solid     # テクスチャを読まずマゼンタ一色
./gradlew runClient -Pvoxy5c1c=full      # 全経路 (既定)
```

`pattern` が<b>この段で最も価値のあるスイッチ</b>である —
5c-1b で目視確認済みの絵がそのまま出るので、<b>色経路が健在かどうかを 1 手で確かめられる</b>。

## 3. 診断ログ — 1 行で経路上の複数の事実を出す

5c-1b では 1 行に 4 つの事実を詰めたことで<b>4 往復の切り分けが 1 回で済んだ</b> [§8.5]。
5c-1c は経路が 1 段長いので、<b>深度が interop に届いているか</b>を最初から出す。

```
[5c-1c] frame 0 mode=FULL mcColourTex=.. mcDepthTex=.. target=1708x960 drawFbo=.. viewport=[..] ...
[5c-1c]   depth in interop: top-of-picture=0.0 middle=0.0234 bottom-of-picture=0.187
             [reverse-Z: 1.0 = nearest, 0.0 = FAR = sky/never drawn]
[5c-1c]   colour in interop: top-of-picture=[255,0,255,255] ... [BGRA bytes]
```

**この 3 行があれば、絵が出ない場合でも前半 (Vulkan まで) と後半 (GL 合成) を切り分けられる。**

## 4. 空の深度 — **クリア値のままだった** [確認済 — 実機]

> **決着済み。** 実機で<b>空はマゼンタ</b>だった。可視化は `z == FAR` の
> <b>完全一致</b>で判定しているので、これは
> 「空の画素の深度が<b>厳密にクリア値</b>である」ことを意味する。
> **以下は判断時の記録であり、§4.1 の推論は観測では現れなかった。**

当初は「空 = 深度がクリア値のまま = マゼンタ」を判定基準にする予定だったが、
実装後の調査で<b>保証できない</b>と分かったため、両方の場合を想定して基準を書いた。
結果として当初の想定どおりになった。

### 4.1 調査結果 [確認済 — バイトコード]

| 事実 | 根拠 |
|---|---|
| MC の `SKY` パイプラインは深度状態を<b>上書きしていない</b> | `RenderPipelines` の `SKY` は `MATRICES_FOG_SNIPPET` から作られ、`withDepthWrite` 等を呼んでいない |
| したがって `DepthStencilState.DEFAULT` が効く | `DEFAULT` = (`GREATER_THAN_OR_EQUAL`, **writeDepth = true**) |
| sky パスは<b>深度を持つメインターゲット</b>に描く | `LevelRenderer.addSkyPass` が `targets.main` を `readsAndWrites` |

つまり **MC の空は深度を書きうる**。書かれていれば、空の画素は
クリア値ではなく<b>空ドームの深度</b>を持ち、可視化は<b>マゼンタではなく暗いグレー</b>になる。

### 4.2 どちらでも経路としては正しい

| 画面上端 | 意味 |
|---|---|
| **マゼンタ** | 空の画素が深度クリア値のまま (`z == FAR`) |
| **暗いグレー** | 空ドームが自前の深度を書いている |

**どちらも 5c-1c の合格である。** 判定に使うのは<b>明暗の向き</b> —
<b>上が遠い (暗い / マゼンタ)、下が近い (明るい)</b> — であり、これは両方の場合に成立する。

### 4.3 実機での結果 — **クリア値のまま** [確認済]

空はマゼンタで出た。したがって<b>Voxy の注入点 (Sodium の CUTOUT パス) の時点では、
空の画素の深度はクリア値 (`FAR`) である</b>。

> ⚠ **§4.1 の推論と観測が食い違っている。**
> `SKY` パイプラインは確かに writeDepth = true だが、
> <b>注入点で観測される深度はクリア値だった</b>。
> 機構 (深度が後で消されているのか、空ドームの描画が深度に届いていないのか) は
> **[未検証]**。5c-1e に必要なのは<b>観測された事実</b>のほうなので、ここでは追わない。

**5c-1e への含意**: 空の画素は深度テストで Voxy の LoD を落とさない。
つまり<b>遠景の LoD は空の領域に描ける</b> — これは 5c-1e で確かめたい前後関係の前提になる。

## 5. 自動検査 — 何が言えて、何が言えないか

### 5.1 `interopCompositeCheck` の C10〜C13 (GL + Vulkan)

| 検査 | 内容 |
|---|---|
| **C10a** | パターンが<b>行を区別できる</b>こと (行ごとに異なる深度。一様な帯ではずれを見逃す) |
| **C10** | MC 相当の深度テクスチャの内容が interop に<b>ビット単位で</b>届くこと |
| **C10 感度** | <b>反転した取り込みでは落ちること</b>、かつ<b>その結果が本当に鏡像であること</b> |
| **C11** | クリア値の画素<b>だけ</b>が空の色になること / 描かれた画素はグレーであること |
| **C11** | <b>手前ほど明るい</b>こと、かつ<b>使える幅がある</b>こと |
| **C12** | <b>ホストが残したサンプラ</b>が取り込みに影響しないこと + <b>それを使う実装は壊れること</b> |
| **C13** | <b>ホストが残したテクスチャパラメータ</b>について同上 |

### 5.2 ⚠ 言えること / 言えないこと

| | |
|---|---|
| **言える** | <b>行と値の保存</b> — GL が行 N に書いた深度が Vulkan 側の行 N にビット単位で届く |
| **言える** | <b>空の判定が `VkDepth.FAR` に結び付いている</b> (規約を変えれば落ちる) |
| **言えない** | <b>行 N が画面の上か下か</b>。生成も検証も同じ「framebuffer の行」を参照しているので、規約が反転すれば<b>両方が反転して一致する</b> [規約 4] |

**だから §2 の目視が要る。** 機械的検査は反転の打ち消しに弱く、5b で実際に素通りした。

### 5.3 JUnit `VkDepthVisualiseTest` (GL 不要、常時走る)

`interopCompositeCheck` は GL コンテキストが要るので手で走らせる検査である。
**規約の結び付きだけは常時走る網に置く** — 逆Zを外したときに
可視化だけが取り残されるのを防ぐため [規約 6]。

| テスト | 守るもの |
|---|---|
| `onlyTheFarTexelsBecomeTheSkyColour` | 空の判定が `VkDepth.FAR` 由来であること (+ 全部が空の色でないこと) |
| `drawnTexelsAreGrey` | 深度以外の情報が混ざっていないこと |
| `nearerDepthIsBrighter` | 値の順序と、読める幅があること |
| `rowsAreNotShuffled` | 1 行だけ印を付け、その行に出ること |

### 5.4 感度の確認 — **変異させて落ちることを見た** [確認済]

検査を書いたら「この検査を空虚に満たす方法」を潰す。実際に 2 つ変異を入れた:

| 変異 | 結果 |
|---|---|
| 空の番人を `z == FAR` → `z == NEAR` (規約の結び付きを切る) | `onlyTheFarTexelsBecomeTheSkyColour` が **FAILED** (他 3 件は PASS = 変異を正しく切り分けている) |
| 可視化の読みに上下反転を入れる | **4 件すべて FAILED** |

C10 の感度対照も同様に、反転した取り込みで落ちることを確かめてある。

## 6. `pow(z, 1/8)` の指数について — **任意の定数である**

**見やすさのために選んだ定数であり、物理量ではない。** 後で値域を議論するときに
「どこかから導いた値」と誤解されないよう、根拠をここに残す。

### 6.1 なぜ生値ではだめか

逆Z・0..1 の投影では、距離 `d` の点の深度は

```
z(d) = n*(f-d) / (d*(f-n))          n = near, f = far
```

で、`f >> n` のとき **`z ≈ n/d`** である。MC の near は 0.05 なので:

| 距離 | 生の深度 `z` | `pow(z, 1/8)` |
|---:|---:|---:|
| 1 ブロック | 0.05 | **0.69** |
| 8 | 0.00625 | **0.53** |
| 64 | 0.00078 | **0.41** |
| 512 | 0.000098 | **0.32** |

**生値のままでは 8 ブロック先で既に 0.006** — 輝度にすると 1/255 未満で、
画面はほぼ真っ黒になる。それでは「地形の形が見える」という
この段の確認ができない。

### 6.2 なぜ 1/8 か

`pow(0.5, 1/8) = 0.917` なので、**距離が 2 倍になるごとに輝度が約 8.3% 下がる**。
1〜512 ブロックが 0.69〜0.32 に収まり、<b>グレーの帯域全体を使い切る</b>。
段差が目で追える範囲に入る、というだけの理由である。

> **⚠ どのテストもこの指数を固定していない。** 検査が要求しているのは
> 「単調であること」と「幅が 32/255 以上あること」だけである。
> 指数を変えたければ変えてよい — <b>表示の選択</b>であって規約ではない。

実装では `VkDepthVisualise.GAMMA` に置き、シェーダには define で渡している
(2 箇所に数値を書かないため)。

## 7. 実装で分かったこと

### 7.1 ⚠ GL が書き手になった瞬間、レイアウトの初期遷移が地雷になる

`VkInteropImage` のレイアウト追跡は生成直後 `UNDEFINED` から始まる。
`UNDEFINED` からの遷移は<b>「内容を捨ててよい」という宣言</b>なので、
**GL が先に書いた画像に対して最初の `toGeneral` を出すと、その書き込みが捨てられる**
[docs/phase5a-gl-to-vk-sync.md §6.1]。

- 5b までは<b>Vulkan が書き手</b>だったので問題にならなかった (捨てられて困る内容が無い)
- 症状は「**最初の 1 フレームだけ深度が化ける**」で、
  <b>2 フレーム目以降を見ていれば検査も目視も通ってしまう</b>

Phase 5a のベンチは同じことを<b>外側で</b>処理していた (`primeLayout`)。
**制約が分かっているならクラス側に持たせる** [規約 6] — `VkInteropImage.primeLayout()` を
足し、生成時に必ず呼ぶことで呼び忘れの余地を消した。

### 7.2 ⚠ 規約 7 (ホストが残す状態) を<b>オフスクリーンで閉じられた</b>

5c-1b の黒画面は<b>MC が残したサンプラオブジェクト</b>が原因で、
「対照環境に存在しない要素は対照では検出できない」という形で規約 7 になった [§12.2]。

**今回はそれを検査側で作った。** C12 / C13 が
<b>敵対的なサンプラとテクスチャパラメータを自分で bind してから</b>取り込みを走らせる。
`GlDepthImport.Defect.NO_SAMPLER_RESET` が対照で、
これを使うと<b>実際にドライバが同じ苦情を出す</b>:

```
UNSUPPORTED (log once): POSSIBLE ISSUE: unit 0 GLD_TEXTURE_INDEX_2D is unloadable
and bound to sampler type (Float) - using zero texture because texture unloadable
```

> **5c-1b で画面が黒くなった機構が、オフスクリーンの検査で再現できるようになった。**
> 規約 7 は「ホストの状態を洗い出せ」だが、<b>洗い出したら検査に持ち込める</b>。

### 7.3 深度テクスチャは<b>サンプラを自分で持つ</b>べき理由が 2 つある

| 残っていると | 症状 |
|---|---|
| mipmap フィルタ | テクスチャが incomplete 扱いになり<b>黒</b>が返る |
| `GL_TEXTURE_COMPARE_MODE` | 深度値ではなく<b>比較結果 (0 か 1)</b> が返る |

どちらも「黒い / 二値の深度」として現れ、**絵を見ても取り違えやすい**。
既存の GL 経路が `DEPTH_SAMPLER` を持っていたのはこのためである
[確認済 — `AbstractRenderPipeline`]。**既存コードの「一見不要な処理」を先に読む** [規約 7]。

> 自動検査に載せたのは mipmap フィルタだけである。
> 比較モードを `sampler2D` で読む挙動は<b>仕様上未定義</b>なので、
> 対照にすると環境依存で揺れる。防御は入れてあるが、検査は well-defined なものに限った。

### 7.4 GL → Vulkan の同期は<b>フェンス</b>にした

`glFinish` とコストはほぼ同じ (5a の表で差 0.03 ms 程度) だが、
フェンスは<b>待つ対象がこのフレームの GL 作業に限定される</b>。
`glFinish` は GL のパイプライン全体を空にするので、
**Voxy と無関係な MC の作業まで巻き込む**。

> ⚠ **「同期無しでも値が合った」ことは同期が不要である証拠にならない。**
> Phase 5a は約 800 回試して陳腐な読みを 1 度も構成できなかったが、
> それは「起きない」ことの証明ではない [未検証]。

## 8. 次の段 (5c-1d) に持ち込むもの

- Phase 4 の**合成地形**を実際に Vulkan で描いて合成する
- そのとき **`GlInteropCompositor` を `writeDepth = true` に戻す** —
