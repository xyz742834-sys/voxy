## 1. この段で何をしたか

Phase 4 の合成地形 (`SyntheticTerrain.boundaryCases()`) を Vulkan で描き、
色と深度の両方を MC のフレームバッファへ合成する。

```
合成地形 ──(VkTerrainRenderer)──→ interop 色(BGRA) ──┐
                     └(VkDepthResolve)→ interop 深度(R32F) ─┴→ GL 合成 → MC の色 + 深度
```

| 追加・変更したもの | 役割 |
|---|---|
| `GlInteropCompositor.DepthMode` | 深度の扱いを 3 通りに明示 (§2) |
| `VkDepth.GL_CLOSER_EQUAL_COMPARE` | GL 側の比較関数を規約から出す (2 箇所に書かない) |
| `SyntheticTerrain.writePositions(buf, anchor)` / `alignAnchor` | 地形をプレイヤーの近くに置く (§3) |
| `VkInteropProbe` の `TERRAIN` モード | 描画・解決・合成の配線 |
| C14 (6 項目) | 深度テストする合成の検査と感度対照 (§4) |

## 2. ⚠ 深度をどう書くか — <b>ここは一度壊した場所である</b>

5c-1b では合成が `GL_ALWAYS` + 深度書き込みのまま走り、
**MC の深度バッファを一様に潰して mob が地形を貫通した**
[docs/phase5c1b-completion.md §9]。
今回は Voxy の<b>実深度</b>を書くので状況は違うが、場所は同じである。

### 2.1 3 つのモードに分けた

| モード | 深度 | 使う場所 |
|---|---|---|
| `NONE` | 書かない・テストもしない | 5c-1b / 5c-1c (まだ Voxy の深度が無い段) |
| `OVERWRITE` | `GL_ALWAYS` で無条件に書く | **5b のオフスクリーン比較専用**。ホストで使ってはならない |
| **`TEST`** | 描いた画素だけ、MC と比べて勝ったら書く | **5c-1d 以降の本番** |

### 2.2 `TEST` は<b>2 つの条件が同時に</b>要る

```glsl
if (texelFetch(depthTex, c).r == 0.0) discard;   // ← 条件 1 (クリア値 = 何も描いていない)
fragColour  = texelFetch(colourTex, c);
gl_FragDepth = texelFetch(depthTex, c).r;
```
```java
glDepthFunc(VkDepth.GL_CLOSER_EQUAL_COMPARE);    // ← 条件 2 (GL_GEQUAL)
glDepthMask(true);
```

**片方だけでは足りない**:

| 欠けるもの | 何が起きるか |
|---|---|
| `discard` が無い | Voxy が何も描いていない画素の深度は<b>クリア値 (FAR = 0.0)</b> で、これは<b>MC の空と同じ値</b>である。`GEQUAL` は等号を含むので<b>空が Voxy のクリア色で塗り潰される</b> |
| 深度テストが無い | MC の近景地形より奥の LoD が<b>手前に描かれる</b> (= 5c-1b の再来) |

> クリア値を GLSL に直書きせず `VkDepth.CLEAR` から出している。
> 逆Zをやめるなら合成も一緒に変わらなければならない [規約 6]。

### 2.3 ⚠⚠ <b>深度は同じ投影空間になければ比べられない</b> — 5c-2 以降の宿題

`TEST` が成立する前提は <b>Voxy の深度と MC の深度が同じ投影空間にあること</b>である。
**5c-1d は MC の投影をそのまま使うことでこれを満たしている。**

しかし<b>本番の Voxy は自前の投影で描く</b> [確認済 — `VoxyRenderSystem.computeProjectionMat`]:

```
near = 16 (描画距離が短ければ 8)      far = 16*3000 = 48000
```

遠景 LoD を MC の far 平面の外まで描くためで、
**この深度をそのまま MC の深度バッファに書くと値の意味が食い違う。**
既存の GL 経路はこれを知っていて、書き戻す前に
`transformBlitDepth` が <b>`inverse(viewport.MVP)` と目標の投影で深度を再投影</b>している
[確認済 — `AbstractRenderPipeline.transformBlitDepth`]。

> **5c-1d では再投影を持ち込まない。**
> MC の投影で描けば深度は最初から MC と同じ空間にあり、
> <b>この段で増える未知が「深度を書くこと」1 つに収まる</b>。
>
> ⚠ **その代わり、この設定では遠景 LoD は MC の far 平面で切られる。**
> 自前の投影 + 深度の再投影は <b>5c-2 以降で必要になる</b>。
> 合成データが near 側にあるうちは表面化しない — <b>忘れやすいので明記する</b>。

## 3. 地形をどこに置くか

合成地形の世界座標はデータセット固定 (原点付近) なので、そのままでは
プレイヤーがどこにいるかで見えたり見えなかったりする。
**プレイヤーのセクションに追従させる。**

```
アンカー = alignNearest(セクション(カメラ + 視線*96) - データセットの中心)
位置     = 各セクション座標 + (アンカー >> そのセクションの LoD レベル)
MVP      = MC の projection * modelView, その後 -(カメラ - アンカー*32) だけ平行移動
```

| 決めたこと | 理由 |
|---|---|
| <b>カメラの正面</b> 96 ブロック先に置く | 固定の方角だと<b>そちらを向いていなければ見えず</b>、不具合と区別が付かない (§6 で実際に踏んだ) |
| 視線の<b>水平成分だけ</b>を使う | 見上げ / 見下ろしで地形が空や地中へ飛ばないように |
| Y は<b>カメラのセクションのまま</b> | 地面をまたがせて、<b>一部が MC の地形に隠れる</b>状況を作る (5c-1e の前哨戦) |
| アンカーを `1 << maxLevel` の倍数に<b>最近傍で</b>丸める | 位置は<b>そのセクションの LoD 空間</b>にあるので `anchor >> level` を足す。倍数でないと<b>レベルの違うセクションだけがずれる</b>。切り下げだとずれが距離と同程度になり<b>方角によって画面から外れる</b> (§6.4) |

計算は [`VkHostViewport`](../src/main/java/me/cortex/voxy/client/core/vk/VkHostViewport.java) に
切り出してあり、`VkHostViewportTest` が<b>24 方位すべてで画面に載ること</b>を要求する。

> **式そのものは本番の GL 経路と同じ**である
> [確認済 — `MDICSectionRenderer.uploadUniformBuffer`]。
> 本番は<b>アンカー = カメラのセクション</b>で、平行移動が「セクション内の端数」に縮退する。
> ここだけ違うのは地形を近くに置きたいからで、<b>経路は同じ</b>。

⚠ **描画モードは `PER_SECTION`** — オフスクリーンの基準と同じ経路である。
本番の統合描画 (`MERGED`) は cmdgen / HiZ が要るので **5c-4** で入る。

## 4. 自動検査 C14 — <b>目視の前に機械で確かめる</b>

MC を起動しなくても、<b>「MC が描いた後」の状態を作って</b>合成できる。

```
左半分: 深度 = mcNear (Voxy のどの断片より手前)  → Voxy は 1 画素も出てはならない
右半分: 深度 = FAR    (空)                       → Voxy が描いた画素だけ出る
```

| 検査 | 主張 |
|---|---|
| C14 control | 絵に地形があり、かつ<b>Voxy より手前の深度が選べている</b> (でないと「たまたま隠れた」と区別できない) |
| **C14a** | MC の近景がある側で Voxy が出ない = <b>Voxy が MC を不当に隠さない</b> |
| **C14b** | 空の側では Voxy が出る = <b>隠しすぎてもいない</b> |
| **C14c** | Voxy が描いていない画素は MC の色が残る = <b>クリア色が漏れない</b> |
| C14 感度 | `OVERWRITE` にすると **C14a と C14c が落ちる**こと |

感度の 2 本が無いと、C14a/C14c は「合成のモードを区別していない」検査かもしれない。

**出力**: `build/vk-test-output/5c1d-depth-tested-composite.png`。
左半分が一様な MC 色、右半分に地形が出て、<b>境界がちょうど中央で切れている</b>。

> ⚠ **これで言えるのは「深度テストが効いていること」までである。**
> MC の描画順との噛み合い (半透明・エンティティ・雲が後から正しく乗るか) は
> <b>ホストの中でしか確かめられない</b> [規約 7]。それが §5 の目視である。

出たら「描いていない画素を捨てる」条件が効いていないということで、
**目立つ色にしてあるので一目で分かる**。

### 5.2 ⚠ 2 と 3 が<b>最も重要</b> — 5c-1c から引き継いだ対照

5c-1c で「水が青く正しい前後で見える」ことを確認した。
**その時点では深度を書いていなかった。**
5c-1d は深度を書き始めるので、<b>同じ観察が同じ結果になるか</b>が
そのまま「書き方が正しいか」の対照になる。

| 水の見え方 | 意味 |

| 青く、正しい前後 | ✅ 深度の書き方が正しい |
| 水が消える / 手前に出すぎる | ❌ 深度を潰したか、値の空間が食い違っている (§2.3) |

**mob が地形を貫通したら 5c-1b の失敗例 12 の再来**である。

## 6. ⚠ 実機で「橙一色」— 置き場所が原因だった (切り分けの記録)

初回の実機確認で<b>合成地形が 1 つも見えなかった</b>。
画面は Voxy のクリア色 (橙) で埋まり、水・雲・MOB・UI だけが上に乗っていた。

### 6.1 診断が 3 手で決着させた

| 手 | モード | 結果 | 分かったこと |
|---|---|---|---|
| 1 | `terrain` (既定) | 普通の MC に見える | 合成が画面を変えていない。だが原因は不明 |
| 2 | `terrain-nodepth` | <b>橙一色</b> | <b>合成は届いている</b>。地形が画面に無い。深度テストは無罪 |
| 3 | `terrain-refmvp` | <b>地形が見えた</b> | <b>Vulkan 側は健在</b>。原因は<b>MC 由来の MVP か置き場所</b>に確定 |

ログの数字が同じことを直接言っていた:

```
voxy footprint: drawn=20663 of 1639680 bbox=[598,331 .. 1405,549] nearestDepth=0.0087
```

> **`drawn` を数える 1 行が効いた。** 「見えない」は
> <b>描けていない / 画面外 / 深度で落ちた</b>の 3 通りあり、
> 目視では区別が付かない。数字はそれを直接分ける。

### 6.2 原因 — <b>固定の方角に置いていた</b>

地形はカメラのセクション + 一定のオフセット (東・南に 2 セクション) に置いていた。
**プレイヤーがそちらを向いていなければ何も見えない。**
経路は最初から正しく動いていた。

> ⚠ **「見えない」が不具合と区別できない置き方をしていた。**
> オフスクリーンの検査は視点を固定できるので、この欠陥は<b>ホストでしか現れない</b> [規約 7]。

### 6.3 修正 — カメラの正面に置き、<b>式を素の JVM に出す</b>

| 変更 | 理由 |
|---|---|
| 置き場所を<b>カメラの正面</b> (視線方向 96 ブロック先) に | <b>見えないこと自体が不具合の証拠</b>になる |
| 計算を `VkHostViewport` に切り出し | ホストの中でしか走らない計算を<b>素の JVM で確かめられる</b>ようにする |
| アンカーの丸めを<b>切り下げ → 最近傍</b>に | §6.4 |

### 6.4 ⚠ 切り出した直後にテストが<b>別の欠陥</b>を捕まえた

`VkHostViewportTest` を書いてすぐ落ちた:

```
yaw 45 deg: the terrain centre landed off screen at ndc=(-1.4030268,-0.2942885)
```

アンカーは `1 << maxLevel` の倍数に<b>切り下げ</b>ていた (量子 = 2 セクション = 64 ブロック)。
それが<b>距離 (64 ブロック) と同程度</b>だったので、方角によっては<b>最大 45°</b> ずれ、
正面に置いたつもりでも画面から外れる。

**最近傍に丸め (ずれが半分)、距離を 96 ブロックに伸ばした。**

> **目視だけで直していたら、この欠陥は「たまに見えない」として残っていた。**
> 24 方位で要求する検査が<b>1 発で位置を特定した</b>。

### 6.5 ⚠⚠⚠ 3 つ目 — <b>視線の向きを決め打ちしていた</b> (失敗例 15)

正面に置いても<b>まだ見えなかった</b>。実機ログが 1 行で答えを出した:

```
modelViewTranslation=(0,0,0)   centreNDC=(0.023, 0.448, -0.9986)   drawn=0
```

- `modelViewTranslation` が 0 → 「平行移動を含んでいる」説は<b>否定</b>
- `sub` から逆算すると地形中心は<b>カメラから約 70 ブロック</b>
- なのに <b>z が負</b> = 視錐台の外

**距離 70 の点が範囲外になるのは、その点がカメラの<b>後ろ</b>にあるとき**である。
後ろの点は {@code w < 0} になり、透視除算で符号が反転するので
<b>NDC の xy だけ見ると画面内に見える</b>。実際 `(0.023, 0.448)` は範囲内だった。

> ⚠ **NDC の xy だけで「画面内」と判断してはならない。必ず {@code w > 0} を見る。**

原因は `forward()` が<b>「前 = -positiveZ」と決め打ち</b>していたこと。
MC の投影は eye-Z の向きが逆で、地形は<b>カメラの真後ろ</b>に置かれていた。

#### そして<b>それを検査した JUnit も同じ決め打ちを共有していた</b> [規約 4]

テストは自分でビュー行列を作り、同じ `forward()` で配置し、同じ `perspective()` で
投影していた。<b>規約が反転していても全部が一緒に反転して一致する。</b>
5c-1d 以前に 2 度踏んだのと同じ型が、<b>3 度目に</b>出た。

#### 直し方 — <b>向きを推測せず、投影して確かめる</b>

`anchorInFront` は<b>両方の向きを試し、実際にクリップ座標を計算して
カメラの前に来るほうを選ぶ</b>。判定に使うのは<b>投影という外部の事実</b>だけで、
向きの規約に依存しない。

> ⚠ **この修正だけでは直らなかった。** 本当の原因は §6.6 だった。
> 向きの決め打ちは<b>確かに直すべき</b>だったが、症状の原因ではなかった。

#### ⚠ 対照の作り方も 1 度間違えた

「逆向き」を模すのに<b>ビュー行列を 180° 回した</b>が、
{@code positiveZ} も一緒に回るので<b>前の向きは変わらない</b> (ただのヨー変更)。
決め打ちの実装に戻しても<b>検査は通ってしまった</b>。

規約差は<b>投影側の eye-Z の向き</b>にある。投影を {@code scale(1,1,-1)} した対を渡すと、
決め打ちの実装は正しく落ちる:

```
yaw 0 deg (eye +Z): w=-68.8 (<= 0 means the terrain is BEHIND the camera)
```

> **対照そのものが空虚でないかを確かめる手順が要る。**
> 「変異させて落ちること」を見なければ、この対照は<b>何も守っていなかった</b>。

### 6.6 ⚠⚠⚠⚠ 本当の原因 — <b>MC の投影は逆Z・-1..1 だった</b> (失敗例 16)

向きを直しても<b>まだ 1 画素も出なかった</b>。ログの数字を最後まで追うと決着した:

```
forward=(-0.117, 0.028, -0.993)   anchor=[-2,4,-6]   sub=(54.9, -14.7, 153.6)
centreNDC=(0.153, 0.119, -0.9992)   drawn=0
```

`sub` から逆算すると地形中心は<b>カメラ相対 (9.1, 14.7, -121.6)</b>、
`forward` との内積は **+120** — <b>間違いなく前方 120 ブロック</b>にある。
それでも z が -0.999。

**前方の点が z ≈ -1 になるのは、その投影が -1..1 の深度を出しているときである。**
逆Z・-1..1 の式に距離 120 を入れると -0.999 で、実測と 3 桁一致した。

| | |
|---|---|
| **Vulkan のクリップ空間** | <b>常に 0..1</b>。切り替える手段は無い |
| **MC の投影行列** | <b>逆Z・-1..1</b> [確認済 — 実機の数値] |
| **結果** | z &lt; 0 の断片が<b>全部クリップされる</b> = 1 画素も残らない |

> ⚠ **既存コードは知っていた。** `VoxyRenderSystem.computeProjectionMat` は
> {@code isZero2One()} を見て <b>m22/m32 を書き換えている</b>。
> 「MC の投影をそのまま使う」と決めたとき、<b>この工程を飛ばした</b>
> — また「既存コードの一見不要な処理」を読まずに落とした型である [規約 7]。

#### なぜ「両方の向きを試す」が効かなかったか

向きの判定に {@code insideFrustum} (z ∈ (0,1) を含む) を使っていたので、
<b>深度規約が違うと どちらの向きも落ちて</b> fallback に戻っていた。

> **判定条件を混ぜてはならない。** 向きは {@code w > 0} だけで決まる。
> 深度の範囲は<b>別の問題</b>で、別に直す。

#### 直し方 — ここでも<b>推測せず検算する</b>

`projectionForVulkan` が<b>そのまま使った場合の深度を計算し、
{@code (0,1)} に入らなければ {@code z' = (z+w)/2} の変換を掛ける</b>。
ホストが将来 0..1 で渡してきても壊れない。

> **深度の値は MC のバッファと一致する。**
> {@code (z+1)/2} は、同じ near/far の逆Z 0..1 の式と<b>恒等的に等しい</b>。
> GL 側もクリップ空間から同じ変換でバッファへ書くので、
> <b>合成の深度テストが比べる 2 つの値は同じ空間にある</b> (§2.3 の前提)。

#### 検査

`VkHostViewportTest` に 0..1 と -1..1 の<b>両方のホスト</b>を通す検査と、
<b>変換を外すと -1..1 側が落ちる</b>対照を置いた。変異させると実機と同じ数字が出る:

```
yaw 0 deg (host -1..1): ndc=(-0.218, -0.152, -0.99906707)
```

### 6.7 ⚠⚠⚠⚠⚠ 4 つ目 — <b>合成先に深度アタッチメントが無かった</b> (失敗例 17)

地形は出るようになった。実機の確認は<b>4 項目中 3 つが OK</b>だった:

| # | 見たもの | 結果 |
|---|---|---|
| 1 | 水が青く、正しい前後 | ✅ |
| 2 | MOB・雲が正しい前後 | ✅ |
| 3 | <b>合成地形が MC の地形に隠される</b> | ❌ <b>NO</b> |
| 4 | 橙が出ない | ✅ |

**この 3 つの ✅ と 1 つの ❌ は、同じ 1 つの原因から出ている。**

`GlScratchFramebuffer` は<b>カラーしか付けていなかった</b>。
深度アタッチメントの無い FBO では:

- 深度テストが<b>常に通る</b> → Voxy が MC の地形に隠されない (3 が NO)
- {@code gl_FragDepth} の<b>書き先が無い</b> → MC の深度バッファは無傷 (1・2 が OK)

> ⚠ **壊れ方が「一見正常」である。**
> 「MC の深度を壊していない」ことを<b>正しさの証拠として読んでいた</b>が、
> 実際には<b>そもそも書けていなかった</b>だけだった。
> 5c-1b の教訓 (深度を潰すな) に引きずられ、<b>逆方向の失敗</b>を見落とした。

**既存の GL 経路は深度も付け替えていた**
[確認済 — {@code AbstractRenderPipeline.runPipeline} が
{@code bind(GL_DEPTH_ATTACHMENT, sourceDepthTexture)}]。
<b>3 度目の「既存コードが同じことを同じ方法で解いていた」</b>である。

#### ガードと対照 (C15)

深度テストする合成が<b>深度の無い描画先</b>に描いていたら数える。
これは<b>ホストの FBO の作り方</b>の問題なので、
検査が自分で FBO を作っている限り再現しない [規約 7] —
だから C15 は<b>わざと深度無しの FBO を作って</b>ガードが鳴ることと、
<b>深度がある描画先では鳴らないこと</b>の両方を要求する。

### 6.8 運用に足す規則

> **【規約 8】ホストの中でしか走らない計算は、<b>素の JVM で確かめられる形に切り出す</b>。**
> ホスト内でしか再現しない不具合は切り分けが高くつく (起動・目視・ログの往復)。
> 切り出せる計算を切り出しておけば、<b>MC 起動が要るのは「実際に見えるか」だけ</b>になる。
>
> 併せて: **診断は「見えるか」ではなく<b>数を出す</b>こと。**
> 「見えない」には複数の原因があり、目視はそれを区別しない。
>
> **【規約 9】ホスト側の規約 (向き・符号・深度の範囲) は<b>推測せず、確かめてから選ぶ</b>。**
> 決め打ちは<b>検査が同じ決め打ちを共有していれば素通りする</b> [規約 4]。
> 「両方試して、外部の事実 (投影結果) で選ぶ」なら規約を知らなくても正しくなる。
>
> **【規約 10】判定条件を混ぜない。**
> 向きは {@code w > 0}、深度の範囲は {@code z/w}。1 つの条件に束ねると、
> <b>片方が原因のときに両方の候補が落ちて選べなくなる</b>。
> 実際 5c-1d では「両方向を試す」修正が<b>深度規約の違いのせいで空振り</b>した。
>
> **【規約 11】「壊していない」を正しさの証拠にしない。**
> <b>そもそも効いていない</b>ときも同じ観察になる。
> 5c-1d では「MC の深度が無傷」を深度の書き方が正しい証拠として読んだが、
> 実際は書き先が無かっただけだった。<b>効いていることを別に示す</b> (隠される側の観察)。
