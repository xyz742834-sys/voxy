# Phase 5c-1b — 非対称パターンの合成 (色経路の向き)

**状態**: **完了。** 実機で赤い帯が画面の上 1/4、緑の四角がその左端に出ることを確認 [確認済 — 目視]。
**⚠ そこに至るまでに 4 つの原因が重なっていた。** §8〜§12。
**自動検査**: `interopCompositeCheck` **15 項目 PASS** (C8 を追加)。JUnit 175 PASS。

## 1. この段で何をしたか

`VoxyRenderSystem` を作らずに、**Vulkan が描いたものを MC の画面に合成する**経路を通した。
描くのは地形ではなく<b>非対称なテストパターン</b>だけである。

```
┌──────────────────────┐
│███████ 赤い帯 (上 1/4)      │  framebuffer 行 [3H/4, H)
│▓▓ 緑の四角                    │  行 [7H/8, H) 列 [0, W/8)
│                              │
│      背景 (濃い青)             │
└──────────────────────┘
```

**なぜ単色ではないか**: <b>単色フルスクリーンは上下反転に無反応</b>である。
5b で踏んだ上下反転は機械的検査 10 項目を通り抜けた
[docs/phase5b-composite.md §6]。だから最初から上下と左右が区別できる模様にする。

| 追加したもの | 場所 |
|---|---|
| `VkInteropProbe` | main。interop 画像の生成・リサイズ・パターン描画・合成 |
| `MixinDefaultChunkRenderer` の分岐 | renderer が無く backend が VULKAN のとき probe を呼ぶ |
| `GlInteropCompositor(boolean writeDepth)` | **深度を書かない正当なモード** (§4) |
| `interopCompositeCheck` の C8 | 行の保存を自動で見張る (§3) |

パターンは `vkCmdClearAttachments` + `VkClearRect` だけで置いている。
<b>シェーダもパイプラインも要らない</b>ので、この段で増える未知が最小になる。

## 2. ⚠ 何が言えて、何が言えないか — 規約 4 の適用

**パターンの生成 (Vulkan の framebuffer 座標) と、機械的な検証 (読み戻した配列の行番号) は
同じ規約を参照している。** 規約が反転していれば<b>両方が反転して再び一致する</b>
[docs/phase4-stage1-completion.md §5.2 の規約 4 / 11 例目]。

| | 言えるか |
|---|---|
| **行の保存** — Vulkan が書いた行 N が GL 側の行 N に届く | **言える** (C8、機械的) |
| **行 N が画面の上か下か** | **言えない** — 物理的な事実なので目視が要る |

### 独立した基準をどこに取るか — **MC のスクリーンショット**

「画面の物理的な上下」を Voxy の規約に依存せず言うには、
<b>Voxy と無関係に正しいことが分かっているもの</b>を基準にする必要がある。

**MC のスクリーンショット機能 (F2) がそれである。**
通常のスクショが正しい向きで保存されることは Voxy とは無関係に成立しており、
その出力の 0 行目は<b>画面の物理的な上端</b>である。

> したがって手動確認は「画面を見る」だけでなく、
> **F2 で撮った PNG の上端に赤い帯があること**まで見る。
> PNG なら後から見返せるし、行番号で機械的にも確認できる。

**MC の UI (ホットバーは下、デバッグ表示 F3 は上) も補助的な基準になる。**
赤い帯が F3 のテキストと同じ側にあれば上、ホットバーと同じ側なら下である。

## 3. 自動検査 C8 — 行の保存

`interopCompositeCheck` に追加。**MC 上で出すのと同じパターン**を使う
(`VkInteropProbe.recordTestPattern` を共用) — 目視と機械的検査が別の模様を見ては意味がない。

| 検査 | 内容 |
|---|---|
| C8 帯が Vulkan の書いた行に来る | 帯の中が帯の色、帯の外が背景色 |
| C8 四角が列の範囲を保つ | 四角の行の左側が四角の色、同じ行の右側が帯の色 |
| **C8 反転した合成では落ちる** | `Defect.FLIPPED` で<b>検出できること</b> (感度の対照) |

3 本目が無いと「行の保存」を主張できない —
反転を検出できない検査は、保存されているかどうかを区別していない。

## 4. 深度を書かない合成は<b>欠陥ではなく設定</b>にした

5c-1b は色だけを見る段なので、深度はまだ運んでいない。
このとき `gl_FragDepth` を書くと、合成は `GL_ALWAYS` なので
<b>MC の深度バッファを一様に潰す</b>。

`Defect.NO_DEPTH` を廃止し、`GlInteropCompositor(boolean writeDepth)` にした。
同じスイッチが

- 5c-1b の<b>正当な用途</b> (深度をまだ運んでいない)
- C4 の<b>対照</b> (深度が壊れても色検査は通ることの実演)

の両方に使える。

> ⚠ 深度テストを切るだけでは足りず、**`glDepthMask(false)` も要る**。
> `GL_ALWAYS` のまま書き込みを許すと `gl_FragDepth` を書かなくても
> <b>ラスタライザ由来の深度</b>が入る。

## 5. ⚠ GL の状態を戻すこと

合成はプログラム・VAO・テクスチャ束縛・深度状態を変える。
**Blaze3D は状態をキャッシュしている**ので、素の GL 呼び出しで変えると
MC 側のキャッシュと実際の状態がずれ、<b>この後の描画が静かに壊れる</b>。

`VkInteropProbe.restoreGlState()` で戻している。
既存の GL 経路も同じことをしている
[確認済 — `VoxyRenderSystem` の「Reset state manager stuffs」ブロック]。
こちらは<b>合成が触るものだけ</b>の最小版。

## 8. ⚠ 初回は画面に何も出なかった — 切り分けの記録

MC の画面に赤い帯も緑の四角も出ない。地形・空・UI は正常 (GL 状態の復帰は効いていた)。
初期化とリサイズのログは出ていたので「フックが呼ばれていない」ではなかった。

### 8.1 最初にやったのは「Vulkan が書けているか」の切り分け

経路の前半 (Vulkan) と後半 (GL) のどちらが悪いかで、見る場所がまったく変わる。
**合成の直前に IOSurface を読み戻した** [確認済 — 実機ログ]:

```
colourWritten=band(BGRA)=[13,13,217,255] background(BGRA)=[64,13,13,255]
```

- 帯: B=13 G=13 **R=217** → <b>赤</b> ✓
- 背景: **B=64** G=13 R=13 → <b>濃い青</b> ✓ (`BACKGROUND` = 0.05,0.05,0.25)

**Vulkan は正しい行に正しい色を書けていた。前半は無実。**
これで原因は後半 (GL 側の合成) に絞られた。

> **この 1 行の診断が調査の 9 割を決めた。**
> 前半が無実と分かった時点で、投影・逆Z・クリア・IOSurface の共有は全て容疑から外れる。

### 8.2 見つかった原因は 3 つ重なっていた

同じ診断ログが残り 3 つを一度に出した:

```
frame 0: drawFbo=0 viewport=[0,0,16,16] blend=false scissor=false
frame 1: drawFbo=0 viewport=[0,0,1708,960] blend=true scissor=true
```

| # | 原因 | なぜ見えないか |
|---|---|---|
| 1 | **`drawFbo=0`** — 既定フレームバッファが束縛されている | MC はワールドを<b>自前のメインターゲット</b>に描き、後から画面へ転送する。既定 FB に描いたものは<b>その転送で上書きされて消える</b> |
| 2 | **`viewport=[0,0,16,16]`** のフレームがある | 仮に FBO が正しくても<b>16x16 の隅にしか描かれない</b> |
| 3 | **`blend=true` / `scissor=true`** | 素通しのつもりの合成が混ざる / 切り取られる |

**3 つとも「MC の状態をそのまま使った」ことが原因である。**
注入箇所の GL 状態は<b>Sodium と Blaze3D の都合で決まっている</b>ので、
合成に必要な状態は<b>自分で作って自分で戻す</b>しかない。

### 8.3 修正 — 既存の GL 経路と同じ形にした

既存の GL 経路は<b>同じ問題を同じ方法で</b>解いていた
[確認済 — `AbstractRenderPipeline.runPipeline` が自前 FBO に MC の色/深度テクスチャを
付け替えてから合成している]。5c-1b もこれに倣う:

1. `GlScratchFramebuffer` に **MC のカラーテクスチャを付け替えて束縛**
2. **ビューポートを明示的に設定**
3. **ブレンドとシザーを一時的に切る**
4. 合成
5. **全て元に戻す** (FBO・ビューポート・ブレンド・シザー・プログラム・VAO・テクスチャ)

### 8.4 ⚠ ここでも GL 4.5 DSA の地雷を踏みかけた

`GlFramebuffer` (Voxy 既存) は
`glCreateFramebuffers` / `glNamedFramebufferTexture` = **GL 4.5 DSA** で書かれている。
そのまま使えば<b>JVM ごと abort</b> していた。

**5c-1a §7 の監査で「GL のクラスを import した時点で疑う」と決めていたので踏まずに済んだ。**
`GlScratchFramebuffer` は `glGenFramebuffers` (3.0) と
`glFramebufferTexture2D` (3.0) だけで書いてある。

> 監査で挙げた 3 つ (`FullscreenBlit` / `UploadStream` / `DownloadStream`) に加えて、
> **`GlFramebuffer` も同じ地雷だった**。一覧に追記する。

### 8.5 学び

> **「フックは呼ばれている」と「結果が画面に届いている」の間には、まだ 3 段ある。**
> 描画先 (FBO)・描画範囲 (viewport)・描画状態 (blend/scissor)。
> どれか 1 つでも他人の都合のままだと、絵は出ない。

診断ログに<b>1 行で 4 つの事実</b>(FBO・viewport・blend/scissor・IOSurface の中身) を
出したのが効いた。1 つずつ試していたら 4 往復かかっていた。

## 9. ⚠⚠ 二度目の不具合 — MC の深度バッファを壊していた (失敗例 12)

§8 の修正後、合成は画面に届いた。しかし
<b>mob が地形を貫通して見える</b>状態になっていた。
最初の報告で「地形・空・UI は正常」としたのは<b>誤り</b>で、
スクリーンショットを見ると地中・洞窟の個体が地表越しに散らばって見えていた。

### 9.1 原因 — <b>復帰処理が、効いてほしい場面で no-op になる</b>

`GlStateManager$BooleanState.setEnabled` は [確認済 — バイトコード]:

```java
if (v == this.enabled) return;      // キャッシュが一致していたら GL を呼ばない
this.enabled = v; glEnable/glDisable(...);
```

したがって:

| 手順 | 実際の GL | Blaze3D のキャッシュ |
|---|---|---|
| 合成の前 (地形を描いた直後) | 深度テスト **有効** | **有効** |
| 合成が<b>素の</b> `glDisable(GL_DEPTH_TEST)` | **無効** | 有効 (知らない) |
| 復帰が `GlStateManager._enableDepthTest()` | **無効のまま** ← <b>glEnable が発行されない</b> | 有効 |
| MC がエンティティを描く | **深度テスト無効** | 有効のつもり |

→ **mob が地形を貫通する。**

> **素の GL で変えたものを、キャッシュ API で戻してはならない。**
> キャッシュは「既にその値」と判断して<b>何もしない</b>。
> 復帰処理が存在するのに効かないので、コードを読んでも間違いに見えない。

### 9.2 修正 — キャッシュに触らず、素の GL で元の値に戻す

`GlInteropCompositor.composite()` が<b>自分で控えて自分で戻す</b>形にした
(プログラム / VAO / active texture / rect テクスチャ 2 本 / 深度テスト・書き込み・比較 /
カラーマスク / ブレンド / シザー)。

**ホストのキャッシュには一切触らない。** そうすればキャッシュは最初から正しいままで、
食い違いが生じない。合成が Minecraft に依存しなくなる副次的な利点もある
(オフスクリーンのベンチと同じコードのままでよい)。

FBO だけは `GlStateManager` 経由で切り替えて戻す —
<b>行きも帰りも同じ API を通る</b>ので、キャッシュは整合したままになる。

### 9.3 ⚠ C9 を書いたが、最初は<b>変異を検出できなかった</b>

再発防止に C9 (合成が GL 状態を戻すこと) を追加し、
対照として<b>復帰処理を外した変異</b>を入れて確かめた:

```
C9 the composite restores every GL state it touches   PASS   ← ★通ってしまった
```

**理由**: C9 が<b>深度を書く版</b>の合成だけを見ていた。
書く版は深度テストを<b>有効</b>にするので、事前状態 (有効) と同じになり差が出ない。
**MC が使うのは書かない版** (深度テストを切る) で、そちらを見ていなかった。

修正後、変異は正しく落ちる:

```
C9 [depth]       ... restores every GL state it touches   PASS
C9 [colour-only] ... restores every GL state it touches   FAIL
    (before=[...,1,0,516,1,1] after=[...,0,0,516,1,1])     ← 深度テスト 1 -> 0
```

> **これも規約 4 の一族である** — 「変種が複数ある実装を、1 つの変種でしか対照していない」。
> <b>本番が通る経路を対照が通っていなければ、対照は本番を守っていない。</b>

### 9.4 運用に足す規則

> **【規約 5】対照は<b>本番が通る経路</b>を通すこと。**
> 実装に変種 (フラグ・モード・分岐) があるなら、
> <b>本番が使う変種</b>で対照を回す。全変種で回すのが確実。

## 10. 行範囲の表示について — 変換は残っていない [確認済]

`red band at framebuffer rows [720,960)` (1708x960) は<b>意図どおり</b>である。

- **GL 規約では 0 行目が絵の下端**なので、`[720,960)` は<b>画面の上 1/4</b>
- Vulkan/画面規約 (0 行目 = 上端) で読むと下 1/4 に見えるが、その規約は採っていない
- `960 * 3/4 = 720` で計算どおり。**Y の変換はどこにも入っていない** (判断 1 の案 B)

紛らわしいのでログに注記を足した:

```
[rows are framebuffer rows; row 0 is the BOTTOM of the picture under the GL convention,
 so this range is the TOP quarter of the screen]
```

**帯が画面の上に出れば規約どおり、下に出れば Y が反転している。**
この判定が §6 の手動確認 2 と 4 である。

## 11. ⚠⚠⚠ 三度目 — 5c-1a で入れた退行が実機クラッシュとして出た (失敗例 13)

黒画面の調査中に MC を再起動したところ、**描画フレームで即クラッシュ**した:

```
java.lang.ClassCastException:
  com.mojang.blaze3d.vulkan.VulkanGpuTextureView cannot be cast to
  com.mojang.blaze3d.opengl.GlTextureView
    at DefaultChunkRenderer.doRender          ← Voxy の mixin
    at ... LevelRenderer.render
```

原因は **MC 自身が Vulkan バックエンドで動いていた**こと
(`run/options.txt` が `preferredGraphicsBackend:"vulkan"` に戻っていた) である。

### 11.1 これは 5c-1a で入れた退行だった

| | MC が Vulkan バックエンドのとき |
|---|---|
| **5c-1a より前** | GL コンテキストが無い → `Capabilities` が no-GL 経路 → `compute=false` → `systemSupported=false` → <b>Voxy は自己無効化 (安全)</b> |
| **5c-1a 以降** | `glSupported=false` → `vulkanIsUsable()=true` → `BACKEND=VULKAN` → <b>Voxy が有効化</b> → Sodium フックが `GlTextureView` にキャスト → <b>クラッシュ</b> |

**「GL が足りない → Vulkan を使う」だけを見て、
「GL がそもそも無い」場合を分けていなかった。**

> ⚠ **Voxy の Vulkan 経路も GL を必要とする。**
> 描いた結果を IOSurface 経由で GL のフレームバッファに合成し、
> MC の色/深度テクスチャも Sodium 経由で<b>GL のテクスチャ ID</b> として受け取るためである。
> 「Vulkan 経路 = GL 不要」ではない。

`docs/phase5c-mc-vulkan-survey.md` §4.2b に
「MC-Vulkan と Voxy の同居は成立しない」と<b>書いてあった</b>のに、
バックエンド選択にその条件を入れ忘れていた。**調査結果が実装に反映されていなかった。**

### 11.2 修正

```java
boolean mcIsOnOpenGl = Capabilities.INSTANCE.glAvailable;   // GL コンテキストの有無 = MC が GL か
if (glSupported)                          BACKEND = Backend.OPENGL;
else if (mcIsOnOpenGl && vulkanIsUsable()) BACKEND = Backend.VULKAN;
else                                       BACKEND = null;   // 自己無効化
```

`CapabilitiesWithoutGlTest.withoutGlTheVulkanBackendIsAlsoRefused` が
判定に使う入力を常設で固定する。

### 11.3 運用に足す規則

> **【規約 6】調査で分かった制約は、その場で<b>実装の条件</b>に落とすこと。**
> doc に書いただけでは、後の変更で<b>条件を通り越してしまう</b>。
> 「§4.2b に書いた」ことと「コードがそれを守る」ことは別である。

### 11.4 黒画面との関係 [未検証]

黒画面が出た実行 (rc5c1b4) は **OpenGL バックエンド**だった [確認済 — ログ]。
クラッシュした実行 (rc5c1b5) は Vulkan バックエンド。
つまり<b>両者は別の問題</b>である。**黒画面の原因はまだ特定できていない。**

§8 で入れた切り分けスイッチ (`-Pvoxy5c1b=off|state|full`) で
1 変数ずつ確かめる必要がある。

## 12. 最後の原因 — <b>サンプラオブジェクトの残留</b> (失敗例 14)

`solid` モード (テクスチャを読まずマゼンタ一色) で切り分けたところ:

- **画面がマゼンタになった** → <b>描画は届いている</b>。FBO・ビューポート・描画状態は正しい
- **MOB・雲・水はそのまま表示された** → <b>合成後の描画も壊していない</b> (状態復帰は効いている)

残るのは <b>`texelFetch` が黒を返している</b>ことだけだった。

### 12.1 原因

**GL ではテクスチャユニットにサンプラオブジェクトが bind されていると、
テクスチャ側のパラメータより<b>サンプラ側が優先</b>される。**
MC / Sodium はサンプラを多用しており、残ったままだと
`GL_TEXTURE_RECTANGLE` に非互換な設定 (mipmap フィルタ等) が適用され、
<b>incomplete 扱いで黒が返る</b>。

**既存の Voxy GL 経路は同じ対処をしていた** —
`VoxyRenderSystem` が `glBindSampler(i, 0)` を明示的に呼んでいる [確認済]。
<b>その理由を読み解かずに、合成パスにだけ入れ忘れていた。</b>

### 12.2 なぜオフスクリーンのベンチで再現しなかったか

**ベンチにはサンプラオブジェクトが存在しない。** 誰も bind しないからである。

> ⚠ **対照環境に存在しない要素は、対照では検出できない。**
> `interopCompositeCheck` が 17 項目 PASS でも、
> <b>ホストが残す状態</b>までは再現していない。

### 12.3 運用に足す規則

> **【規約 7】ホストの中で動かすものは、ホストが残す状態を洗い出すこと。**
> オフスクリーンの検査で通ることは、ホスト内で動くことを保証しない。
> <b>既存コードが「一見不要な後始末」をしていたら、その理由を先に読む。</b>

`VoxyRenderSystem` の reset ブロックは<b>そういう後始末の一覧</b>だった。
5c-1b で必要だったものは全てそこに書いてあった (FBO の付け替え・サンプラのリセット)。

## 13. 切り分けの経過 — モードスイッチが効いた

| 手 | モード | 結果 | 分かったこと |
|---|---|---|---|
| 1 | `off` | 正常 | 原因は<b>合成パスの中</b>に確定。配線は無実 |
| 2 | `state` | 正常 | FBO 束縛・ビューポートの控え/復帰は無実 |
| 3 | `solid` | <b>マゼンタ</b> | 描画は届いている。原因は<b>テクスチャの読み</b> |
| 4 | `full` | <b>正常に表示</b> | サンプラのリセットで解決 |

**4 手で終わった。** 各手が 1 変数だけを動かし、結果が次の手を一意に決めた。

> スイッチ (`-Pvoxy5c1b=off|state|solid|full`) は<b>再ビルド不要</b>にしてある。
> 5c-1c 以降で同種の切り分けが要るときも同じ手が使える。
