# Phase 5a — GL → Vulkan 方向の同期コスト 実測

**測定日**: 2026-08-17
**環境**: Apple M4 Pro / macOS / JDK 25 / LWJGL 3.4.1
**GL**: `Apple M4 Pro / 4.1 Metal - 90.5`
**Vulkan**: MoltenVK (LWJGL 同梱 = api 1.4.334 / brew ローダー = 1.4.357)
**測定コード**: [`src/test/java/me/cortex/voxy/vk/bench/GlToVkSyncBench.java`](../src/test/java/me/cortex/voxy/vk/bench/GlToVkSyncBench.java)
**対象**: `phase5-proposal.md` §2.2「GL → Vulkan の同期コストは [未検証]」

```bash
./gradlew glToVkSyncBench
./gradlew glToVkSyncBench --args="--loads 1,2,4,8,16 --iters 60"
```

---

## 1. 結論

**§2.2 の懸念は否定された。GL → Vulkan 方向の同期は 0.2〜0.3 ms で済む。**

| 問い | 答え |
|---|---|
| `glFinish` が必要なら 0.315 ms では済まないのでは | **済む。** 同期を入れて増えるのは **0.3 ms 未満**、実行間のばらつきと同程度 |
| なぜ安いのか | **同期プリミティブを呼ばなくても待ちは発生している。** 呼ぶ場所が変わるだけ |
| `glFlush` で足りるか | コストは 0.003 ms。**足りるという証明は無い** (§4) |
| 同期は本当に要るのか | **不明。** 陳腐な読みを 1 度も構成できなかった [未検証] |

**設計 (§2.2 の 5 段構成) は変更不要。**

ただし数字が示したより重い事実がある — §5。

## 2. 模したフレーム

```
[GL] 地形パス × load       MC の地形描画に相当。D32F の深度に uDepth を書く
[GL] 深度コピーパス         d32 → interop の R32F IOSurface (initDepthStencil の役割 1)
[SYNC]                     ← 測定対象。NONE / FLUSH / FENCE / FINISH
[VK] interop 深度を読む     vkCmdCopyImageToBuffer で 3 箇所 × 16x16 をホストへ
[VK] vkQueueWaitIdle
[CPU] 値の検証              GL が書いた値とビット一致するか
```

1920x1080。Vulkan → GL の合成は**含めない** — 片方向を分離するのが目的で、
逆方向は Phase 0 §8 が既に測っている。

`load` は地形パスの枚数。1 枚が約 0.87 ms (フラグメント内ループ 64 回)。
実際の MC の地形パスが何 ms かは [未検証] なので、
**コストは `gl_gpu_ms` の関数として読むこと。**

### 3.1 同期の正味コスト

| load | gl_gpu_ms | frame(NONE) | frame(FLUSH) | **FINISH − NONE** |
|---:|---:|---:|---:|---:|
| 1 | 0.855 | 0.953 | 0.947 | **+0.142** |
| 2 | 1.619 | 1.745 | 1.740 | **+0.107** |
| 4 | 3.149 | 3.341 | 3.335 | **+0.047** |
| 8 | 6.212 | 6.536 | 6.564 | **−0.051** |
| 16 | 12.343 | 13.665 | 13.621 | **−0.968** |

**GL 負荷が 16 倍になっても正味コストは増えない。**
load 8 以降で負になるのは、`glFinish` を挟むと GL 側が早く畳まれるため
(`gl_gpu` 自体が 13.5 → 12.3 に下がっている)。

> ⚠ **実行間のばらつきが正味コストと同程度ある。**
> 同条件の別実行では +0.20 / +0.29 / +0.25 / +0.20 / −0.46 だった。
> したがって主張できるのは<b>「0.3 ms 未満」</b>までで、
> 「0.05 ms」のような細かい値には意味が無い。

### 3.2 読み取り — 待ちは同期を呼ばなくても起きている

表の `vk_ms` 列が鍵である。

```
NONE   load=16:  sync_ms =  0.000   vk_ms = 13.550   ← vkQueueWaitIdle が 13.5ms 待っている
FINISH load=16:  sync_ms = 12.363   vk_ms =  0.227   ← glFinish が待ち、Vulkan は素で速い
```

**`vk_ms` と `sync_ms` の和はどちらの経路でもほぼ同じ。**
同期プリミティブは<b>待ちを増やしているのではなく、待つ場所を CPU 側に移しているだけ</b>である。

`FENCE`/`FINISH` の `vk_ms` が 0.15〜0.29 ms なのは、
Phase 0 が測った `vkQueueWaitIdle` 単体の 0.315 ms と同じ桁である。
**別の測定系から Phase 0 の数字が再現された。**

## 4. 対照 — 何が確かめられて何が確かめられていないか

「同期無しでも値が合った」ことは<b>同期が不要である証拠にならない</b>。
検査を空虚に満たす経路を潰すため 4 つの対照を置いた
(運用は `phase4-stage1-completion.md` §5.2 に従う)。

### C1 読み手の生存 — PASS

`glFinish` 付きで 24 回、GL が書いた値と Vulkan が読んだ値がビット一致し、
かつ 24 回とも異なる値だった (`distinct=24/24`)。
**読み戻しが定数や古い値を返しているのではない**ことの確認。
これが落ちたら以下は全て無意味なので、失敗したらベンチはそこで止まる。

> 副産物: これは <b>IOSurface が本当に共有されていることの直接的な証拠</b>でもある。
> Phase 0 は `memReq == allocSize` をゼロコピーの根拠にしたが (§6.2)、
> 値が渡ることのほうが強い証拠である。

### C2 陳腐検出器の感度 — PASS

GL を動かさずに Vulkan の読みだけ 2 回行い、
検査が「2 回目も前の値だった」と報告できることを確認した。
**これができないなら、NONE で不一致が出ないことに意味が無い。**

### C3 失敗の構成可能性 — **できなかった**

`NONE` で GL 負荷 0.19 ms 〜 55 ms、計測対象の反復だけで約 800 回回したが、
**陳腐な読みは 1 度も観測されなかった。**

「GL の作業が大きすぎてドライバが自動 flush してしまい、
結果として競合が起きなかっただけではないか」という疑いに対しては、
`--burn 0`(GL 側 0.19 ms) で 200 回回して確認した。それでも 0 件である。

> ⚠ これは<b>「同期は不要」ではなく「失敗例を構成できなかった」</b>と記録する。
> GL / CGL / IOSurface / Vulkan のどの仕様も、
> 明示同期なしの GL → Vulkan の順序を保証していない。

### C4 GPU の取り合いか、データ依存か — **データ依存**

C3 で失敗が出ない理由は 2 つ考えられた。
切り分けのため、同じ GL 負荷のもとで **interop ではない自前の VkImage** から読んだ。

| load | gl_gpu_ms | vk_ms (interop) | vk_ms (private) |
|---:|---:|---:|---:|
| 1 | 0.857 | 0.871 | 0.148 |
| 2 | 1.645 | 1.665 | 0.179 |
| 4 | 3.236 | 3.254 | 0.170 |
| 8 | 6.431 | 6.459 | 0.190 |
| 16 | 13.531 | 13.550 | 0.314 |

**interop 画像を読むときだけ `gl_gpu_ms` に張り付く。**
自前の画像なら GL が 13.5 ms 走っている最中でも Vulkan は 0.31 ms で戻る。

→ GPU の取り合いではない。**IOSurface に対するデータ依存が、
明示同期なしにシステム側 (Metal / IOSurface) で追跡されている** [確認済 — この実験の範囲で]。

> これでも「同期不要」の証明にはならない。
> <b>観測された挙動であって、保証された挙動ではない。</b>

### 判定

| | 結論 |
|---|---|
| 同期のコスト | **測れた。** 0.2〜0.3 ms |
| 同期の必要性 | **測れていない。** 不要と結論してはいけない |

**推奨: `glFlush` を必ず入れる。** 0.003 ms しかかからず、
「GL のコマンドを他の API から見える状態にする」documented な最小手段である。
`FENCE`/`FINISH` に上げても +0.3 ms 未満なので、
5c で挙動が怪しければ迷わず上げてよい。

## 5. ⚠ 同期より重い事実 — 直列化

数字が示したのは同期プリミティブの安さだけではない。

**Vulkan の LoD 描画は MC の地形描画と重ねられない。** 深度に依存するからである。

```
GL 地形 (a ms) → Vulkan LoD (b ms) → GL 合成 (0.29 ms) → 全部直列
```

C4 は「依存が無ければ Vulkan は GL と並走できる」ことを示している
(private 画像は 0.40 ms で戻る)。つまり<b>並走できる余地は実在するのに、
depth 依存がそれを潰している</b>。

これは同期の設計では解けない。解くとしたら:

- Vulkan の作業のうち<b>深度に依存しない部分</b> (ジオメトリのアップロード、
  traversal の一部) を GL 地形パスと並走させる
- あるいは<b>1 フレーム前の深度</b>を使う (Voxy には temporal 経路が既にある)

**どちらも Phase 5 の範囲外。** ここでは「直列になる」ことを記録するに留める。
フレーム予算の見積りは `GL地形 + Vulkan LoD + 0.29 (合成) + 0.3 未満 (同期)` になる [推測]。

## 6. interop の実装で分かったこと

### 6.1 ⚠ `UNDEFINED` からのレイアウト遷移を毎フレームやってはならない

Phase 0 の `Step8` は毎フレーム `UNDEFINED` → `TRANSFER_DST` に遷移していた。
**Vulkan が書き手だったから成立していた**書き方である。

`oldLayout = VK_IMAGE_LAYOUT_UNDEFINED` は「内容を捨ててよい」という宣言なので、
**GL → Vulkan 方向でこれをやると GL が書いた内容が消える。**

対応: `VkInteropImage.toGeneral()` を用意し、
**初回だけ `UNDEFINED` → `GENERAL`、以降は `GENERAL` 据え置き**にした。
ベンチは GL が書く前に一度だけ遷移させている (`primeLayout`)。

### 6.2 `memReq` と IOSurface の `allocSize` は一致しない

```
1920x1080 R32F:
  vk memReq            = 8,486,912
  IOSurface allocSize  =  8,306,688
  IOSurface bytesPerRow=      7,680   (= 1920 * 4、行パディング無し)
```

Phase 0 §8.3 の 7e は 512x512 でこれが一致したことを
「コピーが発生していない」根拠にした。**一般には一致しない。**
`memReq` は Vulkan 側のアラインメント要求を含むので、大きくても異常ではない [推測]。

ゼロコピーの根拠としては **C1 (GL が書いた値を Vulkan がビット一致で読む)** のほうが強い。
この doc 以降はそちらを使う。

### 6.3 ⚠ バリデーションレイヤは IOSurface backed の画像を理解しない

interop 画像に触るたびに以下が出る (`-PvkValidation=true` で確認):

```
VUID-VkImageViewCreateInfo-image-01020      vkCreateImageView():  used with no memory bound
VUID-VkImageMemoryBarrier-image-01932       vkCmdPipelineBarrier(): used with no memory bound
VUID-vkCmdCopyImageToBuffer-srcImage-07966  vkCmdCopyImageToBuffer(): used with no memory bound
```

`VkImportMetalIOSurfaceInfoEXT` で作った画像は `vkBindImageMemory` を呼ばない
(MoltenVK が内部で IOSurface を紐づける)。しかしレイヤは自前でバインドを追跡しているため、
**「メモリがバインドされていない」と言い続ける。**

Phase 0 §8.5 の「明示的に有効化しなくても MoltenVK は受け付ける」は正しいが、
<b>レイヤ経由では正しくない</b>という追加事実である。

> **これは Phase 5 の実作業に効く。** interop 画像が増えるほどノイズが増え、
> <b>本物の指摘が埋もれる</b>。同期バリデーションが機能しないこの環境で、
> 一般バリデーションは唯一残っている防御線である。
> 対処は §8 の質問 1。

### 6.4 `VK_EXT_metal_objects` をデバイス拡張として有効化した

`VkContext` に条件付きで足した (`hasMetalObjects`)。
Phase 0 は有効化せずに動かしていたが、ローダー + レイヤ経由では
有効化していない拡張の構造体を渡すと指摘されるため。実機では `true`。

## 7. 検証の自動/手動の境界 — 新しい区分が 1 つ増えた

Phase 5 の判断 5 (「MC 起動が要る検証は自動化を諦める」) に対し、
**その中間**が要ることが分かった。GL コンテキストは要るが MC は要らない、という層である。

| 層 | 走らせ方 | 件数 | いま |
|---|---|---:|---|
| 素の JVM (JUnit) | `./gradlew test` | 155 PASS / 1 SKIP | 維持 |
| **GL + Vulkan (JavaExec)** | **`./gradlew glToVkSyncBench`** | **1** | **今回追加** |
| MC 起動 | `./gradlew runClient` | — | 手動 + スクリーンショット (5c 以降) |

> 5b でこの層に `interopCompositeCheck` が加わり、JUnit は 166 件になった。
> 最新の表は `phase5b-composite.md` §7。

**なぜ JUnit に入れられないか**: GLFW は macOS で `glfwInit` を
プロセスの main スレッドから呼ぶことを要求する (`-XstartOnFirstThread`)。
Gradle の test worker はテストを "Test worker" スレッドで実行するため、この条件を満たせない。

したがって **GL が絡む検証は JUnit の 155 件には入らない。**
`build.gradle` の `glToVkSyncBench` タスクが `-XstartOnFirstThread` を付けて起動する。

> 5b (合成パス) もこの層に入る。**5b は「MC 無しで自動検証できる」**ので、
> 判断 5 の「自動化を諦める」対象は 5c 以降だけである。

## 8. 指示を仰ぎたいこと — **回答済み**

> **質問 1 → 案 A (抑制する)。** ただし範囲を最小に: VUID 3 つを明示列挙し、
> interop ハンドルに限定する。実装と検査は `phase5b-composite.md` §3。
> **質問 2 → `FENCE`。** コスト差 0.3 ms 未満なら正しさが確認できているほうを選ぶ。
> 「壊れなかった」と「正しい」を C3 で区別できていない以上、
> `glFlush` の「壊れれば見える」は根拠にならない。最適化は Phase 6 で実データを測ってから。

### 質問 1: バリデーションのノイズ (§6.3) をどう扱うか

interop 画像 1 枚につき 3 種の VUID が出続ける。5b/5c で色・深度の 2 枚に増え、
リサイズのたびに再作成されるので、**本物の指摘が埋もれる**。

- **案 A**: `VkContext` のメッセンジャで、この 3 つの VUID を
  <b>interop 画像のハンドルに限って</b>抑制する。抑制した件数はログに出す ← 推す
- **案 B**: 何もしない。ノイズごと読む
- **案 C**: ダミーの `VkDeviceMemory` を確保して `vkBindImageMemory` を呼ぶ
  (レイヤは黙るが、MoltenVK が IOSurface とダミーのどちらを使うか不明。**危険**)

A を推すが、**「バリデーションを黙らせる」方向の変更**であり、
この環境で同期バリデーションが既に機能していない以上、
一般バリデーションを削るのは慎重に決めたい。ハンドル限定にすれば
「interop 以外で同じ VUID が出たら見える」ことは保てる。

### 質問 2: `glFlush` で進めるか、`FENCE` で進めるか

コスト差は 0.3 ms 未満。正しさの差は**測れていない** (§4 の C3)。

- **案 A**: `glFlush`。安い。documented な最小手段 ← 5b までは推す
- **案 B**: `glFenceSync` + `glClientWaitSync`。0.2〜0.3 ms 払って確実側に倒す

5b はオフスクリーン FBO を読み戻して比較するので、
**A で壊れれば 5b で見える**という考え方もできる。どちらで進めるか。

## 9. 測定の限界

- **MC の実フレームとは GL キューの深さが違う。**
  このベンチは各反復の最後に GL タイマークエリを読むため、
  次の反復は GL アイドルから始まる。実際の MC はドライバが 1〜2 フレーム分
  先行している可能性がある [未検証]。その場合、同期点で溜まっている GL 作業は
  ここで測ったより多い。
- **`load` と MC の地形パスの対応が取れていない。**
  実機の MC で地形パスが何 ms かは [未検証]。`gl_gpu_ms` の関数として読むこと。
- **Vulkan 側の作業が軽すぎる。** 3 x 16x16 のコピーのみ。
  実際の LoD 描画を入れたときに同じ結論になるかは [未検証]。
  ただし §3.2 の「待つ場所が変わるだけ」という構造は Vulkan の作業量に依存しない [推測]。
- **GL 版と同じ絵かは、ここでも検証していない。** Phase 5 全体の限界 (提案書 §5.6)。
