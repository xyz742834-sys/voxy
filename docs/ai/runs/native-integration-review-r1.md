## 2. Safety for normal play

**CONFIRMED: feature requests are unchanged with the feature flag unset.** `MixinVulkanBackend.java:34–41` always injects its helper, but `McNativeDeviceFeatures.java:77–78` returns the identical input set before inspecting it when `voxy.native.features` is false. The fresh `itAddsNothingWhenTheFlagIsUnset` checks object identity. The mixin does set bookkeeping (`attempted`) and loads helper classes; it does not alter Minecraft's feature set. `require=0` allows a missing injection to go unnoticed; it is not evidence that features were enabled.

**CONFIRMED: marker recording and device adoption have their own flag guards and reject GL backends.** `McNativeMarkerDraw.java:176–190` exits before rendering without `voxy.native.marker`; with it set, a GL backend returns before creating a pipeline/pass. `McNativeVkContext.java:92–117` checks `voxy.native.adopt` and requires a `VulkanDevice` before installing a context. A GL player's normal draw/adoption route is not replaced by these paths. Normal native terrain remains disabled by `VoxyClient.java:96–112`.

**B2 — blocking, high: “every native path is inert without a flag” is REFUTED.** `VoxyClient.java:165–172` registers the probe and release callbacks unconditionally. `McNativeVulkanProbe.probeOnce` has no native flag guard: lines 272–299 probe/log and, on a Vulkan backend, enumerate/query physical-device features and invoke the other probes. Their GPU experiments have guards, but the feature audit itself does not. At client stop, `McNativeVkContext.java:263–280` obtains Minecraft's Vulkan device and calls `vkDeviceWaitIdle` *before* checking `VkContext.isAdopted()`. This occurs with all three flags unset and no marker/context at all. The native wait has no timeout and its VkResult is ignored. An ordinary Minecraft-Vulkan player therefore gets additional driver work and can stall at exit for a diagnostic they never enabled.

**REFUTED: an unconditional promise that the probe cannot throw or stall.** The registered `probeOnce` catches ordinary Java failures around probing and audit (lines 271–303), so most failures are logged rather than propagated. Public `probe(device,target)` does not catch `getDeclaredFields()` failures in `backendOf` (`McNativeVulkanProbe.java:169–185`); a reflective SecurityException can escape that public call, although the tick wrapper catches it. The probe runs synchronously on the client/render thread: feature enumeration/query and optional filesystem writes are not time-bounded. With flags enabled, both minimal compute proofs wait up to five seconds, and the real-shader tracker uses `Long.MAX_VALUE` waits (`VkFrameTracker.java:120,165`). `McNativeRealShaderProbe.java:103–109` says shutdown avoids device-idle waiting, but `VkFrameTracker.shutdown → destroy → waitIdle` actually calls `vkDeviceWaitIdle` (`VkFrameTracker.java:103–106,211–221`). Java catches cannot provide a timeout or catch a driver stall/native crash.

There is no reproduced unflagged GL GPU mutation here. For GL, Vulkan-specific audit/wait are skipped by backend identity, although the unconditional tick probe still performs reflection/logging. Ordinary native-Vulkan safety and complete inertness are not accepted.

## 3. Risky implementation parts

### 3a. Type-based reflection

**CONFIRMED for this artifact's unique fields; REFUTED as an ambiguity-safe mechanism.** The inspected Minecraft jar has exactly one `GpuDeviceBackend` field in `GpuDevice`, one `RenderPassBackend` in `RenderPass`, one `VkCommandBuffer` in `VulkanRenderPass`, and one of each desired type in `VulkanFeature`. This candidate does not have an observed wrong-field selection.

`McNativeVulkan.java:140–146` and `McNativeDeviceFeatures.java:200–210` nevertheless choose the first assignable field without rejecting duplicates or static fields. Reflection declaration order is not an identity contract. A new same-typed backup/stale/static field can be silently selected; a wrong Vulkan backend/command buffer can reach native writes. A null/inaccessible/mismatched value usually creates notes or prevents work, but a readable wrong value with the right type does not. `commandBufferOf` retains cached fields without invalidating them after a backend-class change (`McNativeVulkan.java:114–135`). This is a non-blocking compatibility finding for the exact artifact, not a claim that the present fields are ambiguous.

### 3b. Read-back offset calibration

**CONFIRMED: the old 16-byte error cannot pass the present check on this candidate.** `javap -c -private com.mojang.blaze3d.vulkan.init.VulkanFeature` shows the constructor adds `VkPhysicalDeviceFeatures2.FEATURES` for the base-feature struct, then `set` writes one int at the stored offset. `McNativeDeviceFeatures.java:125–142` tries both candidates on zeroed scratch storage. The doubled-header candidate writes another field and fails the independently addressed intended-field check (`bitAt`, lines 152–153); only the intended nonzero field with exactly one nonzero base-feature word is accepted. Fresh `eachAddedFeatureSetsOnlyTheFieldItNames` additionally checks the named LWJGL accessors and `set`'s return value (`McNativeDeviceFeaturesTest.java:49–83`). It would reject the historical depthBounds/shaderStorageImageMultisample/sparseBinding mapping.

This establishes exact current offset semantics, not hardware support, an arbitrary future `set` implementation, or memory safety of unbounded candidate writes against changed internals. The logger's “supported by this device” (`McNativeDeviceFeatures.java:103–104`) is unsupported by any query in `augment`.

### 3c. Core versus KHR dispatch

**CONFIRMED: production callers for the three affected commands are routed through capability dispatch.** `VkCmd.java:34–57` checks each command buffer device's relevant core pointer and otherwise calls its KHR equivalent. The search

```sh
rg -n 'vkCmdPipelineBarrier2\(|vkCmdBeginRendering\(|vkCmdEndRendering\(' src/main/java
```

finds direct core calls only inside the three guarded branches in `VkCmd`. Searches for other VK13 command calls found constants/imports, not an additional unguarded production core-1.3 call. A missing KHR pointer would still throw rather than supply an unsupported fallback; on the documented Minecraft extension set that is the correct required route. Fresh tests exercise the core device, not Minecraft's KHR branch. No direct-call blocker found; native KHR runtime evidence remains unavailable.

### 3d. Adopted destruction and failure paths

**CONFIRMED, conditional happy-path order:** `McNativeVkContext.java:263–305` waits for Minecraft's device, destroys the marker, empties GPU caches, shuts down the tracker, then shuts down the context. `VkContext.java:686–700` destroys its own pool and memory-property storage while skipping device/instance destruction in adopted mode. Assuming the same active device and successful retirement, the ordering respects borrowed ownership and drains tracker deferred frees before pool destruction.

**B5 — blocking, high: safe retirement on failure is REFUTED.** The compute proof submits at `McNativeComputeProbe.java:204–208`; if its five-second fence wait returns VK_TIMEOUT, `check` throws, then `finally` immediately destroys the fence, command pool, pipeline, descriptors, buffer and memory (lines 218–230), although submitted commands may still be pending. The adopted-context proof has the same pattern (`McNativeVkContext.java:223–245`). `VkBuffer.free` immediately destroys/frees storage (`VkBuffer.java:92–97`). A diagnostic timeout must not corrupt Minecraft's borrowed device. No timeout was induced on the GPU during review.

Shutdown also proceeds after failing to find/wait on the device or after exceptions, and ignores the wait's VkResult (`McNativeVkContext.java:267–280,292–303`). Marker retirement falls back to immediate destruction when `queueForDestroy` throws (`McNativeMarkerDraw.java:435–442`), without retirement proof. These are source-confirmed unsafe failure paths; a clean successful shutdown cannot certify them.

**Non-blocking adoption identity/metadata findings:** `McNativeVkContext.physicalOf`, lines 316–329, adopts the first enumerated physical device, not necessarily the parent of Minecraft's actual logical device. On multiple GPUs, memory types/limits/queue properties can consequently come from the wrong device; the compute probe has the same first-device assumption at lines 256–266. No multi-GPU run is available. `VkContext.java:452–453` sets `hasMetalObjects` from physically supported extensions rather than logical-device enabled extensions, contrary to the adjacent claim that the MC path is automatically disabled. The reviewed native probes do not consume that interop capability, so this is not an observed current GL dependency, but the adopted metadata is wrong for the survey's described device.

## 4. Gate correctness

**B3 — blocking, high: REFUTED that native-stage PASS establishes feature/adoption/real-shader success.** `scripts/verify.py:445–469` enables all probes but only gates environment observations, marker pixels, textual diagnostics, validation-loader evidence and selected ERROR logs. It never reads `native-device-features.json`, `native-compute-probe.json`, `native-adopted-context.json` or `native-real-shader.json`. Probe failures are generally caught and logged at INFO/WARN, not the ERROR level this stage rejects. A failed/skipped adoption or CPU/GPU mismatch with otherwise clean environment/marker can therefore pass. Marker `device` is never compared with checkpoint devices either.

**B4 — blocking, high: REFUTED that marker PASS establishes the expected depth image or eleven rendered lifecycle checkpoints.** `scripts/verify.py:266–333` accepts any near-colour pixels occupying at least one quarter of the inset box. When depth is reported, it merely requires *one* cyan pixel anywhere and zero threshold-matching yellow pixels. It checks neither the 60/40 masks nor complete coverage. `depthAttached` can be false or missing, bypassing all depth requirements. Absence of yellow does not establish that the third draw was issued: removing that draw altogether still leaves the expected two colours.

“Frames without level content” only examines the marker box's brightest RGB sum, not level content or the rest of the image (`verify.py:295,319–333`). Up to three important lifecycle checkpoints can fail to carry a marker and be exempted merely because that box is dark. The gate can pass with nether, overworld and reconnect all unverified. A colour neighbourhood is reasonable for composition darkening, but the channelwise ranges allow unrelated saturated scene pixels and do not enforce any ratio or location beyond the box.
