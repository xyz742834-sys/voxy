## 1. なぜ 5c-2 を 2 つに割ったか

計画書の 5c-2 は「アトラス + ライトマップを実物に」だが、
<b>実データの中身を取ってくる経路にこの環境の地雷がある</b> (§4)。
そこで<b>寸法</b>と<b>中身</b>を分けた:

| 段 | 変える変数 | MC 起動 | 状態 |
|---|---|---|---|
| **5c-2a** | アトラスの<b>寸法とミップ</b> (中身は合成のまま) | 不要 | ✅ 完了 |
| **5c-2b** | アトラスの<b>中身</b> (実際のブロックテクスチャ) | 要る | ⬜ 設計判断待ち (§4) |

**一度に増やす未知は 1 つ**という原則の適用である。
しかも 2a は<b>既に分かっている危険な変数</b>を単独で潰す
[確認済 — Stage 1 で UV 計算と噛み合わない不具合を踏んだ]。

## 2. なぜ「実寸にしても同じ絵」が対照になるのか

シェーダの UV 計算は<b>タイル格子 256x256 を直書き</b>している
[確認済 — `quads.frag`]:

```glsl
vec2 modelUV = vec2(modelId&0xFFu, (modelId>>8)&0xFFu)*(1.0/256.0);
vec2 uv2     = modf(uv, tile)*(1.0/(vec2(3.0,2.0)*256.0));
```

合成アトラス (768x512) は<b>この格子をそのまま</b>持っていて、
面セルを 1 テクセルに縮めただけである:

| | タイル格子 | 面セル | 寸法 | ミップ |
|---|---|---|---|---|
| 合成 (SMALL) | 256 x 256 | **1 x 1** | 768 x 512 | 1 段 |
| 実物 (REAL) | 256 x 256 | **16 x 16** | 12288 x 8192 | 4 段 |

つまり実寸化は<b>面セルの 16 倍拡大</b>であり、
UV の正規化は変わらない。**だから同じ絵が出なければならない。**

> ⚠ **変わるとしたら面セルの継ぎ目である。**
> SMALL はセル内のどこを引いても同じ色だが、REAL は 16x16 あるので
> <b>丸めが違えば隣のセルを引く</b>。計画書が「継ぎ目を跨ぐ quad を含めよ」と
> 書いていたのはこの一点のためである。

## 3. 実装

| 変更 | 中身 |
|---|---|
| `VkTerrainResources.AtlasScale` | `SMALL` (面セル 1px) / `REAL` (16px・実物と同じ寸法とミップ段数) |
| アトラスの充填 | <b>面セル内は一様色</b>。縮小でミップを作っても色が変わらないので、主張がミップにも及ぶ |
| アップロード | <b>モデル単位・ミップ単位</b>に変更 (§3.1) |

### 3.1 ⚠ アップロードの粒度を本番に合わせた

以前は<b>全面 1 回</b>のコピーで、staging もアトラスと同じ大きさだった。
実寸では<b>402MB の staging をホスト側に抱える</b>ことになり成立しない。

本番は<b>モデルごと・ミップごと</b>に上げている
[確認済 — `ModelFactory` が `nglTextureSubImage2D` をその粒度で呼ぶ]。
同じ粒度に揃えたので、staging は<b>使うモデルぶんだけ</b>で済む。

> ⚠ **`maxModels` より先のタイルは未定義のままになった。**
> 本番も「焼いたモデルだけ」を上げるので<b>意味としては本番に近づいた</b>が、
> <b>範囲外の stateId を引くと未定義の色が出る</b>。
> 既存の `VkTerrainResourcesTest` がこれで落ち (モデル 7556 を 4096 個しか
> 確保していない資源で引いていた)、<b>テスト側を意図に合わせて直した</b>。

### 3.2 ⚠ 領域配列をスタックに積んで JVM を落とした

`VkBufferImageCopy.calloc(maxModels * mips, stack)` は
既定のモデル数 (4096) だけで LWJGL の `MemoryStack` を超え、
<b>test JVM が "Out of stack space" で落ちた</b>。ヒープに移した。

> **【規約 13】個数が入力に比例する配列は `MemoryStack` に積まない。**
> <b>2 度目である</b> — Phase 0 の Step4 でも `MemoryStack` をループ内で使い回して枯渇させた。
> 入力が小さいうちは通り、<b>規模を上げた瞬間に落ちる</b>ので、
> 「動いている」ことが証拠にならない型である [規約 11 の一族]。

## 4. ⚠⚠ 5c-2b (中身を実物に) の障害 — <b>設計判断が要る</b>

実際のブロックテクスチャを取るには `ModelFactory` が要るが、**この環境では 2 つ問題がある**:

| 障害 | 中身 |
|---|---|
| **GL 4.5 DSA** | `ModelStore` がアトラスを `GlTexture().store(...)` で作る。Apple の GL 4.1 に無く、<b>呼べば JVM ごと abort</b> [docs/phase5c1a-completion.md §7 の一覧に追加すべき] |
| **MC のワールド依存** | `ModelFactory` が `Minecraft.getInstance().level` を参照する (既定バイオーム)。ワールドに入っていないと成立しない |

**ベイク自体は CPU 側である** — `SoftwareModelTextureBakery` が
`ColourDepthTextureData` を作り、`ModelFactory` がそれを CPU の `MemoryBuffer` に
ミップ込みで並べてから GL へ上げている。
つまり<b>「並べたバッファ」までは GL に触れない</b>ので、
そこから `vkCmdCopyBufferToImage` に分岐できる見込みがある [推測]。

> **どう分岐するかは規約に書かれていない設計判断なので、指示を仰いでから実装する。**
> 選択肢は §4.1。

### 4.1 選択肢

| 案 | 中身 | 良い点 | 悪い点 |
|---|---|---|---|
| **A** | `ModelStore` を<b>バックエンド抽象</b>にし、Vulkan 実装を足す | 本番の形。5c-3 以降もそのまま使える | 既存の GL クラスに手を入れる (「GL 版を無傷で残す」方針との兼ね合い) |
| **B** | `ModelFactory` の<b>アップロード直前のバッファだけ</b>を横取りする専用の入口を足す | 変更が小さい。GL 経路に触れない | 本番の形ではない。5c-3 で作り直しになる |
| **C** | 5c-2b を<b>後回し</b>にし、先に 5c-3 (実ジオメトリ) へ進む | 実データの不変条件検査を先に得られる | アトラスが合成のままなので「実データで正しい絵か」は言えない |

## 5. 自動検査 — 何が言えて、何が言えないか

`VkAtlasScaleTest` (JUnit、GL 不要):

| 検査 | 主張 |
|---|---|
| `theTwoScalesReallyDiffer` | 2 つの倍率が<b>本当に違う</b> (寸法・ミップ段数・モデルあたりのバイト数) |
| `theRealSizedAtlasProducesTheSamePicture` | 実寸で描いても<b>1 画素も変わらない</b>。絵が非自明であることも同時に要求 |

**感度の確認** [確認済]: 実寸側だけ<b>タイル格子を 16 に取り違える</b>変異
(Stage 1 で踏んだ型) を入れると、**5526 画素の差**として落ちる。

```
5526 pixels differ ... First at (388,180): small=0x4c69114d real=0x4c990099
```

**言えないこと**: <b>実際のブロックテクスチャで正しい絵になるか</b>。
それは 5c-2b (§4) の仕事である。ここで言えたのは
<b>「寸法とミップを実物にしても UV の解釈が変わらない」</b>までである。
