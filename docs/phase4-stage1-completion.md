## 2. 見つかった不具合 — 3 件 [確認済]

**いずれも既存コードにあり、絵を出す作業の中で表に出た。**

### 2.1 🔴 両面/半透明 quad が `faceData[6]` を読んでいた

`SyntheticTerrain.writeGeometry` は両面ランと半透明ランの quad に
`Face.DOUBLE_SIDED.bit` = **6** を face として書き込んでいた。

しかし quad の face は頂点シェーダで `model.faceData[face]` の添字になり、
`BlockModel.faceData` は **6 要素しかない** [確認済 — `block_model.glsl`]。
6 を渡すと構造体の次のメンバ (`flagsA`) を面データとして読む**範囲外アクセス**になる。

「両面」「半透明」はセクションメタデータの本数 (`b.x`) で表す**区分**であって、
quad の面の値ではない [確認済 — `cmdgen.comp` の msk 構築は本数しか見ていない]。

→ これらのランにも実在の面 (0..5) を回して入れるよう修正した。

### 2.2 🔴 合成データの quad が重なっていて、索引ずれが絵に出なかった

既存の doc は「索引がずれれば絵に出る」と書いていたが、**成り立っていなかった。**

位置をラン内連番 `i` から作っていたため、同じセクションの別のラン (別の面) が
**まったく同じ格子点を共有**していた。この状態で全描画コマンドの
`quadOffset` を一律 +1 しても、描かれる quad の集合は
ラン境界で隠れている 1 枚が入れ替わるだけになる。

**実測: 512x512 で差分 0 ピクセル** [確認済 — 実際に観測]。

Stage 2b が検出したいのはまさにこの種の索引ずれ (二分探索の off-by-one) なので、
これは**基準データとして致命的**だった。位置をセクション内通し番号から作るよう変更し、
同じ 1 quad ずらしで **735 ピクセルの差分**が出るようになった。

> この件は「対照実験を書いたから見つかった」類のもので、
> 決定性テストだけを書いていたら通過していた。

### 2.3 🔴 アトラスがシェーダの UV 計算と噛み合っていなかった

`VkTerrainResources` のアトラスは 256x256 px を「16x16 タイル x 16px」として作っていた。

しかしフラグメントシェーダはタイル原点を
`vec2(modelId&0xFF, (modelId>>8)&0xFF) * (1/256)` で求める [確認済 — `quads.frag` の `getBaseUV`]。
**タイル格子はアトラスの画素数ではなく modelId の分解の仕方で決まり、256x256 で固定**である。
さらに 1 タイルは `vec2(face>>1, face&1) * (1/(vec2(3,2)*256))` で 3x2 の面セルに割られる。

256px のアトラスでは **1 モデル = 1 テクセル、1 面 = 1/3 テクセル**となり、
面どころかモデルすら分離できない。

→ 768x512 に変え、**(modelId, face) の組ごとに 1 テクセル**が対応するようにした。
色は `R = modelId&0xFF`, `G = modelId>>8`, `B = face*40+15` で、
描かれたピクセルから索引を逆算できる。

**サンプラは NEAREST でなければならない。** 線形補間すると隣の組と混ざる。

### 2.4 その他 2 件 (軽微)

| 箇所 | 内容 |
|---|---|
| `writeSimpleModel` の indentation | 63 (= 1.0) を入れていたため各面が反対側に貼り付き、内外の裏返った箱になっていた。0 に修正 |
| `VkRenderTarget.beginRendering` | src が `TOP_OF_PIPE`/0 だったため、同一コマンドバッファ内の「読み戻し → 再描画」の **WAR に実行依存が張られていなかった**。`ALL_COMMANDS`/0 に修正 (WAR は実行依存だけで足り、可視化は不要) |

### 2.5 既存テストが JVM ごと落としていた件

`ValidationLayerProbeTest.enumerateLayerProvidedExtensions` が
存在しないレイヤ名で `vkEnumerateInstanceExtensionProperties` を呼び、
**libMoltenVK 内で SIGSEGV** になっていた [確認済 — 素の `./gradlew test` で再現]。

LWJGL 同梱の MoltenVK はローダーを介さないため explicit layer の概念が無い。
レイヤ一覧に載っていることを先に確かめるようガードした。
これで**ローダー無しでも `./gradlew test` が通る** (92 PASS / 3 SKIP)。

### 3.1 検証 1 が最も強い理由

`minimal()` の唯一の quad について、期待値を CPU 側で全経路たどって出している:

```
位置    UP 面 -> indentation 0 かつ face&1==1 なので y=1 の水平面
        中心 (0.5, 1, 0.5) を同じ MVP で射影 -> 画素 (256, 256)
色      stateId = (section 0, run 3, i 0) = 192
        アトラスの (modelId 192, face 1) = (192, 0, 55)
ティント UP_FACE_TINT = 1.0、ライトマップ一様白 -> RGB 素通り
アルファ 不透明度ではなく face|lod<<3|hasAO<<6 = 1|0|64 = 65
```

**実測 `[192, 0, 55, 65]` @ (256,256) で完全一致** [確認済]。

アトラスの UV 計算・モデルデータ・ライティング・面ティント・位置エンコード・
投影の約束事が**同時に**合っていないと一致しない。

## 4. バリアの記録 — **絞れたが、根拠は弱い**

### 4.1 縮小スコープに残るハザードは 3 点しかない

5 段を除いたため、`phase4-buffer-hazards.md` が挙げる WAR 6 箇所は
**Stage 1 の式には現れない** (どれも「前フレームの描画 → 今フレームの生成」に由来し、
生成側が無いため)。残るのは:

| # | ハザード | NARROW での記述 |
|---|---|---|
| B1 | ホスト書き込み → 描画の読み (間接/SSBO/UBO) | `HOST/HOST_WRITE` → `DRAW_INDIRECT\|VERTEX\|FRAGMENT` / `INDIRECT_COMMAND_READ\|SHADER_STORAGE_READ\|UNIFORM_READ` |
| B2 | アトラス転送 → サンプリング | `recordAtlasUpload` 内で個別記述済 (レイアウト遷移と不可分) |
| B3 | 読み戻し → 次フレームの描画 (WAR) | `beginRendering` の `ALL_COMMANDS`/0 (§2.4 で修正) |

### 4.2 「絞っても壊れなかった」の意味

`Barriers.CONSERVATIVE` (`ALL_COMMANDS` 全書き) と `Barriers.NARROW` で
**差分 0 ピクセル**だった。しかしこれは十分性の証明ではない:

1. **同期バリデーションが機能しない** — 記述漏れを検出する手段が無い
2. **in-flight = 1** — フレーム境界で必ず GPU がアイドルになる
3. **ユニファイドメモリ + HOST_COHERENT** — ホスト書き込みの可視化が構造的に起きやすい
4. **`vkQueueSubmit` の暗黙の可視化** — submit 前のホスト書き込みは仕様上必ず見える

**4 の帰結として、B1 は実のところ NARROW の側すら省ける** [確認済 — 仕様ベース]。
それでも明示的に置いているのは、この保証が「submit 前に書いた」ことに依存しており、
アップロードを `VkUploadStream` 経由や別スレッドに移した瞬間に崩れるためである。
繰り返し踏んでいる誤りの型 (CPU 書き込みと GPU コマンドに順序が付かない) がまさにここなので、
依存関係をコードに残した。

### 4.3 「絞って壊れた箇所」は無い [未検証に近い]

手順としては「壊れた箇所を記録する」ことになっていたが、
**上記の理由でこのスコープでは壊れようがない**。
バリアの記述漏れが表に出るのは、5 段を戻して
「前フレームの描画 → 今フレームの生成」の WAR が実在するようになってからである。

→ **Stage 3 / Phase 5 で 5 段を戻すときが、バリア設計の本番。**
そのときは `phase4-buffer-hazards.md` の系列表が主の根拠になる。

### 5.1 【規約】基準データの各 quad は別々の可視位置を占めること

> **これは手順ではなく、データセットの不変条件として常設検査する。**
> 検査は `SyntheticTerrainTest.everyQuadOccupiesADistinctVisiblePosition`。
> 新しいデータセットを足したら、同テスト内の `namedDatasets()` に必ず登録すること。

**なぜ手順ではだめか**: この性質はデータセットを増やすたびに壊れうる。
新しい境界条件が既存のものと同じ格子点を共有した瞬間、
**対照実験だけが静かに無力化され、全テストは PASS のままになる**。
手順は忘れられるが、テストは忘れられない。

**破れると何を失うか** (2 つある):

| # | 失うもの |
|---|---|
| 1 | **索引ずれが絵に出なくなる。** 隠れている quad と入れ替わるだけになり、対照実験が効かない |
| 2 | **描画順に結果が依存する。** 共平面の矩形は深度で決着せず後勝ちになる。Stage 1 (セクション順) と Stage 2b (面順) は<b>発行順が違う</b>ので、統合と無関係な差分が出て比較そのものが成立しない |

2 は Stage 2 に入って初めて効いてくる要件で、Stage 1 時点では見えていなかった。

**なぜ「投影後の画素」ではなくワールド空間で見るか**: 投影後の重複を禁じると、
遠くの quad が同じ画素に落ちただけで失敗する。それはカメラの性質であって
データの欠陥ではない。ワールド空間のフットプリント重複は視点に依らないデータの性質で、
上の 2 つを直接保証する。「選んだカメラで実際に分離できているか」は
`shiftingTheQuadIndexChangesTheImage` の対照実験が受け持つ
(この 2 段構えで、どちらの層が壊れたか切り分けられる)。

不変条件検査それ自体にも対照を付けてある
(`duplicateFootprintsAreActuallyDetected`) — 検査が重複を実際に捕まえられなければ、
「重複ゼロ」は「検出できていない」と区別が付かない。

### 5.1b 【規約 2】半透明 quad は画面上で重ならないこと

> 検査は `VkTranslucentTest.translucentQuadsDoNotOverlapOnScreen`。
> 半透明を持つデータセットを足したら、同テスト内の `translucentDatasets()` に登録すること。

**なぜ 1 本目と別に要るのか**: 1 本目 (§5.1) はワールド空間の重なりを禁じるが、
ブレンドで問題になるのは<b>同じ画素に 2 枚落ちること</b>である。
ワールドで離れていても視線方向に並べば画面上では重なる。

**破れると何を失うか**: ブレンドは順序依存で、
<b>距離バケット内の描画順は非決定的</b> (スロットを `atomicAdd` で取るため。
GL 版も同じ [確認済 — `buildtranslucents.comp`])。
重なった半透明 quad があると<b>同じ入力でも絵が実行ごとに変わり</b>、
Stage 1〜3 で使ってきた「差分ゼロ」の比較が成立しなくなる。

**⚠ 画面外の quad は自動的に「重ならない」。**
それだけだと<b>検査していない quad があるのに通ってしまう</b>ので、
全 quad が画面内にあることも同時に検査する (実際に 1 枚が画面外のまま通っていた)。

対照は `overlapDetectionActuallyWorks` (同じ位置に 2 セクション置いて検出されること)。

| **Phase 5c-1b (12)** | **復帰処理が no-op だった。** 素の GL で深度テストを切り、Blaze3D のキャッシュ API で戻していた。キャッシュが「既に有効」と判断して `glEnable` を発行せず、<b>MC のエンティティが深度テスト無効で描かれた</b> (mob が地形を貫通) | 目視 (スクリーンショット)。ログ上は正常だった |

| **Phase 5c-1b (13)** | **調査で分かっていた制約が実装に入っていなかった。** 「MC-Vulkan と Voxy は同居できない」と doc に書いた後、バックエンド選択にその条件を入れ忘れ、<b>MC が Vulkan のとき Voxy が有効化されて描画フレームでクラッシュ</b>した | 実機で MC の設定が Vulkan に戻っていて発火 |
| **Phase 5c-1b (14)** | **オフスクリーンの検査に存在しない要素だった。** 合成が黒くなる原因は<b>MC が残したサンプラオブジェクト</b>で、テクスチャ側の設定より優先され RECTANGLE が incomplete 扱いになっていた。ベンチには誰もサンプラを bind しないので再現しない | `solid` モード (テクスチャを読まず定数色) で「描画は届く / 読みが黒」を分けた |
| Phase 5c | **逆Z / Y 規約の切り替えで既存テストが 1 件も落ちなかった。** 描いた結果どうしを比べる形なので、<b>全体が一様に変わっても差が出ない</b> | 「落ちないこと自体」を疑った。深度値と画素位置を直接見る検査を新設 |

**毎回「基準そのものが正しいか」を疑って初めて見つかっている。**
偶然ではなく<b>この環境での常態</b>である。検証を書いたら
**それが壊れたときに落ちるか**を対照実験で必ず確かめること。

**Stage 3 で分かった追加の教訓**: 対照実験は<b>書いたあとも壊れる</b>。
上の表の 3 と 4 は同じ対照が別々の理由で 2 回無効化された。
データやレイアウトを変えたら、対照が今も効いているかを確かめ直すこと。

**Stage 4 で分かった追加の教訓**: 壊れるのは<b>検査対象だけではない</b>。
6 例目は「判定の初期条件」が、7 例目は「対照の作り方」が壊れていた。
どちらも検査コード自体は正しく、周辺の前提が検査を無意味にしていた。
新しい条件を足すときは「これが壊れたらこのテストは落ちるか」を毎回問うこと。

### 【規約 3】打ち消し合う変換を疑う (Phase 5b、10 例目)

> **打ち消し合う 2 つの変換を含む経路では、端点の一致は何も保証しない。**

「空虚に満たす方法の列挙」は経路の<b>端点だけでなく途中も見る</b>。
入力と出力が一致しても、途中に対称な誤りが 2 つあれば通ってしまう。
経路に座標変換・順序変換・形式変換が入るたびに
「この変換の逆が経路のどこかに居ないか」を確かめること。

**機械的検査だけに寄せない。** 10 例目は差分ゼロ比較 10 項目が全て PASS し、
<b>目視だけが効いた</b>。

### 【規約 4】予測と実装が同じ規約を参照していないか (Phase 5c、11 例目) — **最も一般性が高い**

> **「予測 vs 実装」型の検査では、予測が実装と同じ規約を参照していないか確かめる。**
> **計算経路が別 (CPU / GPU) でも、規約を共有していれば規約の誤りは打ち消し合う。**
> **少なくとも 1 つは<b>規約に依存しない外部の事実</b>を主張すること。**

11 例目は `VkOrientationTest` で実際に起きた。
ジオメトリの世界座標を CPU で投影して行を予測し、GPU が塗った行と比べる —
一見「CPU と GPU で独立」だが、<b>独立しているのは計算の経路だけ</b>で、
<b>投影行列 (= 規約) は共有</b>していた。行列の Y 符号を反転すると両方が反転して一致する。

塞ぎ方の例:

```java
// 行列に依存しない物理的な事実。
// 「ジオメトリより上を見れば、ジオメトリは画面の下半分に出る」
assertTrue(cov.centroidRow() < H / 2.0, ...);
```

**この観点で既存の検査を洗い直した結果は §5.3。**

### 【規約 5】対照は<b>本番が通る経路</b>を通すこと (Phase 5c-1b、12 例目)

> 実装に変種 (フラグ・モード・分岐) があるなら、<b>本番が使う変種</b>で対照を回す。
> 全変種で回すのが確実。

12 例目では、再発防止に書いた検査が<b>変異を検出できなかった</b>。
検査が「深度を書く版」の合成だけを見ており、
<b>MC が実際に使う「書かない版」</b>を見ていなかったためである。
**本番が通る経路を対照が通っていなければ、対照は本番を守っていない。**

> 規約 4 と同じ一族である — 規約 4 は「予測と実装が規約を共有していないか」、
> 規約 5 は「対照と本番が経路を共有しているか」。<b>向きが逆の同じ問い</b>。

### 5.3 【監査】規約 4 の観点で既存の検査を洗い直す

| 検査 | 規約を共有しているか | 判定 |
|---|---|---|
| `VkOrientationTest.geometryLandsOnThePredictedRow` | **していた** (投影行列) | **修正済み** — 行列非依存の主張を追加 |
| `VkTerrainRenderTest.singleQuadLandsWhereAndHowPredicted` | **している** (投影行列) | **Y/X の向きは検証できていない** (下記) |
| `VkTranslucentTest` の中心画素比較 (2 箇所) | している (投影行列) | 目的が「どの quad か」なので<b>向きの検証には元々使えない</b>。役割の範囲内 |

**`singleQuadLandsWhereAndHowPredicted` について**: 同じ行列で射影した画素の
<b>色</b>を見ているが、対象は 1 枚の平坦な面なので<b>面上のどの画素でも同じ色</b>になる。
したがって上下・左右の反転を入れても<b>この検査は通る</b>。

javadoc の「投影の約束事を一度に押さえる」は<b>言い過ぎ</b>だった —
押さえているのは UV 計算・モデルデータ・ライティング・面ティント・位置エンコードで、
<b>画面上の向きは含まない</b>。向きは `VkOrientationTest` が受け持つ。

> **重複して書き直すのではなく、担当範囲を明示して分ける。**
> 1 本の検査に全部を負わせると、どれかが空虚になったときに気づけない。
