# Phase 5c 計画 — MC への接続と実データ投入

**状態**: 段階分けと確認事項の整理。**5c-1 の実装は未着手。**
**前提**: 5b 完了 (interop 合成が Phase 4 出力とビット一致)、
`Capabilities` の clinit クラッシュ修正済み、
**逆Zへの切り替えと再検証が完了** ([`phase5c-reverse-z.md`](phase5c-reverse-z.md))。

---

## 1. なぜ段階を切るか

5c は<b>これまでで最も未知が多い</b>。一気に繋ぐと絵が出ないときに
「接続の問題」「データの問題」「規約の食い違い」を切り分けられない。

原則: **一度に増やす未知は 1 つ。**

Phase 1〜4 で使ってきた手 (まだ移していない段は合成データで代用する) を、
今度は<b>逆向き</b>に使う — <b>先に接続だけを実物にし、データは合成のまま</b>にする。
理由は<b>合成データなら正解の絵が既知</b>だからである。

## 2. 段階

### 5c-1 — MC への接続 (データは合成のまま)

`VoxyRenderSystem` / `AbstractRenderPipeline` を Vulkan 経路に繋ぐ。
描くのは <b>Phase 4 の合成地形</b>。不透明パスのみ。

| 確認できること | 確認できないこと |
|---|---|
| 起動して落ちない (ライフサイクル・スレッド) | 実データでの正しさ |
| MC のフレームバッファ (**D32F・ステンシル無し**・別サイズ) への合成 | 半透明・temporal |
| ウィンドウリサイズでの作り直し | 性能 |
| フレームが回る (同期の実コスト) | |
| **MC 地形との前後関係** (深度が効いているか) | |

**対照**:
- 合成地形は `interopCompositeCheck` と<b>同じ絵</b>になるはず。
  MC 内でスクリーンショットを撮り、オフスクリーン版と見比べる
- **深度が効いていることの対照**: MC の地形の<b>手前</b>と<b>奥</b>に
  同じ合成地形を置き、奥のものが隠れること。
  これをやらないと「深度を無視して全部手前に描いている」状態を見逃す
  (5b で踏んだ「打ち消し合う変換」と同じ型 — 色だけ見ても分からない)

**なぜ不透明だけか**: 半透明はバケット順が非決定的で
[確認済 — `atomicAdd`、提案書 §5.2 障害 B]、
接続の不具合と区別が付かなくなる。

### 5c-2 — アトラス + ライトマップを実物に

提案書 §4.4 の ①。ジオメトリ・lookup・HiZ は合成のまま。

| 確認できること |
|---|
| 実テクスチャで合成ジオメトリが正しく描かれる |
| **アトラスの UV 計算が実寸 (12288 x 8192) で合っているか** |
| `ModelFactory` のアップロード先差し替え (`nglTextureSubImage2D` → `vkCmdCopyBufferToImage`) |

**この段が最初なのは、アトラスが唯一「合成データと実データで挙動が変わることが
既に分かっている」入力だから** [確認済 — Stage 1 で UV 計算と噛み合わない不具合を踏んだ]。

**対照**: 合成アトラス (768x512) は実アトラスの<b>最小構成</b>である。
実寸に変えても<b>同じ quad が同じ色で出る</b>こと。
タイル境界 (面セルの継ぎ目) を跨ぐ quad を明示的に含めること。

**Phase 4 の資産がそのまま効く段。** 絵の正しさとは独立に「壊れていない」ことの下限を保証する。

## 4. ⚠ 実装前に確認したいこと

### 質問 1 (最重要): **MC 26.2 は逆Zである。Phase 4 は逆Zで検証していない** — **解決済み (案 A)**

> **完了。** 逆Zに切り替え、`VkDepth` に約束事を集約し、再検証した。
> 詳細と、**既存 168 件が 1 件も落ちなかった**という発見は
> [`phase5c-reverse-z.md`](phase5c-reverse-z.md)。以下は判断時の記録である。

[確認済 — `com.mojang.blaze3d.pipeline.DepthStencilState.DEFAULT` が
`CompareOp.GREATER_THAN_OR_EQUAL`]。したがって MC 上では
`RenderProperties.isReverseZ()` が **true** になり:

```
NEAR = 1.0   FAR = 0.0   clearDepth = 0.0   closerEqual = GEQUAL   #define USE_REVERSE_Z
```

**一方 Phase 4 の Vulkan 経路は非逆Zで組んで、非逆Zで検証してある** [確認済 — 実物]:

| 箇所 | 現状 (非逆Z) | MC に合わせるなら |
|---|---|---|
| `VkTerrainRenderer` のシェーダ define | `USE_ZERO_ONE_DEPTH` のみ | `USE_REVERSE_Z` を追加 |
| パイプラインの深度比較 | `VK_COMPARE_OP_LESS_OR_EQUAL` | `GREATER_OR_EQUAL` |
| 深度クリア | `1.0f` | `0.0f` |
| `VkSceneUniform.perspective` | near→0, far→1 | near→1, far→0 |
| `depthBound` の中立値 | `0.0` (「誰も落とさない」) | **`1.0`** に反転 |

つまり **155 → 166 件のテストが検証したのは、本番で使う設定ではない**。

- **案 A**: Vulkan 経路を逆Zに切り替え、**Phase 4 の深度関連テストを逆Zで再検証する**。
  基準画像は取り直し。工数はかかるが<b>検証した設定と出荷する設定が一致する</b> ← 推す
- **案 B**: 両方を設定可能にし、テストは両方で回す。テスト数がほぼ倍
- **案 C**: 非逆Zのまま、interop の境界で深度を変換する。
  変換が 1 つ増える = **5b で踏んだ「打ち消し合う変換」の温床**。推さない

**これは 5c-1 の前に決める必要がある。** 深度の約束事は全ての段に効く。

> 補足: ステンシル等価性の解析 (`phase5b-stencil.md`) は<b>逆Z / 非逆Z の両方</b>で
> 成立を確認済みなので、この判断に影響しない。

### 質問 2: SSAO をどうするか — **解決済み (5c では無効化)**

> **5c では無効化する** [判断済]。理由:
> 5c の目的は「実データで地形が正しく出るか」でありポストプロセスの完成度ではない。
> ステンシル依存が `initDepthStencil` の扱いと絡んで変数が増える。
> また `ssao.comp` は **push constant 未移行** で
> (location 4 の重複が未確定 — [`phase2-pushconstant-todo.md`](phase2-pushconstant-todo.md))
> Vulkan 経路に載っていない。**Phase 6 で扱う。**
> 以下は判断時の記録である。

`SSAO.computeSSAO(viewport, colourSSAOTex, colourTex, fb.getDepthTex(), sourceDepthTex)` は
GL のフルスクリーンパスで、**Voxy の深度と色を読んで色を書く**。
また `initDepthStencil` が張ったステンシルテストが<b>有効なまま</b>走る
[確認済 — `SSAO` はステンシルに触らない]。

- **案 A**: GL のまま。interop の色・深度テクスチャを入力にする。
  合成パスの前段に挟むだけで済む ← 単純
- **案 B**: Vulkan に移す。パスが 1 つ増えるが interop の往復が減る
- **案 C**: 5c では SSAO を無効化して進め、後で決める ← 未知を減らす意味では有効

SSAO は Voxy の絵の見た目に効くが、**移植の成立性には効かない**。
5c-1 の未知を減らすなら C、最終形なら A が素直だと考えている。

### 質問 3: 5c-1 で MC のどの深度を Vulkan に渡すか — **確認完了、判断不要**

> **MC の深度は `D32_FLOAT`、ステンシル無し** [確認済 — §8.1]。
> interop の R32F がそのまま運べる。GL 側は「MC の深度 → R32F にコピーするだけ」。

## 8. 5c-1 着手前の確認結果と、残る 2 つの判断

### 8.1 MC の深度は `D32_FLOAT`・ステンシル無し [確認済 — バイトコード]

`com.mojang.blaze3d.pipeline.RenderTarget` が参照する深度書式は
**`GpuFormat.D32_FLOAT` の 1 つだけ**で、クラスに stencil を扱うフィールドもメソッドも無い。

> ⚠ **提案書と本計画の「MC の d24s8 フレームバッファ」は誤りだった。**
> d24s8 は <b>Voxy 自前の `DepthFramebuffer`</b> であって MC のものではない
> [確認済 — `AbstractRenderPipeline.fb = new DepthFramebuffer(GL_DEPTH24_STENCIL8)`]。
> MC 側は D32F でステンシルを持たない。

**これは 5c-1 を楽にする**:
- 合成先にステンシルが無いので、`phase5b-stencil.md` の案 A (ステンシル不要) と噛み合う
- interop の R32F は 32bit float なので、MC の深度を<b>変換なしで運べる</b>
- Voxy 自前の d24s8 は Vulkan 側の D32F 深度アタッチメントに置き換わる

Voxy が受け取る深度は Sodium 経由である
[確認済 — `MixinDefaultChunkRenderer` が
`((GlTextureView) target.getDepthTextureView()).glId()` を渡す]。
<b>`GlTextureView` にキャストしている</b>ので、
**Voxy は MC が OpenGL バックエンドのときしか動かない**。
MC-Vulkan と Voxy の同居は現状そもそも成立しない (interop 経路が主軸である裏づけ)。

### 8.2 MC の MVP は逆Z・0..1 まで済んでいる。残るのは **Y の向きだけ** [確認済 — 実物]

`VoxyRenderSystem.computeProjectionMat` は既に

```java
if (properties.isReverseZ()) { /* near と far を入れ替える */ }
... .m22((properties.isZero2One() ? far : (far+near)) / (near - far))
```

を行っており、`viewport.MVP` は<b>逆Z・0..1 の GL 規約行列</b>である。
逆Zの切り替えが済んだ今、Vulkan 側との差は **Y の向き 1 点だけ**になった。

---

### ⚠ 判断 1: Y の向きをどこで吸収するか

**5b で踏んだ「打ち消し合う変換」が、今度は 2 経路に増える。**

5b で測れた事実 [確認済]: Vulkan 側が `m[5] = -f` (Vulkan 規約) で描くと、
IOSurface の 0 行目が<b>絵の上端</b>になり、GL 合成側は
`height-1-y` の読み替えが要る。C7 がこれを常設で見張っている。

5c-1 では色に加えて<b>深度が逆向きに流れる</b>:

```
MC 深度 → (GL パス) → IOSurface → (Vulkan が texelFetch(gl_FragCoord.xy)) → cull / depthTex
Vulkan 色 → IOSurface → (GL 合成が texelFetch) → MC の FBO
```

GL の `gl_FragCoord.y` は下から、Vulkan の `gl_FragCoord.y` は上から数える。
<b>2 経路それぞれに反転の要否がある。</b>

| | 案 A: Vulkan 規約に寄せる | 案 B: GL 規約のまま通す |
|---|---|---|
| MVP | MC の MVP に Y 反転を掛ける | **MC の MVP をそのまま使う** |
| IOSurface の 0 行目 | 絵の上端 | 絵の下端 |
| 色の合成 (GL) | **反転が要る** (5b の現状のまま) | **反転しない** (5b の実装を戻す) |
| 深度の受け渡し | **反転が要る** (GL のコピーパスか Vulkan の読みで) | **反転しない** |
| Y 反転の総数 | **3 箇所** | **0 箇所** |

- **案 B を推す。** 反転が 1 つも無いので「打ち消し合う変換」が原理的に発生しない。
  5b の教訓 (変換は減らすほど安全) の直接の適用になる
- ただし案 B は<b>5b で検証した `GlInteropCompositor` の反転を取り消す</b>ことになる。
  C7 の意味も反転する (「反転しないことが正しい」に変わる)
- さらに `VkSceneUniform.perspective` の `m[5] = -f` を落とすと
  <b>テストと本番の Y 規約が揃う</b>。落とさないと、逆Zで直したのと同じ
  「テストが本番でない設定を検証している」状態が Y 軸で再発する

**案 B を採る場合に一緒に決めたいこと**: `VkRenderTarget.writePng` は
0 行目を PNG の上端として書いている。案 B では 0 行目が絵の下端になるので、
<b>PNG 書き出し側で反転する</b>ことになる (表示のための反転で、経路上の変換ではない)。

### ⚠ 判断 2: この Mac で Voxy をどう有効化するか

**現状、この Mac では Voxy は自分を無効化する** [確認済 — 実機ログ]:

```
[Voxy] Voxy is unsupported on your system.
[Voxy] Not creating renderer due to disabled
```

`VoxyClient.initVoxyClient` の
`systemSupported = compute && indirectParameters && !hasBrokenDepthSampler` が
false になるためで、Apple の GL 4.1 に `glDispatchComputeIndirect` と
`glMultiDrawElementsIndirectCountARB` が無いことが原因である
[確認済 — docs/phase2-binding-audit.md §8.4]。**これは Vulkan 移植の出発点そのもの。**

5c-1 で繋ぐには、この判定を通り抜けてバックエンドを選ぶ仕組みが要る。

- **案 A**: `systemSupported` の条件に「または Vulkan が使える」を足し、
  <b>GL が足りなければ Vulkan を使う</b>。判定は 1 箇所で済む ← 推す
- **案 B**: 設定項目 (`voxy.backend = auto | gl | vulkan`) を足す。
  切り替えて比べられるが、**この Mac では GL 経路が動かないので比較対象が無い**
- **案 C**: macOS では常に Vulkan。フォークの性格には合うが、
  将来 GL 4.6 環境で動かす余地を消す

案 A を推す。判定が 1 箇所に留まり、
「GL で動くなら GL、動かないなら Vulkan」という読みやすい規則になる。

> どちらの判断も<b>規約に書かれていない設計判断</b>なので、
> 指示を仰いでから実装する。

## 9. 5c-1 の内部段階 (判断 1・2 が決まり次第)

「半端に配線して壊れた状態で置かない」ため、5c-1 をさらに 5 つに割る。
<b>各段階は単独で MC を起動して確認できる</b>状態にする。

### 5c-1a — 配線して「何も描かない」

Voxy が Vulkan バックエンドで有効化され、`VkContext` が MC のライフサイクルで
初期化・破棄される。**合成は一切しない。**

| 確認できること | 確認できないこと |
|---|---|
| 起動・終了で落ちない | 絵に関すること全部 |
| ワールド入退出、リサイズでリークしない (`TrackedObject` の未解放検出) | |
| MC の絵が<b>一切変わらない</b> (対照: Voxy 無効時と同一) | |

**対照**: この段で MC の絵が変わったら、それは<b>意図しない副作用</b>である。
スクリーンショットを Voxy 無効時と突き合わせる。

### 5c-1b — 非対称なテストパターンを合成 ← **Y の向きの判定**

Vulkan が interop 色に<b>非対称な模様</b>を描き、GL が合成する。

> ⚠ **単色フルスクリーンでは Y の向きを検証できない。** 上下反転に無反応だから。
> 「打ち消し合う変換を最初に潰す」ために、**最初から非対称な模様**を使う:
> 画面の<b>上 1/4 だけ赤</b>、<b>左上に小さな四角</b>、のように
> 上下と左右の両方が区別できるもの。

| 確認できること |
|---|
| 合成が MC の画面に出る (位置・サイズ) |
| **Y の向き** — 赤帯が上に出るか |
| **X の向き** — 四角が左に出るか (ついでに確認できる) |

**この段の判定は目視でしかできない**が、それでよい —
機械的検査は反転の打ち消しに弱く、5b で実際に素通りした。

### 5c-1c — MC の深度を Vulkan に渡して可視化 ← **もう 1 つの Y 判定**

MC の深度を interop 経由で Vulkan に渡し、<b>Vulkan がそれを色に変換して</b>返す。

| 確認できること |
|---|
| 深度が届いている (MC の地形の形が見える) |
| **深度側の経路の Y の向き** (5c-1b とは別経路) |
| 深度の値域・向き (手前が明るいか) |

**5c-1b と独立した 2 つ目の向き検査であることが重要。**
色と深度で別々に確かめるので、<b>片方の反転をもう片方が打ち消す</b>ことが起きない。

### 5c-1d — 合成地形を描く

Phase 4 の合成地形を実際に Vulkan で描いて合成する。

| 確認できること |
|---|
| `interopCompositeCheck` と同じ絵が MC の画面に出る |
| MC の MVP で描いても破綻しない (座標系・スケール) |

### 5c-1e — MC 地形との前後関係

Voxy の LoD が<b>近景の MC 地形に隠れる</b>こと。

| 確認できること |
|---|
| 深度テストが効いている |
| `initDepthStencil` 相当の NEAR/FAR 化が正しい |

**対照**: MC 地形の<b>手前</b>と<b>奥</b>に同じ合成地形を置き、
奥のものだけが隠れること。**「全部隠れる」「全部出る」はどちらも失敗**である。
片側だけ試すと、この 2 つの失敗を見分けられない。
