## 1. なぜ 2 か所なのか — 片側では対照にならない

5c-1d で「合成地形が MC の地形に隠される」ことは確認できた。
しかし<b>それだけでは深度テストが効いている証拠にならない</b>:

| 観察 | ありうる説明 |
|---|---|
| 奥のものが隠れた | ✅ 深度テストが効いている / ❌ <b>全部隠れている</b> (描けていない・捨てられている) |
| 手前のものが出た | ✅ 深度テストが効いている / ❌ <b>全部出ている</b> (テストが効いていない) |

**手前が出ていて、同時に奥が隠れている**ことを見て初めて、
2 つの失敗 (全部隠れる / 全部出る) の<b>どちらでもない</b>と言える。
7 例目 (遮蔽を外したらフレームアウトしていた) から一貫して守ってきた設計である。

```
カメラ ──── 手前の組 (64b) ──── [MC の丘] ──── 奥の組 (160b, 横に 64b ずらす)
              ↑ 出るはず                          ↑ 隠れるはず
```

## 2. 実装 — 位置だけで表す

**描画パスもシェーダも増やさない。** 頂点位置は
{@code (getLoDPosition(sPos) << lodLevel) - baseSectionPos} で解かれるので、
<b>セクション位置を絶対座標で書けば、1 つのユニフォームで 2 か所を表せる</b>。

| 追加したもの | 役割 |
|---|---|
| `SyntheticTerrain.duplicated()` | 同じセクションを 2 組持つデータセット (前半 = 手前、後半 = 奥) |
| `SyntheticTerrain.writePositionsPerSection` | セクションごとに別々のアンカーで位置を書く |
| `VkHostViewport.verifiedForward` | <b>投影で確かめた</b>視線方向を返す (§3.1) |
| `VkHostViewport.anchorAlongDirection` | 指定方向 + 直交方向へずらしたアンカー |
| `VkInteropProbe` の `PAIR` モード | 既定。2 組の配置と診断 |

ユニフォームの {@code baseSectionPos} は<b>手前のアンカー</b>である
(位置は絶対座標なので、原点はどちらでもよい)。

## 3. ⚠ 配置で踏んだ 3 つの罠 — <b>全部 JUnit が先に捕まえた</b>

MC を起動する前に、`VkHostViewportTest` が 3 回落ちた。
どれも<b>実機では「奥が見えない」という同じ症状</b>になり、
遮蔽と区別が付かなかったはずのものである。

### 3.1 量子化されたアンカーから方向を逆算していた

奥の組の方向を<b>手前のアンカーから引いて</b>いた。アンカーは 1〜2 セクション単位に
丸められているので、近い距離では<b>方向が最大数十度ずれる</b>。
横に 96 ブロックのつもりが<b>200 ブロック以上</b>ずれ、奥の組が画面外に出た。

> **修正**: {@link VkHostViewport#verifiedForward} が
> <b>投影で確かめた向きをそのまま返す</b>。逆算しない。

### 3.2 量子化が距離差を潰した

アンカーの丸めを {@code 1 << maxLevel} (= 2 セクション = 64 ブロック) にしていたため、
<b>32 / 144 ブロックのつもりが 82 / 106 になった</b>。

> **修正**: 5c-1e の配置は<b>量子 1 セクション</b>にする。
> LoD 1 のセクションが 1 つだけ最大 1 セクションずれるが、
> <b>この段で見たいのは前後関係</b>であって配置の精度ではない。

### 3.3 手前が近すぎて画面から外れた

手前を 32 ブロックにすると、丸めで 10 ブロックまで寄ることがあり、
<b>カメラとの高さの差 (7 ブロック) が 36° を占めて</b>画面外に出た。

> **修正**: 手前 64 / 奥 160 ブロック。丸めの最悪値を入れても
> 距離差が 50 ブロック以上残り、どちらも画面に入る。

## 4. ⚠⚠ この対照を空虚にする最大の要因 — <b>far 平面</b>

**奥の組が MC の far 平面の外に出ると、隠れる理由が「遮蔽」ではなく「切り落とし」になる。**
見た目は同じなので、<b>気づかずに「遮蔽が効いた」と読んでしまう</b>。

JUnit でも実際に踏んだ (奥 192 ブロック・far 平面 192 で {@code z = -1.5e-6})。

**実行時にも見張る**: 奥の組の中心が視錐台の外にいたら警告を出す。

```
[5c-1e] the FAR copy is outside the frustum (probably beyond Minecraft's far plane
        at this render distance). It would be hidden by CLIPPING, not by occlusion
        — the control is vacuous. Lower it with -Pvoxy5c1eFar=<blocks>
```

既定 (奥 160 ブロック) は<b>描画距離 12 チャンク (192 ブロック) でぎりぎり収まる</b>。
警告が出たら描画距離を上げるか、距離を詰めること。

## 6. 自動検査 — 何が言えて、何が言えないか

`thePairSitsAtTwoDifferentDistances` (JUnit、GL 不要) が 24 方位で要求する:

| 主張 | 使う量 |
|---|---|
| 2 組とも<b>カメラの前</b>にある | {@code w > 0} |
| 2 組とも<b>画面に入る</b> | {@code x/w}, {@code y/w} |
| 奥の組が<b>本当に遠い</b> (50 ブロック以上) | {@code w} の差 |

> **{@code w} で比べているのが要点である。**
> {@code w} は<b>カメラからの距離そのもの</b>で、深度の規約
> (逆Zか、0..1 か -1..1 か) に<b>一切依存しない</b>。
> 5c-1d で規約の思い込みを 2 回踏んだので、ここは規約に依存しない量だけで主張する
> [規約 4 / 9]。

**言えないこと**: <b>MC の地形が実際に奥の組を隠すか</b>。
それはワールドの中身に依存するので、目視でしか確かめられない。
自動検査が保証するのは<b>「隠れなかったら、それは配置のせいではない」</b>ところまでである。

## 7. ⚠ 実機で JVM ごと落ちた — <b>診断コードのサイズ依存資源</b> (失敗例 18)

初回の実機確認で <b>SIGSEGV (JVM の abort)</b>。落ちたのは<b>この調査のために足した診断コード</b>だった:

```
Problematic frame:
J  me.cortex.voxy.client.core.vk.interop.VkInteropProbe.screenFootprint()
```

### 7.1 原因

`screenFootprint` の読み戻しバッファを<b>最初に呼ばれたときのサイズで 1 度だけ</b>確保し、
{@code freeSizeDependent()} にも入れていなかった。ログのとおり
<b>frame 0 の直後にウィンドウが 1708x960 → 4112x2580 にリサイズ</b>され、
<b>6.5MB のバッファを 42MB 読んだ</b>。

> ⚠ **リサイズしたときにだけ壊れる。** 起動して眺めるだけの確認では出ない。
> しかも壊れ方が<b>範囲外読み</b>なので、運が良ければ黙って動き続ける。

### 7.2 直し方 — <b>二重に</b>防ぐ

| 直し | 効き方 |
|---|---|
| {@code freeSizeDependent()} に入れる | 本来の置き場所。<b>リサイズで作り直される</b> |
| 使う直前に<b>大きさを確かめて足りなければ作り直す</b> | 置き忘れても<b>範囲外読みにはならない</b> |

2 つ目が要点である。1 つ目だけだと<b>次に誰かが資源を足したときに同じ穴が開く</b>。

### 7.3 運用に足す規則

> **【規約 12】画面サイズに依存する資源は<b>1 か所で解放し、使う直前に大きさを確かめる</b>。**
> 入れ忘れは<b>リサイズしたときにだけ</b>現れるので、通常の確認を素通りする。
> 「解放漏れを防ぐ」だけでなく「漏れても壊れない」形にしておく。

> 5c-1a で {@code TrackedObject} の未解放検出を入れたのは<b>解放漏れ</b>のためだった。
> 今回は<b>解放漏れが実害 (範囲外アクセス) に変わる</b>型で、検出器の対象外だった。
