## 1. 2 段に割る — <b>1 変数ずつ</b>

5c-3 には<b>独立した 2 つの未知</b>がある。まとめて入れると切り分けられない。

| 段 | 変える 1 変数 | ジオメトリ | 投影 |
|---|---|---|---|
| **5c-3a** | <b>投影空間</b> | 合成 (既知の対照) | **Voxy 自前 + 深度再投影** |
| **5c-3b** | <b>ジオメトリの出どころ</b> | **実データ** (`RenderDataFactory`) | 3a で確定済み |

⚠ **5c-3b は LoD 0 固定である。** 見たいのは
「実ジオメトリが正しくメッシュ化されて描かれるか」であって LoD の切り替えではない。

> **したがって 5c-3b は Voxy の本質 (遠景を粗く描く) を一度も通らない。**
> <b>粗い LoD が初めて効くのは 5c-4 (HiZ + traversal)</b> である —
> あそこで階層トラバーサルが「どの LoD をどこまで出すか」を決める。
> それまでは<b>「近くを細かく描けている」以上のことは言えない</b>。

**3a が先なのは、合成地形が「既に正しいと分かっている対照」だからである。**
投影を変えて絵が壊れたら、原因は投影しかない。
逆順にすると「ジオメトリが悪いのか投影が悪いのか」が分からなくなる。

## 2. 5c-3a — 投影空間

### 2.1 何が問題なのか

5c-1d 以降は<b>MC の投影で描いて</b>回避してきた。深度が最初から MC と同じ空間にあるので、
合成がそのまま成立する。**しかしこれでは MC の far 平面より先が描けない。**
遠景 LoD は定義上そこにある。

本番の Voxy は near=16 / far=48000 の<b>自前の投影</b>で描き、
書き戻すときに深度を MC の空間へ<b>再投影</b>する
[確認済 — `AbstractRenderPipeline.transformBlitDepth` + `post/blit_texture_depth_cutout.frag`]。

### 2.2 ⚠ 変わるのは<b>深度だけ</b>である

`VoxyRenderSystem.computeProjectionMat` は MC の投影行列の
<b>m22 / m32 だけを書き換える</b>。行 0・1・3 は触らない。したがって:

```
x_clip, y_clip, w_clip は不変  →  x_ndc, y_ndc も不変
z_clip だけが変わる            →  深度だけが変わる
```

**これが「深度だけを画素ごとに変換すれば合成できる」ことの根拠である。**
色は同じ画面位置に出るので、色のブリットは素通しでよい。

> この不変条件は<b>ヘッドレスで検査できる</b> [規約 8]。
> 任意の点について xy が一致し z だけが違うこと — <b>式を再実行するのではなく性質</b>を主張する [規約 4]。

> ⚠⚠ **この性質には裏がある。** 横位置が深度に効かないということは、
> <b>横位置の誤りが深度に出ない</b>ということでもある。
> 画面座標 → NDC の写像がずれていても、<b>深度を比べる検査は全て素通しする</b>
> [失敗例 24 — 実測]。見張るには<b>深度が横位置に依存する投影</b>を写し先に使うしかない (C16c)。

### 2.3 逆Z・0..1 の投影 (導出)

`near=16, far=48000` を逆Zで入れ替え (`near'=48000, far'=16`)、0..1 の式を使う:

```
m22 = far'/(near'-far')       = 16/47984      = 3.334e-4
m32 = far'*near'/(near'-far') = 16*48000/47984 = 16.005
z_ndc = (m22*(-d) + m32)/d = -m22 + m32/d
```

| 距離 d | z_ndc | |
|---|---|---|
| 16 | 0.99998 | ≈ NEAR ✅ |
| 48000 | 0.0 | = FAR ✅ |

**MC の投影と違って 0..1 に収まる**ので、5c-1d で要った `halveDepthRange` は
<b>この経路では不要</b>になる。行を自分で書くからである。

### 2.4 再投影を<b>どこで</b>やるか — GL 版と違える判断

| | GL 版 | ここ |
|---|---|---|
| 実行場所 | GL のブリット (`transformBlitDepth`) | **Vulkan の `VkDepthResolve`** |
| 理由 | — | ①GL 側は 4.1 制約で脆い ②`VkDepth.defines()` の機構が Vulkan 側にある ③既存パスに 2 つ行列を足すだけで済む |

**式は同じで、実行する段だけが違う。** 参照仕様からの逸脱として記録する。

### 2.5 ⚠ `CLOSER_SIGN` は手で反転しない — <b>define 漏れが本当の危険</b>

`CLOSER_SIGN` は `depthutils.glsl` のマクロで、`USE_REVERSE_Z` の有無で
`+1.0` / `-1.0` が切り替わる。GL 版もこのフォークでは逆Zなので<b>符号は一致する</b>。

⚠ **危険は「`VkDepth.defines()` を呼び忘れる」ことである。**
呼び忘れると非逆Z側の分岐に落ち、`CLOSER_SIGN` が黙って `-1.0` になり、
clamp が<b>手前ではなく奥へ押しやる</b>。落ちないし、絵は「遠景が MC の地形に負ける」形でしか出ない。

**対照**: 再投影シェーダに定義が入っていることを検査で見張る。

### 2.6 ⚠ clamp の ε は 24bit 固定小数の値である

```glsl
depth = REDUCTION2(FAR + CLOSER_SIGN*(2.0/((1<<24)-1)), depth);   // ε = 1.19e-7
```

MC の深度は **D32_FLOAT** なので、float の ulp から見ると ε は桁違いに大きい。
安全側だが、数字を出しておく (逆Z, near=0.05):

| | z/w |
|---|---|
| MC の地形 (512 ブロック) | 9.8e-5 |
| Voxy の遠景 (10000 ブロック) | 5.0e-6 |
| **ε** | **1.19e-7** |

ε は MC の地形より<b>2 桁下</b>なので、clamp が MC の地形に勝つことはない。
代わりに <b>ε より遠いもの同士は深度で並べられない</b> (同じ値に潰れる)。GL 版でも同じ。

### 2.7 対照 — <b>3 つ目の組を MC の far 平面の外に置く</b>

5c-1e の near/far ペアに<b>もう 1 組</b>足す。

| | MC の投影 (現状) | Voxy の投影 + 再投影 |
|---|---|---|
| 手前の組 (64b) | 出る | **出る**、前後関係も変わらない |
| 中の組 (160b) | 丘に隠れる | **丘に隠れる** (変わらない) |
| **外の組 (far 平面の外)** | **出ない** (クリップ) | **出る** |

> **「全部出る」「全部出ない」はどちらも失敗である** — 5c-1e と同じ形。
> <b>差が出ることそのもの</b>が主張であり、片側だけでは何も言えない。

## 3. 5c-3b の対照 — <b>規約 1 が「保証」から「要求」に変わる</b>

合成データは<b>各 quad が別々の可視位置を占める</b>ことを構造で保証していた。
実ジオメトリでは位置が実データになるので、**その保証は失われる**。

### 3.1 失われるのは<b>位置だけ</b>である — モデルの側は取り戻せる

5c-2b で<b>合成色 (`fillModels`) と実モデルを切り替えられる</b>ようにしてある。
これをそのまま対照に使う:

| 段 | ジオメトリ | モデル | 索引のずれは |
|---|---|---|---|
| 5c-3b の検査中 | **実** | **合成色** | <b>色に出る</b> (規約 1 の性質を保持) |
| 5c-3b の仕上げ | **実** | **実** | 絵として確認するだけ |

> **5c-2b で作った分岐点が、そのまま 5c-3 の対照になる。**
> 狙って作ったものではないが、<b>境界を切ったことの副産物</b>である。

### 3.2 位置について代わりに何を主張するか

| 主張 | 期待値の出どころ | 規約 4 |
|---|---|---|
| prefix が単調・末尾が総数 | 定義 | ✅ 描画経路を通らない |
| (quad, セクション) に重複が無い | メッシャの性質 | ✅ |
| **stateId < モデル数** | 範囲外読み。バリデーションは捕まえない | ✅ |
| **既知の座標のブロックが、予測した画素に出る** | ワールド座標 + `VkHostViewport` | ✅ <b>期待値が描画経路を通らない</b> |

### 3.3 ⚠ 「変わらなかったら正しい」が言えなくなる

合成データでは「絵が変わらない = 索引が合っている」が成立していた。
実データでは<b>変わらない絵が正しいとは限らない</b> (もっともらしいが違う絵がある)。

> **したがって、検査を書いたら必ず<b>変異を入れて落ちることを確かめる</b>。**
> 失敗例 19 (共有ヘルパが打ち消しの経路を作った) と同じ手を、
> <b>今回は最初から</b>回す。

## 5. ⚠⚠ 失敗例 24 — <b>対照が変異を素通しした</b> (規約 4 の一族)

再投影パスを書いたとき、次のように考えた:

> 「往復 (`src == dst`) が恒等になることを確かめれば、
>  画面座標 → NDC の写像 (Y の向き) も同時に見張れる」

**これは誤りだった。** `uv` の Y を反転する変異を入れても:

| 検査 | 変異あり |
|---|---|
| C16 覆う画素が同じ | PASS |
| C16b 写し先で描いたものと一致 | **PASS** ← 素通り |
| C16 往復が恒等 | **PASS** ← 素通り |

### 5.1 なぜ捕まらないのか

`(ndc_x, ndc_y, depth)` から `inv(MVP)` で復元した点は、
xy を変えると<b>同じ深度平面の上を横に動くだけ</b>で、**視空間の z は変わらない**。
写し先が<b>同じ視点の標準的な透視投影</b>なら、深度は視空間の z だけで決まる。

> **深度だけを比べる検査は、横位置の誤りを<b>原理的に</b>検出できない。**
> 「たまたま通った」のではなく<b>構造的に通る</b>。

### 5.2 塞ぎ方 — <b>深度が横位置に依存する投影</b>

写し先の投影の<b>深度の行に横位置を混ぜる</b> (斜め投影):

```java
shearedProj[2] =  0.002f;   // clip.z += 0.002 * view.x
shearedProj[6] = -0.0015f;  // clip.z -= 0.0015 * view.y
```

x/y の行は触らないので<b>覆う画素は変わらず</b>、比較は成立したままである。
これで両方の変異が落ちる:

| 変異 | C16c |
|---|---|
| `uv` の Y を反転 | **FAIL** (差 5.11e-4) ✅ |
| `SCREEN2NDC` を掛け忘れる | **FAIL** (差 5.20e-4) ✅ |

### 5.3 得られた規約

> **【規約 17】「A を確かめれば B も見張れる」と思ったら、<b>B を壊して確かめる</b>。**
> 規約 4 は「予測と実装が同じ式を参照していないか」を問うものだったが、
> こちらは<b>そもそも出力に現れない誤り</b>である。
> <b>検査の出力が、見張りたい入力に依存しているか</b>を先に問う。
>
> ⚠ 今回は<b>変異を入れる習慣があったから見つかった</b>。
> 数値が 1 桁まで同一だったことが手がかりで、
> 最初は「シェーダが再コンパイルされていない」と疑った (それも確かめた上で否定した)。

## 7. 5c-3a 実機 — <b>数字では通った。目視はできない</b>

| | 描画コマンド | `drawn=` | 深度 |
|---|---|---|---|
| `off` (MC の投影) | 13 / 39 | **全フレーム 0** | — |
| `on` (自前 + 再投影) | 13 / 39 (**同一**) | **1〜12** | `1.192093E-7` と `1.2331092E-5` |

置き場所も描画コマンドも同一で、<b>投影だけが違う</b>。差は出た。

- `1.192093E-7` は **ε = 2/(2²⁴−1) にぴったり一致**する。
  MC の far 平面の外にあるものが設計どおり「ぎりぎり手前」に留め置かれている
- `1.2331092E-5` は <b>clamp されていない自然な値</b>。
  **clamp が一律に効いているのではない**ことの証拠である
  (全部が ε なら「再投影が定数を返している」と区別が付かない)

### 7.1 ⚠ 目視を求めたのが誤りだった

3 組は<b>同じ地形</b>なので、画面のどの塊がどれかは目で区別できない。
さらに MC の far 平面が **2046 ブロック**なので、その外に置いた組は
4092 ブロック先 = <b>1 ブロックあたり約 0.7 画素</b>で、疎な合成地形では
**12 画素**にしかならなかった。

> **見えないのは壊れているからではなく、<b>予測できたはずの大きさ</b>だったからである。**
> 見る前に大きさを見積もっていれば、目視を求めずに済んだ。

**対処**: アンカーのログに<b>見かけの大きさ (画素) を先に出す</b>ようにした。
200 画素を切る場合は「小さすぎて見えない。描画距離を下げよ」と明示する。

### 7.2 ⚠ `drawn=0` に意味が 2 通りあった

`on` でも 15 フレームが 0 だった。これは<b>そちらを向いていなかった</b>だけだが、
「描けていない」と区別が付かない。**対照の答えが 0 か否かなのに、0 の意味が 2 通りある。**

**対処**: 外の組の中心が<b>いま画面に入る位置にあるか</b>を同じ行に出すようにした。

```
voxy footprint: drawn=0 ... [the BEYOND copy's centre is ON screen — drawn=0 here means it was NOT drawn]
voxy footprint: drawn=0 ... [... is OFF screen — drawn=0 here says nothing, turn to face it]
```

> **【規約 18】対照の答えが「0 か否か」なら、<b>0 の意味が 1 通りであることを先に保証する</b>。**
> 「見えなかった」「出なかった」は<b>複数の原因の合流点</b>である。
> 合流したままでは、通っても落ちても何も言えない。

## 8. 5c-3b の下準備 — <b>不変条件を先に立て、変異で確かめた</b>

実データを流す<b>前</b>に検査を書き、<b>壊して落ちること</b>を確かめた。
規約 4 で 4 回、規約 17 で 1 回、検査が変異を素通しているので、
「通った」を証拠にしない。

### 8.1 実データの経路 — <b>5c-2b と同じ形</b>

```
WorldSection --(RenderDataFactory.generateMesh)--> BuiltSection --(IGeometryManager)--> GPU
                     ↑ CPU で完結・GL 非依存           ↑ 既にインタフェース
```

| | |
|---|---|
| `BuiltSection` | `MemoryBuffer geometryBuffer` + `int[8] offsets` + `occupancy`。**GL 依存なし** |
| `IGeometryManager` | **最初から境界になっている**。5c-2b で作った `ModelUploadTarget` に当たるものが既にある |
| ⚠ `RenderGenerationService` | コンストラクタが **`ModelBakerySubsystem` を要求する** = `ModelStore` = DSA 地雷 5 つ目 |

> **5c-2b とまったく同じ罠である。** 使うのは `RenderDataFactory` を<b>直に</b>。
> サービスが `modelBakery` に使っているのは 2 つだけ [確認済] —
> `modelBakery.factory` と `requestBlockBake`。どちらも代替できる。

**形式も一致している**: 実データの `offsets[8]` と合成地形の書き出し順は
どちらも <b>translucent → double-sided → 面 0..5</b>、quad は 8 バイト。

### 8.2 `VkGeometryInvariants` — <b>生産者に依存しない</b>

できあがったバッファの中身<b>だけ</b>を見る。主張:

| 主張 | 期待値の出どころ |
|---|---|
| バケツの起点が 0 始まり・単調非減少・総数以内 | **バッファの大きさ** (足し直さない) |
| 1 回の描画に収まる (超えるなら分割が要る) | 索引バッファの容量 |
| **stateId < モデル数** | モデルバッファの大きさ。⚠ バリデーションは捕まえない |
| 同一 quad がセクション内に 2 枚ない | — |
| prefix が 0 始まり・単調・末尾が総数 | **実際に書いた quad 数** |
| 二分探索が空スロットに着地しない | 線形探索で<b>別に書いた</b> |

> ⚠ **末尾の照合に面マスクを使わない。** 既存の `MergedTableTest` は
> `SyntheticTerrain.faceMask` を<b>生産と検査の両方で</b>引いている。
> マスクが壊れれば<b>両方が同じだけ壊れて一致する</b> — 失敗例 19 と同じ型である。
> こちらは総数をバッファの大きさから取る。
>
> ⚠ **二分探索も別に書いた。** 同じ実装を呼ぶと、探索が壊れていても検査が一緒に壊れる。
> 線形探索なので遅いが、<b>検査の側が単純であること</b>のほうが重要である。

### 8.3 変異で確かめた

| 検査側に入れた変異 | 落ちた検査 |
|---|---|
| stateId の範囲検査を消す | `aStateIdPastTheModelBufferIsCaught` ✅ |
| prefix の単調性検査を消す | `aPrefixThatRunsBackwardsIsCaught` ✅ |
| 重複検査を消す | `duplicateQuadsWithinASectionAreCaught` ✅ |
| **stateId のシフト 26→25** | 2 件 ✅ |
| **posX のシフト 21→20** | 1 件 ✅ |
| **biomeId のシフト 46→45** | 1 件 ✅ |
| **lightId のシフト 55→54** | 1 件 ✅ |
| **sizeX のシフト 3→4** | ⚠ **0 件 — 素通り** |

### 8.4 ⚠ 固定できない値は<b>置かない</b>

`sizeX` / `sizeY` の変異が素通りしたのは、
<b>合成地形が全 quad 1x1 で、大きさのビットが全部 0</b> だからである。
シフトをずらしても 0 を読むだけで結果が変わらない。

**外した。** 固定できていない値を公開すると、
後から誰かが<b>確かめられていない前提</b>の上に書く。

> **【規約 19】検査で固定できない値は<b>公開しない</b>。**
> 「いま使っていないから害はない」ではない —
> <b>使われた瞬間に、確かめていない前提が正しさの根拠になる</b>。
>
> ⚠ これは<b>データセットの性質</b>から来る限界である。
> 実ジオメトリは貪欲メッシュで大きさが変わるので、そこで初めて固定できる。
> 逆に実データで「全部 1x1」なら<b>併合が効いていない</b>という信号になる。

### 8.5 ⚠ 正常系はビット配置を固定しない

`healthySyntheticGeometryReportsNothing` は、シフトを 26→25 にずらしても<b>通った</b>。
「正しいデータで問題が出ない」は<b>読み取り位置を何も主張していない</b>。

`everyQuadFieldIsDecodedAtTheRightBits` を足して、
生産側が<b>何を書くと決めているか</b>から全項目を釘付けにした
(stateId は写像で 0x1234 に固定、位置はセクション内通し番号、
biomeId はセクション番号、lightId は 0xF0)。

## 9. 5c-3b の配線

### 9.1 ⚠ 規約 16 の数え上げ — <b>`ModelBakerySubsystem` の public を 1 つずつ</b>

5c-2b で `addBiome` を落として草と葉が黒くなった。今回は<b>先に数えた</b>。

| member | 中身 | 迂回してどうしたか |
|---|---|---|
| `factory` | `ModelFactory` | 自分で作る [5c-2b] |
| **コンストラクタ** | **`ModelStore` を作る** + 処理スレッド | ⚠ <b>地雷。作らせない</b> |
| `tick` | `factory.processUploads()` | 自分で呼ぶ |
| `shutdown` | スレッド停止 + free | `VkRealModelBakery.free` |
| **`requestBlockBake`** | 出会ったブロックのモデルを焼かせる | ⚠ <b>要る</b>。`ensureModels` を新設 |
| **`addBiome`** | バイオーム色 | ⚠ <b>5c-2b で落とした</b>。配線済み + `replayBiomes` |
| `addDebugData` / `getStore` / `areQueuesEmpty` / `getProcessingCount` | — | 要らない |

**9 つ中 2 つが「落ちると壊れる」ものだった。**
`requestBlockBake` を落とせば `IdNotYetComputedException` で止まっていた。

> **数えたから見つかった。** 前回は数えずに「2 つだけと分かっている」と書いて、
> <b>実際には見落としていた</b> (それが 9.2 の 2 件目)。

### 9.2 ⚠⚠ 迂回で落ちるものが<b>もう 2 つ</b>あった

**① ワールドの `Mapper` を借りなければならない。**
`WorldSection` の中身は<b>ワールドの `Mapper` が採番した</b>
ブロック状態 id とバイオーム id である。
`VkRealModelBakery` が新しい `Mapper` を作ると<b>全部が別のブロックを指す</b>。

> **落ちない。絵も出る。** 「地形が描かれている」ようには見えるので気付きにくい。
> `VkRealModelBakery(target, world.getMapper())` を足した。<b>借りた Mapper は閉じない。</b>

**② `setBiomeCallback` だけでは足りない。**
コールバックは<b>これから登録されるもの</b>しか拾わない。
ワールドは取り込み時に<b>既に</b>バイオームを登録しているので、そのぶんは永久に届かない。

> 症状は 5c-2b の「草と葉が黒い」と<b>同じ</b>だが原因は別である。
> `replayBiomes()` で `mapper.getBiomeEntries()` を流し込む。
> ⚠ <b>モデルより後に呼ぶこと</b> — `addBiome0` は色が要るモデルが無いと何もせず返す [5c-2b §9.4]。

### 9.3 ⚠ 位置のエンコードが 2 種類ある (失敗例を先回りで潰した)

```
WorldEngine.getWorldSectionId : lvl<<60 | y<<52 | z<<28 | x<<4     ← BuiltSection.position
SyntheticTerrain.packPosition : pos_util.glsl の配置              ← GPU が読む
```

**別物である。** そのまま書くと位置が滅茶苦茶になるが、<b>落ちないし絵も出る</b>。
`VkRealPositionTest` が往復を固定し、
<b>「詰め直しを忘れる」誤りを検査が捕まえられること</b>も同時に主張している
(2 つの形式が実際に違うことの対照つき)。

### 9.4 面方向マスクを<b>掛けない</b>

合成側は `faceMask` で裏を向いた面を落としている。実データでは掛けない。

> あれは<b>最適化であって正しさではない</b>。掛けると 5c-3b が
> 「実ジオメトリ」と「マスクの正しさ」の<b>2 変数</b>になる。
> 全部描けば無駄はあるが絵は正しい。マスクは本番では `cmdgen` の仕事で、5c-4 で入る。

### 9.5 色は<b>合成のまま</b> — 規約 1 を保つ

| | ジオメトリ | モデルの面情報 | 色 |
|---|---|---|---|
| 5c-3b (既定) | **実** | **実** | <b>合成アトラス (id 由来)</b> |
| `-Pvoxy5c3bRealColours=true` | 実 | 実 | 実テクスチャ |

モデルは<b>実物を焼く</b> (メッシュ化に metadata が要る) が、
<b>アトラスだけ合成の id 由来の色にする</b>。
これで「索引がずれたら色が変わる」性質が保たれる。

> **規約 1 の崩れは 5c-3b では表面化しない。**
> 位置は実データになるが、色が索引由来なので取り違えは見える。
> <b>5c-3c (実色) で初めて問題になる</b> — そこの対照は別途考える。

### 9.6 貪欲メッシュが効いているかを数える

規約 19 を書いたときの副産物: <b>合成地形は全 quad が 1x1</b> だった。
実データでも全部 1x1 なら<b>併合が働いていない</b>。落ちないし絵も出る。

```
[5c-3b] greedy merging: N of M quads cover more than one block
        ⚠ NOTHING merged — the mesher is emitting 1x1 quads only
```

<b>ここで初めて `sizeX`/`sizeY` が固定できる</b> (規約 19 で外した値)。

## 10. 5c-3b 実機 — <b>実データの地形が出た</b>

```
meshed 291 sections around [0,4,-1] r=4 (LoD 0): 438 empty, 0 not in the world yet, 0 gave up,
                                                 287 models baked on demand
replayed 11 biomes already registered by the world
uploaded 291 sections, 521691 quads, 1999 draws  (colours=REAL textures)
the real geometry satisfies every invariant across 291 sections
greedy merging: 149165 of 521691 quads cover more than one block (823144 faces in 521691 quads)
```

**シルエットが周囲の MC の地形と一致した** — 丘の稜線・木・崖。
不変条件は全部成立、貪欲メッシュも効いている (1 quad あたり 1.58 面)。

> ⚠ ここで初めて `sizeX`/`sizeY` に意味のある値が入った (規約 19 で外した値)。
> <b>「外したから、外したことが検査になった」</b>形である。

### 10.1 ⚠ 1 回目の絵が壊れた原因 2 つ — <b>どちらも配線</b>

**① アトラスを毎フレーム二重に書いていた。**
合成アトラスの転送 (`uploadAtlas`) と焼いた実タイルの転送 (`recordUploads`) が
<b>両方</b>走り、互いに上書きしていた。
症状は「青紫の斑に実物の葉と土が混じる」。**出どころを 1 つに決めた。**

**② 合成色は目で読めない配色だった。**

```java
R = modelId & 0xFF;  G = (modelId >> 8) & 0xFF;  B = face * 40 + 15;
```

実データのモデル id は 200 前後なので <b>G が常に 0</b> — <b>青紫にしかならない</b>。
あの配色は<b>オフスクリーンの検査が `atlasTexel` と突き合わせるため</b>のもので、
人が見るためのものではない。

> **「実ジオメトリ + 合成色」という計画を、<b>その色が何色になるかを確かめずに</b>立てていた。**
> 5c-3a で「見かけの大きさを見積もらずに目視を求めた」のと<b>同じ型</b>である
> (§7.1)。<b>見る前に、何が見えるはずかを計算する。</b>

### 10.2 ⚠ ちらつきは欠陥ではない

半径 4 の LoD 0 は<b>MC 自身が描いている場所</b>である。
同じ面が同じ深度で争うので当然ちらつく。
本番の Voxy は MC の描画距離の<b>外</b>しか描かない。
`-Pvoxy5c3bOnly=true` で深度を見ずに合成すれば Voxy の絵だけを見られる。

### 10.3 ⚠⚠ 規約 1 は<b>実データで本当に弱まった</b>

```
57 indistinguishable pairs among 242 baked models
```

58 モデル (24%) が他と<b>見分けが付かない</b>。25 グループ、最大は 8 個。
model 0 (空気) と model 45 も同一だった。

> **予測どおりだが、<b>予測より大きい</b>。** 5c-2b §6.3 で
> 「モデルのずれが絵に出る性質は弱まる」と書いたときは、
> 8 個の手選びのブロックで<b>0 組</b>だった。実データでは 4 分の 1 が該当する。
>
> **意味**: その 58 個については、<b>取り違えても絵が変わらない</b>。
> 目視はそれらを区別しない。<b>id で見る不変条件のほうは効いたまま</b>である。

**報告を作り直した。** 57 行の警告は読めないし、判断もできない:

| 区別 | 意味 |
|---|---|
| **BLANK なタイル** (全バイト 0) | ⚠ <b>焼き損なっている = 欠陥</b> |
| 中身はあるが同一 | ブロック状態の性質 (見た目に効かない property の違い) |

一緒くたにすると<b>本当の欠陥が 57 行のノイズに埋まる</b>。
グループごとに<b>どのブロックが衝突しているか</b>も出すようにした —
名前が出なければ判断できない。

> **【規約 20】警告は<b>判断できる形</b>で出す。**
> 「57 件あります」は情報ではない。
> <b>欠陥と仕様を分け、どちらなのかを判断できる材料を同じ行に置く。</b>
