# Phase 6 第一項目 — <b>選択集合がカメラ静止でも変わる</b>

**状態**: 候補を絞り、分ける数字を用意した。実機の測定待ち。

---

## 1. 観測 (Phase 5 完了時点)

```
the SELECTED SET changed: 42 / 60,  49 / 60     (カメラ静止、1920x1200)
```

**カメラを止めても、選ばれるセクションの集合が 7〜8 割のフレームで変わる。**

これが揺れ (中央値 0.7%、最大 8〜10% の画素) の主因である。
半透明のバケットはこれに追随しているだけで、**半透明は原因ではない**。

> ⚠ **他の最適化より先にこれを調べる。** 主因が動いている間は、
> 他の項目を測っても<b>数字がぶれる</b>。

---

## 2. ⚠ 候補を先に絞った — <b>コードで 3 つ消えた</b>

規約 22 に従い、測る前に候補を列挙して、**コードで消せるものを消した**。

| 候補 | 判定 | 根拠 |
|---|---|---|
| **カルパスの帰還** | ❌ <b>構造的に不可能</b> | {@code indirectLookup} を書くのは<b>トラバーサルだけ</b>。cull は {@code visibility[]} しか書かない [確認済 — `cull_raster.frag` / `traversal_dev.comp`] |
| **前フレーム描画による抑制** | ❌ 不可能 | {@code lastRenderFrame[getId(node)] = frameId} は<b>書くだけ</b>で、選択を止める読みが無い [確認済 — `enqueueSelfForRender`] |
| **視錐台** | ❌ 不可能 | カメラ静止なら MVP は同一。測定側で<b>MVP が前サンプルと一致するフレームだけ</b>を集計している |

**残るのは 3 つ**:

| # | 候補 | 中身 |
|---|---|---|
| **D** | <b>木が育っている</b> | メッシュ化が進んでノードが増えれば、選択が変わるのは<b>当たり前</b> |
| **A** | <b>HiZ の遮蔽</b> | 選択 → 不透明の深度 → HiZ → 次の選択、の帰還で振動する |
| **B** | <b>降下の閾値</b> | {@code minScreenSize} にヒステリシスが無く、親と子が往復する |

---

## 3. 分ける数字

### 3.1 D は「メッシュ化数が増えていない」で外す

⚠ **外さずに数えると、木が育っているだけの変化を「揺れ」と呼ぶことになる。**
Phase 5 の測定 (42/60) は<b>これを外していない</b> — meshed が 3447 → 4417 と
増え続けていた。**あの 7〜8 割という数字自体、上振れしている可能性がある。**

### 3.2 ⚠⚠ A と B は <b>LoD 別ヒストグラム</b>で分ける

**集合の変化だけを数えても A と B は区別できない。** どちらも
「集合が変わった」としか見えない [規約 22]。

| 原因 | ヒストグラムの動き |
|---|---|
| **A: 遮蔽** | セクションが<b>同じ LoD の中で</b>出入りする → <b>平ら</b> |
| **B: 降下の閾値** | 親と子が入れ替わる → <b>隣り合う LoD の間で数が移る</b> |

LoD は {@code sectionMetadata} の先頭 uint の上位 4 ビットである
[確認済 — `pos_util.glsl` の {@code getLoDLevel} = {@code packedPos.x>>28}]。

**さらに「どの隣接 LoD 対で移ったか」も出す** — B なら特定の段に集中するはずである。

### 3.3 ⚠ 名指しは数字が片方に寄ったときだけ

報告は 3 通りに分ける:

- {@code across-LoD move == 0} → <b>遮蔽</b>を指す
- {@code same-LoD swap == 0} → <b>降下の閾値</b>を指す
- **両方ある** → ⚠ <b>まだどちらも名指ししない</b>。どちらが優勢かと LoD 対を見る

---

## 4. 測り方

```bash
./gradlew runClient -Pvoxy5c4=on -Pvoxy5c5=cull -Pvoxy5c4Interval=1
```

**カメラを止めて、メッシュ化が落ち着くまで待つ** (`meshed` が増えなくなるまで)。
120 サンプル貯まると `[6-1]` が出る。

⚠ `⚠ Nothing to explain — the churn seen earlier was the tree growing` が出たら、
**Phase 5 の 42/60 は木の成長を数えていただけ**ということになる。
その場合は第一項目そのものが消える。

## 6. 結果 — <b>第一項目は消えた</b>

### 6.1 木が固定なら、選択集合は<b>ほぼ動かない</b>

MC 実機、カメラ静止 **かつ** 木が固定 (`meshed` が増えていない)、120 サンプル × 5 窓:

```
窓 1〜3:  the set never changed                        (120 / 120 が不変)
窓 4:     unchanged=117  same-LoD swap=0  across-LoD move=3
窓 5:     unchanged=119  same-LoD swap=0  across-LoD move=1
```

**117〜120 / 120 が不変。** Phase 5 で観測した `42/60` `49/60` は
<b>木が育っている間の変化</b>だった (meshed 3447 → 4417)。

> ⚠ **D を外さなかったのが誤りだった。** 候補を先に列挙していたのに、
> <b>いちばん平凡な候補を測定から外していなかった</b>。
> 「7〜8 割のフレームで揺れる」という前提そのものが誤りだった。

### 6.2 ⚠ HiZ の帰還は<b>起きていない</b>

```
same-LoD swap = 0   (全窓)
```

**同じ LoD 内での入れ替えが 1 件も無い。** 遮蔽で出入りしているなら
ここに出るはずである。**心当たりとして挙げていた HiZ の帰還は、起きていない。**

> LoD 別ヒストグラムで分けたから言えたことである。
> 集合の変化だけを数えていたら<b>「揺れている」で終わっていた</b> [規約 22]。

### 6.3 残る 1〜3 件は L0/L1 の移動 — <b>名指ししない</b>

```
across-LoD move = 3 / 1     adjacent LoD pairs that moved: L0/L1=1
sections entering/leaving per change: min=4 median=25 max=51
```

降下の閾値 (B) と整合するが、**120 サンプル中 1〜3 件では原因を名指ししない**
[規約 23]。⚠ 影響も小さい (1〜2%)。

### 6.4 ⚠⚠ Phase 5 の「揺れの主因は選択集合」は<b>誤りだった</b>

木が固定でも揺れは残る:

```
flickering pixels: median=4263 〜 87628 of 9216000    (0.05% 〜 0.95%)
```

**選択集合がほぼ不変なのに画素は揺れている。** したがって
<b>揺れの主因は選択集合ではない</b>。

⚠ Phase 5 §3.1 の記述は<b>木が育っている間の測定</b>に基づいていた。**訂正する。**

残る候補は<b>半透明の並び</b> ({@code atomicAdd}) である —
同じ窓で {@code order-only changed} が 41 / 17 / 10 と出ていたことと整合する。
**[未検証]** — 半透明の描画を外して揺れが消えるかを見れば分かるが、
⚠ <b>Vulkan 移植の成立性には効かない</b>ので優先度は低い。

## 7. 次 — <b>第二項目へ</b>

第一項目が消えたので、優先度は繰り上がる。

⚠ **第三項目 (`hiz` の振れ幅) は「第一項目を直せば動く」という見立てだったが、
選択が動いていなかった以上その筋も消えた。** 新しい観測:

```
hiz = 0.160 / 0.163 / 0.169  ...  0.785 / 0.893 / 1.243
```

**連続ではなく二極である。** 選択が不変なので<b>仕事量は一定</b>のはずで、
振れは仕事量では説明できない。<b>前段の待ちを吸っている</b>疑いが強い [未検証]。
