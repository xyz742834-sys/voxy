# Phase 5 完了記録 — MC への接続と実データ投入

**最終確認**: JUnit **269 PASS / 3 SKIP**、`interopCompositeCheck` **45 項目 PASS**、
MC 実機で 5c-5a の 5 項目が<b>空虚でなく</b>成立、
カルパス接続後の内訳を取得。

> **Voxy の本質が、実データで、参照実装と同じ並びで動いた。**
> 階層トラバーサルが LoD を選び、カルパスが遮蔽を落とし、
> 不透明・temporal・半透明の 3 パスが MC の画面に出ている。

```
NodeManager(実データ) → VkHiZ(自前の深度) → VkTraversal(選択) → prep → cull
  → 密テーブル → 不透明 / temporal / 半透明
  → IOSurface(BGRA/R32F) → GL 合成 → MC の色 + 深度 → 画面
```

## 3. 揺れ幅の測定 — <b>測定であって検査ではない</b>

**条件**: MC 実機、カメラ静止 (MVP が前サンプルと同一のフレームのみ集計)、
1920×1200、60 サンプル × 3 窓。

```
flickering pixels: min=0  median=16232 / 16889  max=180379 / 234328   of 2304000
```

| | |
|---|---|
| 中央値 | 約 **0.7%** |
| 最大 | 約 **8〜10%** |
| **最小 = 0** | ⚠ <b>これが要である</b> |

> **`min=0` は「連続する 2 フレームがビット一致した」ことを意味する。**
> 入力が変わらなければ経路は<b>決定的である</b>。
> 「全部ノイズ」という読みをここで落とせる。

### 3.1 ⚠⚠ <b>訂正</b>: 「主因は選択集合の変化」は誤りだった

当初こう書いた:

```
the SELECTED SET changed: 42 / 60,  49 / 60
```

**この測定は<b>木が育っている間</b>のものだった** (meshed 3447 → 4417)。
木が固定になるまで待って測り直すと:

```
unchanged = 117 〜 120 / 120        same-LoD swap = 0
```

**選択集合はほぼ動かない。** それでも揺れは残る (median 0.05〜0.95%) ので、
<b>揺れの主因は選択集合ではない</b>。

⚠ 残る候補は<b>半透明の並び</b> ({@code atomicAdd}) — 同じ窓で
{@code order-only changed} が 41 / 17 / 10 だったことと整合する。**[未検証]**

詳細は [`phase6-selection-churn.md`](phase6-selection-churn.md) §6。

### 3.2 バケット割り当ての変化は<b>各窓 1 件</b> — 原因は名指ししない

```
with the SAME set: assignment changed 1, order-only changed 41 / 17 / 10
```

順序だけの変化が大半で、これは `atomicAdd` 由来の想定どおり。
割り当ての変化は各窓 1 件しかない。

> ⚠ **1 件で原因を名指ししない** [規約 23]。
> しかも<b>メッシュ化が走り続けている</b> (meshed 3447 → 4417) ので、
> 同じ集合でも `sectionMetadata` が更新されてバケットが動く。
> **穏当な説明が既にある。**

### 3.3 ⚠ この測定は 1 度<b>自分の診断で汚染された</b>

最初の測定は `min=4134911 median=4186198 max=4747804 of 9216000` (45%) だった。
原因は<b>クリア色の掃引</b>(「画像が毎フレーム書かれているか」を見るために入れた診断)
を有効なままにしていたことで、**45% は空の面積を数えていただけ**だった。

> **【教訓】対照を足したら、それが<b>別の観測に混ざらないか</b>を見る。**
> 診断が本番の観測を壊した。

## 5. 未解決の問題

### 5.1 🔴 同期バリデーションがこの環境で機能しない (Phase 3 から継続)

「指摘ゼロ」は安全の証拠にならない。**バリアの検査は「呼び出しを消す」までしか

§3.1。**Phase 6 の第一項目**。

### 5.3 🟡 GL 版と同じ絵かは検証できない

GL バックエンドがこの Mac で動かない (`glDispatchComputeIndirect` /

### 5.4 🟡 `VkInteropProbe` は本番の構造ではない

5c の足場であり、`VoxyRenderSystem` 経由の本番配線とは別物。
⚠ **足場の欠陥を本番の欠陥として追いかけた**ことが実際にあった (§7.2)。

## 7. Phase 6 への引き継ぎ (優先度順)

### 7.1 ✅ 第一項目: <b>選択集合の揺れ</b> — <b>調査完了。消えた</b>

木が固定でカメラ静止なら **117〜120 / 120 のサンプルで集合は不変**。
Phase 5 の `42/60` は<b>木が育っている間</b>の測定だった。

⚠ **HiZ の帰還も起きていない** (`same-LoD swap = 0`)。
心当たりとして挙げていた筋は<b>否定された</b>。

詳細と、「D (木の成長) を測定から外していなかった」という誤りの記録は
[`phase6-selection-churn.md`](phase6-selection-churn.md)。

### 7.2 🥈 第二項目: `opaque` が支配的 (2.31 〜 3.49 ms、合計の 7〜9 割)

**draw 統合とは別の話**である。統合済みで draw は 7 本しかない。
疑うのは<b>フラグメント負荷</b>と<b>頂点/ジオメトリ処理</b>。

⚠ 関連: **深度境界 (`depthBound`) が中立値のままで `quads.frag:164` の discard が
効いていない**。本番では MC が描く近景の画素を落とすはずのものが落ちていない。
<b>フラグメント負荷に直接効く可能性がある</b>。

### 7.3 🥈 第三項目: `hiz` の 0.07 〜 1.24 ms (16 倍の振れ幅)

フレームによって何かが違う。他の区間は 1.5 倍程度の振れなので、**これだけ異質**。

⚠ **当初「第一項目を直せば動く」と見ていたが、その筋は消えた** (§7.1)。
新しい観測: 振れは<b>連続ではなく二極</b> (0.16 前後 / 0.8〜1.2)。
選択が不変なので<b>仕事量は一定</b>のはずで、仕事量では説明できない。
<b>前段の待ちを吸っている</b>疑い [未検証]。

## 8. Phase 7 への引き継ぎ (MC-Vulkan へのデバイス借用)

調査は [`phase6-device-sharing-survey.md`](phase6-device-sharing-survey.md)。
**アーキテクチャ変更なので「最適化」とは分けて扱う。**

### 8.1 ⚠ ホスト直接書き込みの列挙 — <b>済ませた</b>

survey §2.4.1 に**全 18 ファイルを A〜E に分類して列挙した**
(当初の見積もり「16 本」は実際には 18 本)。

**実際に手を入れるのは A + B + C の 10 本**、D の 3 本と E の 5 本は触らない。

> ⚠ **C (読み出しのみ) を忘れやすい。** 書き込みの破壊ばかり見ていると、
> <b>読み出しが 1 世代古いものを読む</b>ほうを落とす。
> 5c-5a で「絵が凍っている」と「読み戻しが凍っている」を区別できずに
> 往復したのは、まさにこの型である。

### 8.2 残る前提

- MC 26.2 は `MAX_SUBMITS_IN_FLIGHT = 2`。境界は<b>フレームではなく提出</b>
- 同期は fence ではなく<b>タイムラインセマフォ</b>
- ⚠ **借用と interop は排他** — `VK_EXT_metal_objects` を MC のデバイスは有効化していない。
  「MC が GL なら interop、Vulkan なら借用」の<b>2 経路</b>になる
- 正味 **-400 行前後**。⚠ 消える 1000 行は検証済み、増える 400 行は未検証

### 8.3 ⚠ 比較の基準は §2 の数字

**5c-4c の数字を参照点にしてはならない** (§2.1)。
