## 1. なぜこの段が今までと違うのか

5c-3b までの対照は<b>全て同じ形</b>だった:

> **入力を制御して、出力を予測する。**
> 合成地形をここに置いた → ここに出るはず。実ジオメトリを 291 セクション上げた → 291 セクション出るはず。

**トラバーサルではこの手が使えない。** 何を描くかを<b>GPU が選ぶ</b>。
選択を予測するには選択の実装を書き直すことになり、それは規約 4 そのものである
(予測と実装が同じ式を共有する)。

> **「置いたものが出る」から「出るべきものが出る」へ。**
> 主張の形を変えなければならない。

## 2. 調査結果

### 2.1 経路の全体

```
NodeStore/NodeManager  --(nodeBuffer)-->  traversal_dev.comp  --(renderQueue)-->  cmdgen  --> draw
        ↑ CPU                                   ↑ HiZ で遮蔽判定
```

| 部品 | 行数 | GL 依存 | 判定 |
|---|---:|---:|---|
| `NodeStore` | 314 | **0** | そのまま使える |
| `NodeManager` | 1718 | **4** (1 メソッド) | ⚠ <b>境界は `writeChanges(GlBuffer)` だけ</b> |
| `traversal_dev.comp` | 191 | — | ⚠ 既に `#ifdef VULKAN` 対応済み [Phase 2] |
| `HiZBuffer` | — | 多い (DSA) | Vulkan で書き直す |
| `AsyncNodeManager` / `NodeCleaner` | 1033 / 191 | 多い | この段では<b>使わない</b> |

> **境界が 3 度目に同じ形で出た。**
> `ModelUploadTarget` (5c-2b)、`IGeometryManager` (5c-3b)、そして
> `NodeManager.writeChanges` (ここ)。いずれも<b>CPU で並べ終えたバッファを上げる 1 手</b>である。

### 2.2 ⚠ ディスパッチループは CPU 駆動 [確認済]

`MAX_ITERATIONS = WorldEngine.MAX_LOD_LAYER + 1 = 5` 回、CPU から積む。
2 回目以降は `glDispatchComputeIndirect` で、<b>個数は前の回が書いたバッファ</b>から来る。

> **回数の上限は構造で決まっている** (CPU のループ回数)。
> Vulkan は `vkCmdDispatchIndirect` があるので<b>構造をそのまま移せる</b>。
> ⚠ <b>構造を変えるなら上限の根拠も変わる</b>。移すときに変えない。

### 2.3 ⚠⚠ GPU 側に<b>境界検査のない書き込み</b>がある

`queue.glsl` にコメントが残っている:

```glsl
//TODO: limit the size/writing out of bounds
uint nodePushIndex = -1;
void pushNode(uint nodeId) {
    nodeQueueSink[nodePushIndex++] = nodeId;   // ← 上限がない
}
```

キューが溢れると<b>範囲外に書く</b>。GL でも Vulkan でも未定義動作である。

⚠ **`enqueueChildren` のループは<b>上限がある</b>** — 調べたら予測が外れた:

```glsl
uint getChildCount(in UnpackedNode node) { return ((node.flags >> 2)&7U)+1; }
```

<b>3 ビット幅で抽出している</b>ので、データが何であっても <b>1..8 に収まる</b>。
「ノードデータ由来だから上限がない」という当初の見立ては<b>誤りだった</b>。
clamp は入れない — <b>要らない上限を足すと、なぜ足したかが分からなくなる</b>。

> **危険だと思った箇所を数えたら、片方は構造で守られていた。**
> 上限を切る前に<b>本当に上限が無いのか</b>を確かめる。

> **Phase 0 で OS レベルの GPU リセットを起こしたのと同じ型である。**
> Vulkan 版では<b>両方に上限を切る</b>。
> ⚠ 上限に当たったことを<b>数えて報告する</b> — 黙って切り捨てると
> 「描かれない」が「選ばれなかった」と区別できなくなる [規約 18]。

### 2.4 HiZ は<b>逆Zの min</b> で、穴埋めは no-op [確認済]

```glsl
float res = REDUCTION(REDUCTION(depths.x, depths.y), REDUCTION(depths.z, depths.w));
```

逆Zでは `REDUCTION = min` = <b>4 テクセルのうち最も奥</b>。
遮蔽判定は「最も奥の遮蔽物より更に奥のものだけ落とす」ので、これで保守的になる。

⚠ その手前の「穴埋め」は<b>どちらの規約でも no-op である</b>:

```glsl
bvec4 cv = equal(vec4(FAR), depths);
if (any(cv)) depths = mix(vec4(NEAR), depths, cv);   // FAR は FAR のまま、他は NEAR に
```

`mix(x,y,bvec)` は<b>true で y</b> なので、FAR の要素は FAR のまま残り、
他が NEAR になる。逆Zでは `min(0, 1, ...) = 0 = FAR` — <b>穴埋めしなくても同じ</b>。

> <b>参照仕様なので直さない。</b> ただし<b>「穴埋めが効いている」を前提にしない</b>。

## 4. 対照の設計

### 4.1 【A】出力の<b>集合としての性質</b>を主張する — 予測しない

いちばん強いのは<b>木の切り口 (cut) であること</b>である。

トラバーサルは根から降り、各ノードは<b>自分を描く</b>か<b>子を積む</b>かのどちらかをする。
したがって描かれた集合は<b>反鎖 (antichain)</b> でなければならない —
**描かれたノードの祖先が、描かれた集合に居てはならない。**

| 破れ方 | 絵に出る形 |
|---|---|
| 祖先と子孫が両方描かれる | <b>同じ体積が二重に描かれる</b> (深度で争う) |
| どちらも描かれない | <b>穴が開く</b> |

> **これは「どの切り口か」を予測せずに検査できる。**
> 主張しているのは<b>切り口であること</b>であって、切り口の場所ではない [規約 4]。

⚠ ただし「穴が無い」は<b>覆うべき範囲を知らないと言えない</b>。
5c-4b の合成木なら知っている。5c-4c では<b>弱い版</b>しか言えない
(描かれたノードは全て視錐台と交わる、など)。

### 4.2 【B】両方向を同時に要求する — <b>5c-1e の形</b>

「全部出る」「全部落ちる」は<b>どちらも失敗</b>である。

- 遮蔽物を<b>意図的に置いた</b>構成で、その裏のノードが落ちること
- <b>同時に</b>、遮蔽されていないノードが出ていること

⚠ トラバーサルには既に<b>統計バッファ</b>がある
(`traversalCounts[lod]` / `renderCounts[lod]`)。
LoD ごとの「見た数」と「描いた数」が取れるので、<b>両方向を数字で出せる</b>。

### 4.3 【C】カメラを動かして<b>変化の向き</b>だけ主張する

個々の選択を予測せず、単調性を言う。5c-1c で
`movingTheCameraCloserIncreasesTheClosestDepth` を作ったのと同じ発想。

| 主張 | |
|---|---|
| ノードに近づくと、その LoD レベルは<b>粗くならない</b> | 距離と LoD の単調性 |
| 視線を外すと、そのノードは集合から<b>出る</b> | 視錐台判定が効いている |
| 遠ざかると、描かれるノード数は<b>増えない</b> | ⚠ 粗くなるので<b>減るとは限らない</b>。増えないことだけ言う |

### 4.4 【D】CPU で同じ選択を再現する — <b>規約 4 に注意</b>

アルゴリズムは GL 版と同じはずなので、CPU で再現して突き合わせる手はある。
**ただし危険である**: GPU の実装と CPU の予測が<b>同じ規約を共有していないか</b>。

> 5c-1d で 4 度踏んだ型である。<b>採るなら、視錐台の判定を別の定式化で書く</b> —
> シェーダは平面との内外判定、CPU 側は 8 隅を射影して NDC で見る、のように。
> <b>同じ式を 2 回書いたものは対照にならない。</b>

⚠ **HiZ の遮蔽判定は CPU で再現しない。** 深度バッファの内容に依存するので、
再現しようとすると<b>レンダリングそのものを再現する</b>ことになる。
遮蔽については【B】の両方向だけで主張する。

### 4.5 まとめ — 何をどこで主張するか

| 主張 | 5c-4a | 5c-4b | 5c-4c |
|---|---|---|---|
| HiZ のミップが縮約の定義どおり | ✅ オフスクリーンで厳密に | | |
| 描かれた集合が<b>反鎖</b> | | ✅ | ✅ |
| 穴が無い (覆う) | | ✅ 合成木なので言える | ⚠ 弱い版のみ |
| 遮蔽で<b>落ちる</b>ものがある | | ✅ | ✅ |
| <b>同時に</b>出るものがある | | ✅ | ✅ |
| LoD が距離に対して単調 | | ✅ | ✅ |
| 上限に当たった回数 = 0 | | ✅ | ✅ |
| フレーム時間 | | | ✅ <b>初めて意味がある</b> |

## 6. 5c-4a 完了 — <b>HiZ のミップ連鎖</b>

### 6.1 何を作ったか

| | GL | Vulkan (`VkHiZ`) |
|---|---|---|
| 格納 | `GL_DEPTH24_STENCIL8` + `gl_FragDepth` | **`R32_SFLOAT` の色** |
| 読み側を 1 レベルに絞る | `GL_TEXTURE_BASE_LEVEL/MAX_LEVEL` | **レベルごとのビュー** |
| 断片シェーダ | `voxy:hiz/blit.fsh` | **同じものを使う** (`OUTPUT_COLOUR` を定義) |

traversal は `sampler2D` の `.r` を `texelFetch` するだけなので<b>色でも深度でも等価</b>である
[確認済 — `screenspace.glsl`]。

⚠ `textureGather` には LOD 引数が無いので、<b>ビューを絞る以外に方法がない</b>。
`VkDescriptorSetGroup.variantTextureLevel` を足した。

⚠ 精度は<b>むしろ上がる</b> (24bit 固定小数 → float)。
逆Zでは奥ほど 0 に近いので float のほうが遠方に細かい。
<b>GL 版と数値が一致するとは限らない</b>が、この環境では GL 版を走らせられないので
比較はもともとできない。

### 6.2 ⚠ レベル 0 だけは厳密に言えない

| レベル | 中身 |
|---|---|
| 0 | 元の深度の<b>再標本化</b>。元 (100x40) と HiZ (64x32) で大きさが違うので<b>一致は言えない</b> |
| i ≥ 1 | レベル i-1 の<b>ちょうど 2 倍</b>なので、`textureGather` の 4 テクセルは <b>2x2 ブロックそのもの</b> |

**したがって i ≥ 1 についてはビット単位で厳密に要求できる。**
レベル 0 については「平坦でないこと」だけを言う。

> <b>言えることと言えないことを分けて書く。</b>
> レベル 0 まで「一致」を主張すると、通らないか、通す代わりに許容幅を入れて
> <b>i ≥ 1 の厳密さまで緩める</b>ことになる。

### 6.3 検査

| 検査 | 主張 |
|---|---|
| `theChainIsSizedTheWayTheReferenceSizesIt` | 2 の冪へ<b>切り下げ</b>、レベル数 = `ceil(log2(max(w,h)))` |
| **`eachLevelIsTheExactReductionOfTheOneAbove`** | i ≥ 1 が i-1 の 2x2 の **min と厳密に一致** |
| `theSourcePatternActuallyDistinguishesMinFromMax` | ⚠ <b>対照</b>。平坦なら縮約が何でも通る |
| `takingTheMaximumInsteadWouldBeDetected` | ⚠ <b>対照</b>。min と max を区別できること |
| `levelZeroActuallySampledTheSource` | 元が読まれている |

### 6.4 変異で確かめた

| 変異 | 落ちた検査 |
|---|---|
| **`VkDepth.defines()` を外す** (`USE_REVERSE_Z` 忘れ) | 2 件 ✅ |
| 読むレベルを i-1 ではなく i に | 1 件 ✅ |
| レベルを絞らず全レベルのビューを渡す | 1 件 ✅ |

> ⚠ **1 つ目が要である。** 定義を忘れると `REDUCTION` が min から max へ反転し、
> HiZ は「最も手前」を持つことになる。すると遮蔽判定は
> <b>見えているノードを隠れていると判定して落とす</b> — <b>絵に穴が開く</b>。
> 落ちないし、警告も出ない。
>
> **5c-3a の再投影で予測した壊れ方が、別のシェーダでそのまま再現した。**
> `VkDepth.defines()` の呼び忘れは<b>この移植で繰り返し出る型</b>である。

### 6.5 ⚠ 検査の主張が過剰だった (自分で踏んだ)

`levelZeroActuallySampledTheSource` に
「レベル 0 の先頭が FAR なら元が空」という主張を入れたが、
模様の (0,0) が<b>たまたま 0.0 = FAR</b> だったので落ちた。**縮約は正しかった。**

> 実際の深度バッファでは<b>空が FAR なのは正常</b>である。
> 「FAR だから空」は成り立たない。模様のほうを 0 から外した —
> <b>0 の意味を 1 通りにする</b> [規約 18]。

## 7. ⚠⚠ `VkDepth.defines()` の呼び忘れを<b>構造で塞いだ</b> [規約 6]

### 7.1 なぜ塞ぐか — <b>2 度同じ型を踏んだ</b>

| 忘れると | 定数 | 絵はどうなるか |
|---|---|---|
| 5c-3a 再投影 | `CLOSER_SIGN` +1 → -1 | clamp が<b>奥へ押しやる</b>。遠景が MC の地形に負ける |
| 5c-4a HiZ | `REDUCTION` min → max | <b>見えているノードを落とす</b>。絵に穴 |
| — | `NEAR`/`FAR` 反転 | 「何も描いていない」の判定が全部裏返る |

**いずれも落ちないし警告も出ない。** どちらも変異を入れて確かめた実在の壊れ方である。

### 7.2 ⚠ GLSL の `#error` は<b>採らなかった</b>

最初 `depthutils.glsl` に
`#if defined(VULKAN) && !defined(USE_REVERSE_Z) #error ...` を置いた。**これは失敗だった。**

`#error` は<b>プリプロセスそのものを失敗させる</b>ので、
`VkShader.explainCompileFailure` が展開テキストを得られなくなり、
<b>他のガードの診断を潰した</b> — `gl_InstanceID` の案内が出なくなった。

> **ガードが他のガードを隠す。** 新しい検査を足すときは
> <b>既存の診断が生き残るか</b>を見ること。

**代わりに `VkShader.Builder.compile()` で Java 側から弾く。**
取り込みガード (`#define UNDEFINE_DEPTH`) の有無で判定する。
shaderc より先に、読めるメッセージで止まる。

### 7.3 ⚠⚠ ガードを入れたら<b>8 件の検査が落ちた</b> — <b>全部が本物の穴だった</b>

| シェーダ | 使っている定数 |
|---|---|
| `screenspace.glsl` (traversal が import) | `REDUCTION` / `NEAR` / `DEPTH_SCALAR_COMPARE_EQUAL` |
| `quads.frag` | `DEPTH_SCALAR_COMPARE` |
| `depth_resolve.frag` (非再投影版) | (取り込むが未使用。<b>使った瞬間に壊れる</b>) |

**`TraversalShaderTest` はトラバーサルを深度規約なしでコンパイルしていた。**

> ⚠ <b>5c-4b でその形を真似ていたら、遮蔽判定が裏返ったまま出荷していた。</b>
> HiZ が「最も手前」を持ち、見えているノードを隠れていると判定して落とす —
> <b>絵に穴が開くだけで、落ちないし警告も出ない</b>。
>
> **ガードは、書いた直後に「まだ書いていないコード」の欠陥を見つけた。**
> これが規約 6 (分かった制約は同じ変更の中でガードにする) の値打ちである。

### 7.4 検査

`aVulkanShaderThatForgetsTheDepthConventionCannotCompile`:

- 定義を忘れたら<b>読めるメッセージで落ちる</b> (何を呼ぶか・何が欠けているか・なぜ効くか)
- ⚠ <b>定義があれば通る</b>ことも要求する — 無いと「常に落ちるガード」と区別が付かない
- ⚠ <b>実在のシェーダで試す</b>。手書きの断片では `#import` が展開されず
  <b>ガードの発火条件を満たさない</b> (最初そう書いて空振りした)

## 8. 5c-4b 完了 — <b>合成の木でトラバーサルが動いた</b>

### 8.1 対照が全部成立した

| 主張 | 結果 |
|---|---|
| 【A】描かれた集合が<b>反鎖</b> (閾値 6 通り) | ✅ どの切り口でも祖先と子孫が同時に出ない |
| 【B】粗い閾値 → <b>根だけ</b> | ✅ 「全部描く」を落とす |
| 【B】細かい閾値 → <b>子だけ</b>、根は出ない | ✅ 「常に根」を落とす |
| 視錐台 — 後ろは落ち、前は出る | ✅ 両方向 |
| 【C】同じフレームで<b>近いほど細かい</b> | ✅ 遠いほうは根で止まる |
| 【C】遠ざかると<b>粗くなる一方</b> | ✅ 下記 |
| 上限 — 溢れが<b>数まで一致</b> | ✅ 捨て 4 / 範囲外読み 4 / 描画 4 |
| 上限 — 足りていれば <b>0 件</b> | ✅ 「常に 4 を返すカウンタ」を落とす |

カメラを遠ざけたときの切り口:

```
finest=[0, 0, 0, 1, 1, 2]   drawn=[64, 64, 64, 8, 8, 1]
```

葉 64 → 子 8 → 根 1。<b>単調で、かつ実際に変わっている</b>
(全部同じなら単調性は何も言っていない)。

> ⚠ 「遠ざかると<b>数が減る</b>」とは主張していない。粗くなるので数は減りうるが、
> <b>体積は同じ</b>である。<b>増えないこと</b>だけを言う。

### 8.2 変異で確かめた

| 変異 | 落ちた検査 |
|---|---|
| フリップフロップをやめて常に variant 0 | 4 件 ✅ |
| {@code queueIdx} を常に 0 | 3 件 ✅ |
| `pushNode` の上限を外す | 溢れの検査 ✅ |
| `getCurrentNode` の上限を外す | 溢れの検査 ✅ |
| 常に降りる / 決して降りない | それぞれ 3 件 / 5 件 ✅ |
| カメラの位置を無視する | <b>単調性の検査だけ</b> ✅ (切り分けが効いている) |
| **ディスパッチ間のバリアを外す** | ⚠ **0 件 — 素通り** |

### 8.3 ⚠⚠ バリアはこの環境で<b>誰も見張っていない</b>

| 変異 | 結果 |
|---|---|
| ループ内の {@code barrier(cmd)} <b>呼び出し</b>を消す | ✅ 落ちる (呼び出しを数えているため) |
| {@code barrier()} の<b>中身</b>を空にする | ❌ <b>どの検査も通る</b> |

数えているのが<b>呼び出しであって効果ではない</b>のと、
仕事量が小さいと GPU が事実上直列に走るためである。
**同期バリデーションがこの環境で機能しない**ので、範囲が足りているかは検証できない [未検証]。

> **「限界がある」ではなく<b>「どこまで捕まるかを測った」</b>として記録する。**
> 曖昧な但し書きは後から読めない。境界線が実測で引いてあれば読める。
>
> ⚠ これは Phase 3 から抱えている穴で、<b>Lavapipe が唯一の解</b>だった。
> Phase 6 で着手する価値が上がっている。

### 8.4 ⚠ 警戒が過剰だった箇所 (記録)

危険に見えた 4 箇所のうち、<b>本物は 2 つ</b>だった。

| 箇所 | 判定 |
|---|---|
| `pushNode` の書き込み | ⚠ <b>本物</b>。予約の添字が際限なく増える |
| `getCurrentNode` の読み出し | ⚠ <b>本物</b>。個数も溢れても増え続けるので境界にならない |
| `enqueueChildren` の子数ループ | ✅ 安全。`((flags>>2)&7)+1` = <b>3 ビット抽出で 1..8</b> |
| `isCulledByHiz` の二重ループ | ✅ 安全。ミップレベルを大きさから選ぶので<b>領域が常に数テクセル</b> |

> **上限を切る前に、本当に上限が無いのかを確かめる。**
> 要らない上限を足すと<b>必要な上限の理由まで薄まる</b>。

### 8.5 境界がこの形で出るのは<b>3 度目</b>

| 段 | 境界 | 渡すもの |
|---|---|---|
| 5c-2b | `ModelUploadTarget` | ベイク済みのモデル |
| 5c-3b | `IGeometryManager` | メッシュ化済みのセクション |
| **5c-4b** | **`NodeUploadTarget`** | 更新のあったノード |

いずれも<b>CPU で並べ終えたバッファを上げる 1 手</b>である。
<b>Voxy の設計が元々そうなっている</b>ので、移植が想定より素直に進んでいる。

### 8.6 ⚠ 同じ詰め方に<b>ワード順が 2 通り</b>ある

| | long の中身 | 書き出し |
|---|---|---|
| `SyntheticTerrain.packPosition` | 下位 = `.x` | 下位を先に |
| `NodeStore.nodePosition` | <b>上位 = `.x`</b> | 上位を先に |

**メモリ上は同じ並びになる**が、long の中では逆である。
片方の書き出し規約でもう片方の long を書くと<b>位置が滅茶苦茶になる</b> —
落ちないし、地形はどこかに描かれる。5c-4c で実ノードを流すときの罠。

## 9. ⚠⚠ ワード順の件は<b>「別物」ではなく「入れ替え」だった</b>

8.6 で「同じ詰め方にワード順が 2 通りある」と書いたが、<b>関係を取り違えていた</b>。
調べると:

```
WorldEngine のキー : lvl<<60 | y<<52 | z<<28 | x<<4
packPosition       : px = lvl<<28 | y<<20 | z上位   (long の下位ワード)
                     py = x<<4 | z下位<<28          (long の上位ワード)

  (int)(key >>> 32) == px          (int) key == py
```

**キーは packPosition の 2 ワードを入れ替えたものである。**

> これが分かると、上流が<b>復号せずに上位ワードから書いている</b>理由が読める
> [`NodeStore.writeNode` / `SectionMeta.writeMetadataSplitParts`]。
> メモリ上は `.x = px, .y = py` になり、`pos_util.glsl` の読み方と合う。
>
> ⚠ 5c-3b で「別物なので復号して詰め直す」と書いたのは<b>結果は正しいが理由が違う</b>。
> `VkRealSectionUpload` は遠回りをしている。<b>動いていて検査もあるので変えない</b> —
> 等価な書き換えで壊す危険のほうが大きい。

**関係そのものを検査で固定した** (`theWorldKeyIsPackPositionWithItsWordsSwapped`)。
崩れたら<b>上流の書き出しとこちらの詰め直しが同時に壊れる</b>ので、
ここを見張るのが最も広く効く。

> **【規約 21】「別物だ」で済ませない。<b>どう違うのかを式で書く。</b>**
> 「別物」は対処 (復号して詰め直す) を導くが、
> <b>なぜ上流がそうしていないのか</b>を説明しない。
> 説明できない差分は、次に同じ形を見たときに<b>また別物に見える</b>。

## 10. 5c-4c の準備 — <b>GPU の区間計測</b>

`VkGpuTimer` を足した。この装置は `timestampValidBits=64`, `period=1.0ns` で<b>使える</b>。

| 検査 | 主張 |
|---|---|
| `reportWhetherTimestampsAreAvailableAtAll` | 使えるかを<b>まず言う</b> |
| **`aBiggerWorkloadMeasuresLonger`** | 8x の仕事は 1x より長い (実測 3.719ms / 0.057ms) |

> ⚠ <b>「正の数が返る」だけでは定数を返す実装と区別できない</b> [規約 11]。

> ⚠ 取れないときは <b>{@code null}</b> を返す。0 を返すと<b>「速いから 0」と読める</b> [規約 18]。

### 10.1 ⚠ 初回は<b>数字を出すだけ</b>

> 合計を見て「遅い」と判断して最適化に飛ぶと、
> <b>測ってから絞る</b>という順序が崩れる。内訳が出て初めて何を疑うかが決まる。

## 11. 5c-4c の下準備

### 11.1 `verifyIntegrity()` は<b>名前どおりだった</b> — 確かめた

上流が用意した不変条件検査なので、こちらの反鎖検査とは<b>独立した根拠</b>になる。
ただし名前だけで信用せず、<b>壊して落ちることを確かめた</b>:

| 壊し方 | 結果 |
|---|---|
| 監視器がノードを見なくなる | ✅ 落ちる |
| 監視集合を渡して、余計な位置がある | ✅ 落ちる (⚠ <b>引数なしでは見ない</b>) |
| ノード集合を渡して、食い違う | ✅ 落ちる |
| 素直に組み立てる | ✅ 通る (弾きすぎていない) |

中身は実質的である — 上から辿って、位置集合・ノード数・要求数・最上位ノード集合を
<b>両方向で</b>突き合わせる。

> ⚠ **例外に一切メッセージが無い。** 素の {@code new IllegalStateException()} が 30 箇所以上。
> 発火しても<b>どの不変条件が壊れたか分からない</b>。
> 上流のコードなので<b>今は触らない</b> — 5c-4c で実際に発火したら、
> <b>そのとき必要なものだけ</b>に付ける。予測で参照仕様を触らない。

### 11.2 境界 4 度目 — <b>今回は上流が既に抽象にしていた</b>

`BasicAsyncGeometryManager` は <b>GL に一切触れない</b>。
クラス自身が「the underlying store is irrelevant」と書いている。
割り当てを `AllocationArena` で決め、<b>CPU 側のバッファを溜める</b>だけである。

**したがって Vulkan 側は流すだけでよく、新しい管理器は要らない** (`VkGeometryFlush`)。

### 11.3 ⚠ 罠は<b>要素単位とバイト単位</b>

`getUploads()` の鍵は<b>要素 (quad) 単位</b>である。バイトに直し忘れると
<b>8 分の 1 の位置へ書き、他のセクションを黙って壊す</b>。

### 11.4 ⚠ 「0 でない」で書いた検査が変異を素通しした

メタデータの検査を最初「その位置が全部 0 でない」で書いたところ、
<b>刻みを 32 から 16 にずらす変異が通った</b> — 重なった領域にも値が入るためである。

**位置の中身まで要求する形に直した** (先頭 8 バイトは位置、上位ワードが先)。

> **「何か入っている」は主張ではない。<b>何が入っているべきか</b>を書く。**
> 規約 18 の系列 — 0 の意味が 1 通りか、を「非 0 の意味が 1 通りか」に広げたもの。

### 12.2 ⚠ ここまでに踏んだもの (5 つ、いずれも「落ちない」型)

| # | 何が起きたか | 症状 |
|---|---|---|
| 1 | アトラスを転送していなかった | 一色になる |
| 2 | 合成器の選択に `HIERARCHICAL` を入れ忘れ (`DepthMode.NONE`) | <b>クリア色が画面を覆う</b> |
| 3 | 自前投影が既定で無効 | 遠景が届かない |
| 4 | `cmdgen` が要求する<b>可視の印</b>を書いていなかった | テーブルが空 |

> 「<b>このフレームの描画は前フレームのテーブルで行う</b>」と書いていた。
> <b>読んでいれば reset の前に取ると分かった。</b>

### 12.3 ⚠⚠ 進め方の反省 — <b>測る前に原因を名指しした 3 回はすべて外れた</b>

| 名指しした原因 | 実際 |
|---|---|
| 「要求のループが繋がっていない」 | <b>動いていた</b> (早いサンプルだけ見て判断した) |
| 「不正な mesh id が入っている」 | <b>0 件だった</b> |
| 「可視の修正は効かなかった」 | <b>効いていた</b> (木が降りる前のサンプルを見た) |

**共通するのは「1 サンプルで結論を出した」こと。**
一方、<b>1 つ測って半分に絞る</b>を 4 回繰り返した側は毎回前進した:

```
footprint → 選択と画素は別      不正 id → キューは正常
totalQuads → テーブルは正常      描画コマンド → prefix の入力
```

> **【規約 22】原因を名指しする前に、<b>それを分ける 1 つの数字</b>を出す。**
> 説明は安く、測定は高いように見えるが、<b>外れた説明の往復のほうが高い</b>。
>
> **【規約 23】1 サンプルで結論を出さない。** 系が落ち着くまでの値と、
> 落ち着いたあとの値は別物である。
