## 1. なぜこの段が今までと違うのか

5c-3b までの対照は<b>全て同じ形</b>だった:

> **入力を制御して、出力を予測する。**
> 合成地形をここに置いた → ここに出るはず。実ジオメトリを 291 セクション上げた → 291 セクション出るはず。

**トラバーサルではこの手が使えない。** 何を描くかを<b>GPU が選ぶ</b>。
選択を予測するには選択の実装を書き直すことになり、それは規約 4 そのものである
(予測と実装が同じ式を共有する)。

> **「置いたものが出る」から「出るべきものが出る」へ。**
> 主張の形を変えなければならない。

## 2. 調査結果

### 2.1 経路の全体

```
NodeStore/NodeManager  --(nodeBuffer)-->  traversal_dev.comp  --(renderQueue)-->  cmdgen  --> draw
        ↑ CPU                                   ↑ HiZ で遮蔽判定
```

| 部品 | 行数 | GL 依存 | 判定 |
|---|---:|---:|---|
| `NodeStore` | 314 | **0** | そのまま使える |
| `NodeManager` | 1718 | **4** (1 メソッド) | ⚠ <b>境界は `writeChanges(GlBuffer)` だけ</b> |
| `traversal_dev.comp` | 191 | — | ⚠ 既に `#ifdef VULKAN` 対応済み [Phase 2] |
| `HiZBuffer` | — | 多い (DSA) | Vulkan で書き直す |
| `AsyncNodeManager` / `NodeCleaner` | 1033 / 191 | 多い | この段では<b>使わない</b> |

> **境界が 3 度目に同じ形で出た。**
> `ModelUploadTarget` (5c-2b)、`IGeometryManager` (5c-3b)、そして
> `NodeManager.writeChanges` (ここ)。いずれも<b>CPU で並べ終えたバッファを上げる 1 手</b>である。

### 2.2 ⚠ ディスパッチループは CPU 駆動 [確認済]

`MAX_ITERATIONS = WorldEngine.MAX_LOD_LAYER + 1 = 5` 回、CPU から積む。
2 回目以降は `glDispatchComputeIndirect` で、<b>個数は前の回が書いたバッファ</b>から来る。

> **回数の上限は構造で決まっている** (CPU のループ回数)。
> Vulkan は `vkCmdDispatchIndirect` があるので<b>構造をそのまま移せる</b>。
> ⚠ <b>構造を変えるなら上限の根拠も変わる</b>。移すときに変えない。

### 2.3 ⚠⚠ GPU 側に<b>境界検査のない書き込み</b>がある

`queue.glsl` にコメントが残っている:

```glsl
//TODO: limit the size/writing out of bounds
uint nodePushIndex = -1;
void pushNode(uint nodeId) {
    nodeQueueSink[nodePushIndex++] = nodeId;   // ← 上限がない
}
```

キューが溢れると<b>範囲外に書く</b>。GL でも Vulkan でも未定義動作である。

同様に `enqueueChildren` のループ:

```glsl
uint children = getChildCount(node);
for (int i = 0; i < children; i++) { pushNode(ptr+i); }
```

`children` は<b>ノードデータ由来</b>である。八分木なので 8 以下のはずだが、
<b>データが壊れていれば上限がない</b>。

> **Phase 0 で OS レベルの GPU リセットを起こしたのと同じ型である。**
> Vulkan 版では<b>両方に上限を切る</b>。
> ⚠ 上限に当たったことを<b>数えて報告する</b> — 黙って切り捨てると
> 「描かれない」が「選ばれなかった」と区別できなくなる [規約 18]。

### 2.4 HiZ は<b>逆Zの min</b> で、穴埋めは no-op [確認済]

```glsl
float res = REDUCTION(REDUCTION(depths.x, depths.y), REDUCTION(depths.z, depths.w));
```

逆Zでは `REDUCTION = min` = <b>4 テクセルのうち最も奥</b>。
遮蔽判定は「最も奥の遮蔽物より更に奥のものだけ落とす」ので、これで保守的になる。

⚠ その手前の「穴埋め」は<b>どちらの規約でも no-op である</b>:

```glsl
bvec4 cv = equal(vec4(FAR), depths);
if (any(cv)) depths = mix(vec4(NEAR), depths, cv);   // FAR は FAR のまま、他は NEAR に
```

`mix(x,y,bvec)` は<b>true で y</b> なので、FAR の要素は FAR のまま残り、
他が NEAR になる。逆Zでは `min(0, 1, ...) = 0 = FAR` — <b>穴埋めしなくても同じ</b>。

> <b>参照仕様なので直さない。</b> ただし<b>「穴埋めが効いている」を前提にしない</b>。

## 3. 段の分け方 — <b>予測できる形を 1 段はさむ</b>

| 段 | 変える 1 変数 | ノード木 | 選択 |
|---|---|---|---|
| **5c-4a** | <b>HiZ の生成</b> | — | — |
| **5c-4b** | <b>トラバーサルの機構</b> | **合成** (CPU で組む) | 予測できる |
| **5c-4c** | <b>選択が実データで起きる</b> | 実データ | ⚠ 予測できない |

**5c-4b が要である。** 合成のノード木なら<b>木の形をこちらが決める</b>ので、
「この構成なら必ずこれが出る」を予測できる。
つまり<b>「置いたものが出る」の形を 1 段だけ保てる</b> —
機構の誤りと選択の誤りを、そこで切り分けられる。

> 5c-3 で「合成地形 → 実ジオメトリ」と分けたのと同じ構造を、木に対して行う。

## 4. 対照の設計

### 4.1 【A】出力の<b>集合としての性質</b>を主張する — 予測しない

いちばん強いのは<b>木の切り口 (cut) であること</b>である。

トラバーサルは根から降り、各ノードは<b>自分を描く</b>か<b>子を積む</b>かのどちらかをする。
したがって描かれた集合は<b>反鎖 (antichain)</b> でなければならない —
**描かれたノードの祖先が、描かれた集合に居てはならない。**

| 破れ方 | 絵に出る形 |
|---|---|
| 祖先と子孫が両方描かれる | <b>同じ体積が二重に描かれる</b> (深度で争う) |
| どちらも描かれない | <b>穴が開く</b> |

> **これは「どの切り口か」を予測せずに検査できる。**
> 主張しているのは<b>切り口であること</b>であって、切り口の場所ではない [規約 4]。

⚠ ただし「穴が無い」は<b>覆うべき範囲を知らないと言えない</b>。
5c-4b の合成木なら知っている。5c-4c では<b>弱い版</b>しか言えない
(描かれたノードは全て視錐台と交わる、など)。

### 4.2 【B】両方向を同時に要求する — <b>5c-1e の形</b>

「全部出る」「全部落ちる」は<b>どちらも失敗</b>である。

- 遮蔽物を<b>意図的に置いた</b>構成で、その裏のノードが落ちること
- <b>同時に</b>、遮蔽されていないノードが出ていること

⚠ トラバーサルには既に<b>統計バッファ</b>がある
(`traversalCounts[lod]` / `renderCounts[lod]`)。
LoD ごとの「見た数」と「描いた数」が取れるので、<b>両方向を数字で出せる</b>。

### 4.3 【C】カメラを動かして<b>変化の向き</b>だけ主張する

個々の選択を予測せず、単調性を言う。5c-1c で
`movingTheCameraCloserIncreasesTheClosestDepth` を作ったのと同じ発想。

| 主張 | |
|---|---|
| ノードに近づくと、その LoD レベルは<b>粗くならない</b> | 距離と LoD の単調性 |
| 視線を外すと、そのノードは集合から<b>出る</b> | 視錐台判定が効いている |
| 遠ざかると、描かれるノード数は<b>増えない</b> | ⚠ 粗くなるので<b>減るとは限らない</b>。増えないことだけ言う |

### 4.4 【D】CPU で同じ選択を再現する — <b>規約 4 に注意</b>

アルゴリズムは GL 版と同じはずなので、CPU で再現して突き合わせる手はある。
**ただし危険である**: GPU の実装と CPU の予測が<b>同じ規約を共有していないか</b>。

> 5c-1d で 4 度踏んだ型である。<b>採るなら、視錐台の判定を別の定式化で書く</b> —
> シェーダは平面との内外判定、CPU 側は 8 隅を射影して NDC で見る、のように。
> <b>同じ式を 2 回書いたものは対照にならない。</b>

⚠ **HiZ の遮蔽判定は CPU で再現しない。** 深度バッファの内容に依存するので、
再現しようとすると<b>レンダリングそのものを再現する</b>ことになる。
遮蔽については【B】の両方向だけで主張する。

### 4.5 まとめ — 何をどこで主張するか

| 主張 | 5c-4a | 5c-4b | 5c-4c |
|---|---|---|---|
| HiZ のミップが縮約の定義どおり | ✅ オフスクリーンで厳密に | | |
| 描かれた集合が<b>反鎖</b> | | ✅ | ✅ |
| 穴が無い (覆う) | | ✅ 合成木なので言える | ⚠ 弱い版のみ |
| 遮蔽で<b>落ちる</b>ものがある | | ✅ | ✅ |
| <b>同時に</b>出るものがある | | ✅ | ✅ |
| LoD が距離に対して単調 | | ✅ | ✅ |
| 上限に当たった回数 = 0 | | ✅ | ✅ |
| フレーム時間 | | | ✅ <b>初めて意味がある</b> |
